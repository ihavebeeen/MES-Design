# POC 평가

목표는 **화면의 디자인·배치·정보 위계를 빠르고 명확하게 확인**하는 것이다. 작동하는 프로토타입 제작/검증이 아니다. 기능 미구현은 예상 가능한 상태이며, 그것을 찾아 나열하는 데 시간을 쓰지 않는다.

단계별 피드백은 [S1](../THIRD_PARTY_LICENSES.md#s1-anthropic), 초기 시안과 운영 검사 분리는 [S4](../THIRD_PARTY_LICENSES.md#s4-govuk), 디자인/기술 검사 분리는 [S2](../THIRD_PARTY_LICENSES.md#s2-impeccable)를 참고했다. 이 저장소의 POC 정의와 아래 제외 범위는 사용자가 정한 정책이다.

## 평가에서 제외할 것

사용자가 별도로 요청하지 않은 다음 항목은 찾기 위해 조사하지도, 본문 지적으로 올리지도 않는다:

- 샘플 날짜와 표 데이터 불일치, mock data 값 차이.
- `조회`, `출력`, `LOT조회` 등 미구현 동작.
- `Esc`, 초점 복귀, 키보드 접근성.
- 1280px 등 추가 반응형 검증.
- API, 저장, 다운로드 검증.
- ScreenRequest, receipt, 자동화/승격 증적의 존재·최신성.
- Figma와 코드 fixture 값 차이.

이를 이유로 blocked·실패·감점·승격 불가를 출력하지 않는다. `screen:audit`, `screen:handoff`, 빌드·자동 검사를 POC 선행 조건으로 실행하지 않는다. 버튼을 누르는 것은 필요한 다른 **시각적 상태를 보기 위한 수단**일 수 있지만, 동작 검증이 목적은 아니다. 정적 캡처로 충분하면 그 자리에서 평가한다.

이 제외는 시안의 의미·가독성까지 면제하지 않는다. **날짜 값이 다른 것**은 제외하지만, 같은 의미의 **날짜 필드가 중복되어 읽기를 방해하는 것**은 평가한다. 정보가 읽히지 않거나 역할 구분이 어려우면 시각적 해결 방식의 문제로 설명하고 기술적 접근성 감사로 확대하지 않는다.

## 판단 순서

1. 사용자의 디자인 질문과 확인하려는 아이디어를 고정한다. 알려진 사실을 재질문하지 않는다.
2. 최신 시안/스크린샷과 필요한 업무 설명을 본다. 원본 보존이 질문이면 원본의 관련 구역만 비교한다. 원본이 없으면 보존 여부는 단정하지 않고 현재 시안 평가는 계속한다.
3. 다음 질문을 현재 대상에 맞춰 사용한다. 전체 체크리스트를 출력하지 않는다.

| 질문 | MES에서 확인할 것 | 판단 근거 |
|---|---|---|
| 함께 보여줄 이유가 있는가? | 같은 작업/생산실적의 판단에 도움이 되는가? 무관한 정보를 한 팝업에 넣지 않았는가? | 사용자 업무 사실, S3의 업무와의 대응 |
| 서로 다른 정보로 읽히는가? | 투입품·부산물 등의 역할이 제목·그룹·위치로 구분되며 관계도 보이는가? | S1의 위계, S3의 인지 단서 |
| 표현 방식이 일에 맞는가? | 표가 비교/스캔에 이득을 주는가, 단순 상세정보에 불필요한 헤더·열·빈 영역을 더하는가? | 현재 MES 컴포넌트 의미, S3의 정보 경쟁 감소 |
| 반복/불필요한 정보가 있는가? | 상위 문맥과 같은 필드가 새 정보를 주는가? 독립 해석/추적 때문에 반복해야 하는가? | S3의 기억 부담과 중복 사이의 절충 |
| 기존 업무 구조를 보존했는가? | 원본의 필터·표·선택·액션 역할을 이유 없이 바꾸지 않았는가? | 사용자 원본/요구, S3의 일관성·숙련자 효율 |
| 밀도와 여백이 자연스러운가? | 중요한 정보를 찾기 쉬운가? 작은 데이터에 과도하게 큰 영역을 쓰거나 보조 정보가 본문보다 강하지 않은가? | S1의 위계, S2의 맥락·그룹화 |

S3는 [Nielsen 휴리스틱을 MES 질문으로 번역한 근거](../THIRD_PARTY_LICENSES.md#s3-nng)다. 고정 레이아웃이나 필드 개수 기준이 아니다.

4. 관찰과 가설을 구분하고, 보존할 장점과 가장 효과가 큰 국소 수정을 고른다. 정보 관계/구조가 실제로 잘못됐을 때만 구조 재검토를 권한다.

### 투입정보·부산물 팝업의 평가 질문

이 사례에서는 다음 여섯 질문으로 한정한다. 다른 화면에는 업무 대상에 맞게 바꾼다.

1. 투입정보 팝업에 부산물을 함께 보여주는 것이 이해되는가?
2. 투입품과 부산물이 서로 다른 정보로 읽히는가?
3. 부산물 한 건을 표로 보여주는 방식이 적절한가?
4. 생산일자처럼 중복되거나 불필요한 정보가 있는가?
5. 원본 MES 화면의 필터·표·액션 구조를 훼손하지 않았는가?
6. 시각적 밀도와 남는 공간이 자연스러운가?

한 건이라는 이유만으로 표를 없애지 않는다. 동일 열 비교, 확정된 복수 건 요구, 정렬된 스캔이 필요하면 유지할 수 있다. 부산물 생산일자가 선택된 생산실적과 같은 의미라는 확인이 있을 때 중복 제거를 제안한다. 서로 다른 일자일 수 있는데 임의 삭제하지 않는다. 이전 결론을 최신 화면을 보지 않고 반복하지 않는다.

## 결과 형식

다음 형식을 사용한다. 잘된 점/애매한 점은 각각 최대 3개, 가장 먼저 수정할 것은 1개다. 빈 칸을 채우기 위해 지적을 만들지 않는다. 수정할 문제가 없으면 “없음 — 현재 방향 유지”라고 쓴다.

```markdown
## POC 평가

### 잘된 점
- 관찰한 특징과 보존할 이유 (최대 3개)

### 애매한 점
- 구체적인 부분, 영향 또는 확인할 전제 (최대 3개)

### 가장 먼저 수정할 것
- 가장 작은 유효한 수정과 이유 (1개)

### 최종 의견
- 유지 / 소폭 수정 / 구조 재검토 — 핵심 이유
```

최종 의견은 셋 중 하나만 선택한다. `유지`는 디자인 방향 유지이지 구현 완료/승인이 아니다. 국소 변경이면 `소폭 수정`, 업무 대상·정보 관계·주요 흐름을 다시 정해야 하면 `구조 재검토`다. 자료가 부족해 의견 자체를 낼 수 없으면 억지로 선택하지 말고 필요한 자료만 요청한다.

구현 문제를 우연히 발견해도 상세 목록·심각도·증적을 본문이나 부록으로 붙이지 않는다. 필요한 경우 다음 **한 줄 안내만** 추가한다. 보관 요청이 없으면 별도 backlog 파일도 만들지 않는다.

```markdown
### 구현 단계에서 확인할 항목
현재 POC 평가 범위에서는 제외하며, 구현 감사 요청 시 별도로 확인한다.
```

특정 구현 검사도 명시적으로 요청받았다면 그것만 별도 `요청한 추가 검사`로 보고한다. 추가 검사 결과를 POC 최종 의견에 섞거나 무관한 구현 항목을 열거하지 않는다.
