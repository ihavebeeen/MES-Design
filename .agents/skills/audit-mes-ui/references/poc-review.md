# POC 평가

목표는 **화면의 디자인·배치·정보 위계를 빠르고 명확하게 확인**하는 것이다. 작동하는 프로토타입 제작/검증이 아니다. 기능 미구현은 예상 가능한 상태이며, 그것을 찾아 나열하는 데 시간을 쓰지 않는다.

단계별 피드백은 [S1](../THIRD_PARTY_LICENSES.md#s1-anthropic), 초기 시안과 운영 검사 분리는 [S4](../THIRD_PARTY_LICENSES.md#s4-govuk), 디자인/기술 검사 분리는 [S2](../THIRD_PARTY_LICENSES.md#s2-impeccable)를 참고했다. 이 저장소의 POC 정의와 아래 제외 범위는 사용자가 정한 정책이다.

## 평가에서 제외할 것

사용자가 별도로 요청하지 않은 다음 항목은 찾기 위해 조사하지도, 본문 지적으로 올리지도 않는다:

- 샘플 날짜와 표 데이터 불일치, mock data 값 차이.
- `조회`, `출력`, `LOT조회` 등 미구현 동작.
- `Esc`, 초점 복귀, 키보드 접근성.
- 1280px 등 추가 반응형 검증.
- API, 저장, 다운로드 검증.
- ScreenRequest, receipt, 자동화/승격 증적의 존재·최신성.
- Figma와 코드 fixture 값 차이.

이를 이유로 blocked·실패·감점·승격 불가를 출력하지 않는다. `screen:audit`, `screen:handoff`, 빌드·자동 검사를 POC 선행 조건으로 실행하지 않는다. 버튼을 누르는 것은 필요한 다른 **시각적 상태를 보기 위한 수단**일 수 있지만, 동작 검증이 목적은 아니다. 정적 캡처로 충분하면 그 자리에서 평가한다.

이 제외는 시안의 의미·가독성까지 면제하지 않는다. **날짜 값이 다른 것**은 제외하지만, 같은 의미의 **날짜 필드가 중복되어 읽기를 방해하는 것**은 평가한다. 정보가 읽히지 않거나 역할 구분이 어려우면 시각적 해결 방식의 문제로 설명하고 기술적 접근성 감사로 확대하지 않는다.

## 판단 순서

1. 사용자의 디자인 질문과 확인하려는 아이디어를 고정한다. 알려진 사실을 재질문하지 않는다.
2. 최신 시안/스크린샷과 필요한 업무 설명을 본다. 원본 보존이 질문이면 원본의 관련 구역만 비교한다. 원본이 없으면 보존 여부는 단정하지 않고 현재 시안 평가는 계속한다.
3. 아래 관점 중 요청 범위에 해당하는 것은 모두 검토한다. 세 개의 지적을 찾았다고 멈추지 않는다. 내부적으로 각 관점을 유지할 만함/개선 필요/자료 부족/비해당으로 구분하되, 전체 체크리스트를 출력하거나 빈 칸을 채울 지적을 만들지 않는다. 특정 구역만 요청받았다면 그 구역에 적용하며, 보이지 않는 상태·다른 화면을 찾기 위해 감사 범위를 늘리지 않는다.

| 관점 | MES에서 확인할 것 | 판단 근거 |
|---|---|---|
| 업무상 우선순위 | 무엇을 먼저 식별·비교·판단해야 하는가? 그 정보가 먼저 보이는가? 처리 순서가 미정이면 임의로 긴급도나 새 업무 규칙을 만들지 않는다. | 사용자 업무 사실, S3의 업무 대응·효율 |
| 정보 관계와 그룹화 | 함께 볼 정보와 구별할 정보가 제목·구역으로 읽히는가? 반복 필드는 새 정보/독립 해석에 필요한가, 같은 내용을 경쟁시키는가? | S2의 그룹화, S3의 인지 단서·중복 절충 |
| 시선과 읽기 순서 | 식별 정보·판단 근거·입력/행동의 순서가 목적에 맞는가? 제목·글자 크기/굵기·색·위치가 중요한 정보에 맞춰 강조되는가? | S1의 위계, S3의 정보 경쟁 감소 |
| 배치의 적합성과 절충 | 페이지/슬라이드/팝업, 좌우/상하 배치가 함께 볼 정보를 확보하는가? 분할·중첩으로 폭이나 맥락을 잃는 손해는 없는가? | 현재 MES 셸 의미, S2의 제품 맥락 |
| 표현 방식의 적합성 | 표·상세 필드·배지·섹션 제목이 비교/설명/구분에 각각 필요한가? 표의 헤더·열 비용이나 과도한 박스/구역 분리가 내용보다 무겁지 않은가? | 현재 MES 컴포넌트 의미, S3의 정보 경쟁 감소 |
| 시각적 구별과 일관성 | 조회 정보와 입력 영역, 주요/보조 행동, 선택/미선택·정상/이상이 시안에서 구별되는가? 같은 의미의 표현이 일관되고 다른 의미의 표현은 혼동되지 않는가? | S1의 일관성, S3의 인지 단서 |
| 밀도·여백·가독성 | 정렬·간격·타이포·열 너비가 비교와 읽기를 돕는가? 핵심 정보의 잘림, 보조 영역의 과도한 강조, 데이터 대비 과한 빈 공간이 있는가? | S1의 위계, S2의 구성, S3의 숙련자 효율 |
| 화면 사이의 맥락과 원본 보존 | 제공된 목록·상세·확인에서 같은 대상이 식별되는가? 필요한 문맥을 다시 찾아야 하는가? 원본 필터·표·선택·액션 역할을 이유 없이 바꾸지 않았는가? | 사용자 원본/요구, S3의 일관성·기억 부담 |

S3는 [Nielsen 휴리스틱을 MES 질문으로 번역한 근거](../THIRD_PARTY_LICENSES.md#s3-nng)다. 이 관점은 고정 레이아웃/필드 개수 기준이 아니다. 시각적 상태의 구별은 제공된 시안에서 판단하며 상태 전이·키보드·저장 동작 검사를 추가하지 않는다. MES와 외형이 일관된다는 관찰을 자산 계약·가중치 준수 검증으로 확대하지 않는다.

4. 핵심 디자인 선택에 대해 어떤 정보/판단을 돕는지 설명한다. 배치에 의미 있는 절충이 있으면 현재 구성의 이점과 비용을 비교하고, 변경 판단에 필요한 경우에만 가까운 대안과 비교한다. 모든 요소에 대안을 만들거나 여러 시안을 새로 제작하지 않는다. “좌우라 좋다”가 아니라 “판단 근거와 입력 영역을 함께 볼 수 있어 좋다”처럼 구체화하고, 실제 자료가 뒷받침할 때만 그 이점을 주장한다.
5. 지적 후보를 업무상 영향과 근거의 확실성으로 비교한 뒤 핵심 항목을 선별한다. 대상 혼동·핵심 판단 정보 누락, 반복적인 읽기/비교 방해, 국소적 시각 조정 중 실제로 무엇이 중요한지 설명한다. 이 순서를 기계적 심각도표로 쓰지 않으며, 핵심 식별 정보를 가리는 열 잘림은 큰 영향일 수 있다. 사용 빈도나 위험은 자료 없이 단정하지 않는다.
6. 최우선 문제를 고른 **후에** 그 문제를 해결하는 최소 수정안을 제시한다. 단순히 열 너비 수정이 쉽다는 이유로 정보 관계/대상 맥락 문제보다 앞세우지 않는다. 반대로 근거 없는 구조 변경도 권하지 않는다. 영향이 비슷할 때만 수정 비용을 보조 기준으로 삼는다.

### 투입정보·부산물 팝업의 평가 질문

사용자가 이 사례의 평가를 다음 여섯 질문으로 한정했다면 그 범위를 지킨다. 일반 POC 전체에 이 목록을 고정 적용하지 않으며, 넓은 평가를 요청하면 위 관점을 사용한다.

1. 투입정보 팝업에 부산물을 함께 보여주는 것이 이해되는가?
2. 투입품과 부산물이 서로 다른 정보로 읽히는가?
3. 부산물 한 건을 표로 보여주는 방식이 적절한가?
4. 생산일자처럼 중복되거나 불필요한 정보가 있는가?
5. 원본 MES 화면의 필터·표·액션 구조를 훼손하지 않았는가?
6. 시각적 밀도와 남는 공간이 자연스러운가?

한 건이라는 이유만으로 표를 없애지 않는다. 동일 열 비교, 확정된 복수 건 요구, 정렬된 스캔이 필요하면 유지할 수 있다. 부산물 생산일자가 선택된 생산실적과 같은 의미라는 확인이 있을 때 중복 제거를 제안한다. 서로 다른 일자일 수 있는데 임의 삭제하지 않는다. 이전 결론을 최신 화면을 보지 않고 반복하지 않는다.

## 결과 형식

다음 형식을 사용한다. 잘된 점/애매한 점은 각각 최대 3개, 가장 먼저 수정할 것은 1개다. **출력의 상한이지 검토 범위의 상한이 아니다.** 전체 관련 관점을 본 뒤 중요한 결과를 압축하고, 동일 원인의 세부 조정은 묶는다. 필요한 경우 제목 아래 한 문장으로 실제 본 화면/관점과 자료 한계를 알린다. 보지 않은 영역까지 검토했다고 쓰지 않는다.

잘된 점에는 검토 후 유지할 디자인 선택과 업무상 이유를 적는다. 문제가 적으면 장점의 근거와 절충 설명으로 평가 깊이를 보여주며 지적을 억지로 늘리지 않는다. 수정할 문제가 없으면 “없음 — 현재 방향 유지”라고 쓴다.

```markdown
## POC 평가

### 잘된 점
- 구체적 디자인 선택 → 판단/읽기에 주는 이점 → 유지 이유 (최대 3개)

### 애매한 점
- 관찰한 부분 → 업무 영향/절충 → 개선 방향 또는 확인할 전제 (중요도순, 최대 3개)

### 가장 먼저 수정할 것
- 최우선 문제와 다른 후보보다 먼저 다룰 이유 → 그 문제의 최소 수정 (1개)

### 최종 의견
- 유지 / 소폭 수정 / 구조 재검토 — 핵심 이유
```

최종 의견은 셋 중 하나만 선택한다. `유지`는 디자인 방향 유지이지 구현 완료/승인이 아니다. 국소 변경이면 `소폭 수정`, 업무 대상·정보 관계·주요 흐름을 다시 정해야 하면 `구조 재검토`다. 자료가 부족해 의견 자체를 낼 수 없으면 억지로 선택하지 말고 필요한 자료만 요청한다.

구현 문제를 우연히 발견해도 상세 목록·심각도·증적을 본문이나 부록으로 붙이지 않는다. 필요한 경우 다음 **한 줄 안내만** 추가한다. 보관 요청이 없으면 별도 backlog 파일도 만들지 않는다.

```markdown
### 구현 단계에서 확인할 항목
현재 POC 평가 범위에서는 제외하며, 구현 감사 요청 시 별도로 확인한다.
```

특정 구현 검사도 명시적으로 요청받았다면 그것만 별도 `요청한 추가 검사`로 보고한다. 추가 검사 결과를 POC 최종 의견에 섞거나 무관한 구현 항목을 열거하지 않는다.
