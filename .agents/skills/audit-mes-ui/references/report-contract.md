# 구현/승격 보고 기준

`poc`에는 적용하지 않는다. POC는 [전용 결과 형식](poc-review.md#결과-형식)으로 끝낸다.

## implementation

```markdown
## MES 구현 감사

- 대상: route/file/Figma 노드 또는 흐름
- 범위: surface | connected-flow; 요청한 검사와 원본 비교 여부
- 결과: passed | needs-revision | limited | blocked

### 주요 지적
- [blocker/warning/info] 관찰과 위치 → 업무 영향/위반 계약 → 가장 작은 수정 → 재확인 방법

### 확인한 것
- 실제 실행한 자동 검사, 관찰한 상태 전이, 완료한 원본 비교만

### 미확인 / 범위 밖
- 미확인과 범위 밖을 구분하고 요청한 결론에 생기는 제한을 설명

### 다음 행동
- 가장 작은 후속 작업
```

빈 지적을 만들지 않는다. 문제가 없으면 선언 범위에서 발견하지 못했다고 쓰며 미확인 범위를 통과로 표현하지 않는다. 승격을 요청하지 않았으면 `Promotion recommendation` 등 승격 항목을 출력하지 않는다.

### 결과 의미

- `passed`: 선언한 검사 범위에 blocker/warning이 없고 결론을 뒷받침하는 확인을 했다.
- `needs-revision`: 확인된 수정 사항이 있다. 별도의 미확인 항목이 있다면 같이 밝힌다.
- `limited`: 일부 평가를 했지만 요청한 전체 결론을 낼 증거가 부족하다. 증거 부재를 UI 결함으로 단정하지 않는다.
- `blocked`: 대상에 접근할 수 없거나 핵심 경로가 막혀 요청한 검사를 진행할 수 없다. 가능한 부분 결과와 최소 해소 조건을 남긴다.

심각도는 결함 영향이고 결과는 검사 범위의 상태다. `passed`는 승인·배포·표준 편입·전체 완료가 아니다. 실제로 남은 중대한 구현 문제는 과거에 POC였다는 이유로 면제하지 않는다.

## promotion

구현 결과와 분리하여 [승격 기준](promotion-review.md)의 결론을 추가한다.

```markdown
## MES 승격 심사

- 대상 / 범위:
- 구현 감사 결과:
- Promotion recommendation: not-ready | review-ready | promotion-candidate

### 승격 판단 근거
- 현재 구현과 일치하는 검사·관찰·사용자 검토 기록, 실제 부족한 요건

### 다음 행동
- 보완하거나 사용자가 별도로 승인해야 하는 사항
```

숫자 점수는 요청할 때만 제공하며 기준·미확인 범위·blocker를 함께 보여준다. 평균으로 승인 여부를 대신하지 않는다.
