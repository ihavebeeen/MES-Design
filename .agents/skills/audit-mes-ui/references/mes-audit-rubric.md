# 구현 감사 기준

`implementation`과 `promotion`에서만 읽는다. `poc`는 [POC 평가](poc-review.md)를 따른다. 범주가 있다는 이유로 모두 검사하지 말고 요청 범위에 해당하는 것만 선택한다.

## 수행 순서

1. 대상·사용자 요구·현재 계약/구현을 읽고 평가할 경로를 정한다. 승인 계약과 최신 사용자 수정본의 충돌은 명시한다. 과거 코드/fixture로 최신 디자인을 되돌리지 않는다.
2. 업무 의미·정보 위계·화면 내 관계에 대한 판단을 먼저 기록한다. 정적 검사 경고가 검토 주제를 대신하지 않게 한다.
3. 계약과 구현이 있고 계약 검사가 범위에 포함되면 `mes-ui` MCP의 구현 감사 도구를 우선 사용한다. 연결되지 않았으면 `component-library/`에서 `npm run screen:audit -- <contract.json> <implementation.tsx>`를 실행한다. UX·렌더링·실제 저장까지 통과했다고 확대하지 않는다.
4. 기능 주장은 실제 상태 전이로, 시각 주장은 렌더로 확인한다. 제공된 캡처를 재사용할 수 있으며 비교 시 화면·viewport·상태를 맞춘다. 스크린샷은 지적을 설명할 때만 추가하고 실제로 본 것을 인용한다.
5. 해당 범주를 검사하고 [보고 기준](report-contract.md)으로 끝낸다. 실패를 통과시키려고 코드나 증적을 바꾸지 않는다.

계약이 없는 기존 화면도 사용성과 기능은 평가할 수 있다. 계약 부재는 계약 준수의 확인 한계이지 모든 UX의 실패가 아니다. 실행 자료가 없으면 동작을 추정해 통과시키지 않고 해당 항목만 미확인으로 남긴다.

## 1. 업무와 정보 구조

업무 대상, 비교 단위, 입력/저장 단위, 선택 결과, 행동 순서가 요구와 맞는지 확인한다. 전체/행 액션을 혼동시키거나 서로 다른 업무 정보를 같은 것으로 읽히게 만드는 구성은 구체적인 오조작/오해 경로로 설명한다.

셸·구역 순서·제목·표/상세정보의 역할은 현재 MES 계약과 대조한다. 필터·선택·액션을 줄인 것이 실제 효율을 개선하는지 확인하며 밀도가 높다는 사실만으로 문제라고 하지 않는다.

## 2. 컴포넌트와 조합 계약

등록 여부뿐 아니라 capability, `useWhen`/`doNotUseWhen`, 허용 부모, 선택 수, 상태, 인접 자산과의 업무 연결을 확인한다. 생성 계약이 있으면 `assetDecisions`, `componentRefs`, 섹션 순서와 실제 구현을 대조한다.

현재 승인 컴포넌트/variant를 우선한다. 원시 상호작용 요소, 로컬 CSS 대체, 미등록 wrapper 등은 **실제 위반 계약과 영향**을 확인해 지적한다. 컴포넌트명이 코드에 있다는 이유로 통과시키거나 자동 탐지만으로 위반을 확정하지 않는다.

## 3. 동작·상태·회복

요청된 조회·입력·선택·검증·저장·출력·취소·닫기·재열기를 확인한다. loading/empty/error/disabled/권한/재시도 등은 실제 업무에 필요한 것만 선택한다. 취소/X의 dismiss 경로와 미저장 값 복원은 해당 계약을 따른다.

`surface` 통과는 서버 저장 증명이 아니다. `connected-flow`이면 진입 트리거, 대상 전달, 저장 후 반영, 필요 시 필터·선택·스크롤 보존까지 확인한다. 원격 데이터 변경이 필요한 검사는 권한과 안전한 테스트 환경을 먼저 확인한다.

미구현으로 선언한 항목은 범위에서 제외하되 요청된 완료 주장과 충돌하면 범위 충돌로 밝힌다. **실제 동작을 요구한** 버튼의 no-op은 프로토타입이라는 이유로 면제하지 않는다.

## 4. 시각·원본 비교·반응형

선언한 viewport에서 위계·정렬·타이포·토큰·가독성·표 너비·잘림·의도하지 않은 overflow를 확인한다. 1280px 등 추가 viewport는 요청/계약/반응형 주장에 필요할 때만 확인한다.

원본 비교는 최신 사용자 수정본과 같은 의미·상태를 비교한다. fixture 값 차이와 정보 의미/레이아웃 차이를 분리한다. 정확한 콘텐츠 재현이 요청됐거나 값이 표시/행동을 바꾸는 경우에만 데이터 차이를 결함으로 평가한다. 근거가 있을 때만 `source-error`, `implementation-error`, `intentional-exception`, `normalization-candidate`로 분류한다.

## 5. 접근성

범위에 포함되면 대상 표준/수준을 확인한다. 지정이 없으면 **WCAG 2.2 AA를 참조한 위험 점검**이라고 밝히되 저장소 전체의 새 승인 기준으로 만들지 않는다. 필요할 때 [W3C 원문](https://www.w3.org/TR/WCAG22/)의 성공 기준을 확인한다.

- 의미/이름/상태: 레이블·heading·table/dialog semantics, 동적 피드백.
- 키보드: 접근, 순서, 초점 표시, 모달 trap/복귀, 계약에 따른 Escape.
- 시각: 텍스트/컨트롤 대비, 색상 외 상태 단서, 확대/리플로우, 타깃 크기.
- 오류/회복: 식별 가능한 입력 오류와 수정 방법, 값 보존.

관찰·측정한 문제와 못 한 보조기술 검사를 구분한다. 텍스트 크기별 대비 기준이나 타깃 크기 예외를 무시한 단일 숫자 판정은 하지 않는다. 스크린샷만 있으면 키보드·스크린리더 동작은 미확인이다. 부분 검사를 “WCAG 준수”로 보고하지 않는다. ([W3C 평가 한계](https://www.w3.org/WAI/test-evaluate/preliminary/))

## 지적 우선순위

- `blocker`: 요청 범위의 핵심 업무가 불가능하거나 다른 대상으로 실행되는 등 심각한 실패, 필수 계약의 중대한 위반.
- `warning`: 혼동·반복 작업·접근성/표시 문제가 업무에 영향을 주지만 진행 경로가 남아 있다.
- `info`: 선택적인 개선/절충. 취향을 blocker로 올리지 않는다.

영향, 해당 경로의 사용 빈도, 회복 가능성으로 우선순위를 정한다. 빈도 자료가 없으면 추정임을 밝힌다. 미확인 증거는 결함 심각도와 별개다. 모든 미확인을 blocker finding으로 만들지 않는다. 동일 원인은 묶고 가장 작은 수정과 재확인 방법을 제시한다.
