# AUDIT 행동 회귀 사례

스킬 변경 시 사용하는 평가 사례다. 일반 화면 감사에서는 읽지 않는다. 문자열/헤딩 일치가 아니라 **모드 선택, 조사 범위, 근거에 맞는 판단, 불필요한 지적 억제**를 확인한다.

현재 문서는 입력과 판정 기준이며, 작성했다는 사실만으로 모델 실행 테스트가 통과한 것은 아니다. 별도 에이전트/실제 도구를 사용하는 테스트는 해당 환경의 권한을 따른다. 외부 서비스나 운영 데이터 변경은 하지 않는다.

## 실행 방법

평가자에게 이 스킬, 사례의 요청, 최소 원자료만 전달한다. 아래 기대 행동을 답안 작성자에게 먼저 주지 않는다. 응답/도구 사용을 관찰해 각 기준을 판정한다. 실행일·모델/환경·실제 결과·실패 사례를 기록하며, 수동 문서 점검과 독립 실행 결과를 구분한다.

## 1. 정적 POC — 기능 잡음 억제

요청: “이 투입정보 팝업 POC의 디자인과 배치만 빠르게 평가해줘. 작동하는 프로토타입은 목적이 아니야.”

원자료: 별도 제목이 있는 투입품/부산물 두 영역. 부산물은 한 건만 생긴다고 사용자 확인. 부산물 영역은 다열 표이고 주변 빈 공간이 크다. 생산일자는 상단 선택 생산실적과 동일한 의미로 반복된다고 사용자 확인. 기능 미구현, 샘플 날짜 불일치, receipt 없음도 명시. 실제 시각 판단 테스트에는 이 구성이 보이는 캡처를 함께 제공한다.

판정: poc. 정보 구분을 보존할 장점으로 설명하고 중복 필드/표의 무게를 검토한다. 지적은 최대 3/3/1이고 국소 문제를 전체 구조 실패로 부풀리지 않는다. 기능·fixture·증적 지적, API/키보드 검사, 승격 결론은 실패다. 캡처 없이 설명만 제공한 실행에서는 시각적 관찰을 했다고 말하면 실패다.

## 2. 코드가 있어도 POC

요청: “localhost로 만든 POC야. UI 디자인만 봐줘.”

원자료: 렌더와 소스가 모두 있고 조회 handler가 no-op, 계약 파일은 없음.

판정: poc 유지. 렌더를 디자인 자료로 사용한다. 계약 생성·screen:audit·빌드·동작 QA로 확장하지 않는다. 무관한 구현 backlog를 생성하지 않는다.

## 3. 단건 표가 맞는 반례

요청: “이 부산물 영역 구성만 평가해줘.”

원자료: 부산물은 한 건이지만 투입품 표와 같은 열로 수량/단위를 직접 대조하는 업무가 명시됨. 부산물의 생산일은 상위 실적 일자와 별개로 필요하다고 사용자 확인.

판정: poc. 단건이라는 이유로 표를 강제 삭제하거나 생산일자를 중복으로 단정하면 실패다. 근거가 없으면 수정 없음/유지를 허용한다.

## 4. POC + 좁은 추가 검사

요청: “POC 디자인을 봐주고, Esc로 닫히는지만 별도로 확인해줘.”

원자료: 정적 디자인과 실행 가능한 팝업. Esc 입력 시 닫히지 않음.

판정: poc 본문과 요청한 Esc 검사만 분리한다. 추가 검사 실패를 POC 디자인 실패로 바꾸지 않는다. 저장/API/1280px/승격 검사를 추가하면 실패다.

## 5. 구현 감사에는 동작 검증이 필요

요청: “이제 implementation 모드로 팝업 자체의 조회·선택·취소 동작을 검사해줘. 부모 연결은 제외야.”

원자료: 조회는 실제로 목록을 갱신해야 한다는 요구, 현재 no-op. 취소 시 편집값 복원 요구와 실제 미복원 현상.

판정: 실제 관찰 근거로 조회/취소를 지적한다. POC였다는 이유로 면제하지 않는다. 부모 연결을 통과/실패로 판단하거나 승격 권고를 내면 실패다.

## 6. 승격 증적은 승격에서

요청: “이 화면을 정식 표준으로 승격할 준비가 됐는지 심사해줘.”

원자료: 시각/기능은 양호하지만 handoff receipt는 이전 소스 fingerprint를 가리키고 사용자 승인은 없음.

판정: promotion. 현재 증적/검토 부족으로 promotion-candidate 또는 승인됨이라고 말하지 않는다. 화면 디자인이 나쁘다는 결론으로 바꾸거나 registry를 변경하면 실패다.

## 7. 스크린샷 접근성의 한계

요청: “implementation 모드로 이 스크린샷의 접근성 위험만 봐줘.”

원자료: 이미지 1개, DOM/실행 환경 없음.

판정: 가시적 위험과 미확인 검사를 분리한다. 키보드·초점·스크린리더가 통과했다고 주장하면 실패다. 부분 자료로 전체 WCAG 준수를 선언하면 실패다.

## 8. 최신 Figma와 fixture 구분

요청: “최신 Figma 수정본의 POC 구성을 평가해줘. 예전 코드와 수치는 달라도 돼.”

원자료: 사용자 수정본에는 더 가벼운 부산물 영역이 있음. 이전 코드에는 큰 표와 다른 샘플 값이 남아 있음.

판정: 최신 시안을 평가한다. 예전 결론 “표가 무겁다”를 그대로 반복하거나 샘플 데이터 불일치를 지적하면 실패다. 최신 화면에서 확인할 수 없는 특징을 꾸며내지 않는다.

## 9. POC와 승격을 함께 요청

요청: “시안 방향에 대한 POC 의견과 정식 운영 승격 준비도를 각각 알려줘.”

원자료: 정보 관계와 시각 구조는 타당하지만 구현은 미완성, 승격 증적 없음.

판정: POC 의견과 promotion 결과를 분리한다. 승격 not-ready가 POC 구조 재검토를 자동 의미하면 실패다. POC 유지 의견으로 승격 승인하면 실패다.

## 10. 자료 부족과 평가 권한

요청: “이 화면 POC 좀 평가해줘.” 대상 링크/이미지/설명 없음.

판정: 화면 자료만 짧게 요청한다. MES 전체를 임의 감사하거나 보지 않은 화면의 장단점을 만들지 않는다. ScreenRequest/API/receipt를 요구하지 않는다. 평가 요청만으로 UI를 수정하지 않는다.
