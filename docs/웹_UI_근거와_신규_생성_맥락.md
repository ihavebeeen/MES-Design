# 웹 UI 근거와 신규 생성 맥락

이 문서는 업무 명세, 실제 개발 MES, Figma, 승인된 디자인 시스템을 새 화면 제작에 어떻게 사용하는지 설명한다. 웹 관찰 원본은 `web-ui-usage-inventory.json`, `web-figma-reconciliation.json`, `web-generation-context.json`이며, 업무별 정보 관계는 [business-knowledge.json](../component-library/src/design-system/registry/business-knowledge.json), 화면·섹션 사용 맥락은 [usage-contexts.json](../component-library/src/design-system/registry/usage-contexts.json)에 둔다. 둘 다 **참고 자료**이며 배치·필수값을 자동 확정하는 규칙이 아니다.

> **핵심 선택 규칙을 기본으로 적용하고, 생성 피드백을 통해 필요한 규칙만 추가 보강**

## 근거별 역할

| 근거 | 역할 | 자동으로 하지 않는 것 |
|---|---|---|
| 최신 Figma | 기존 화면의 콘텐츠·위계·상태·배치 기준 | 고립된 수치를 곧바로 공통 토큰으로 승격하지 않음 |
| 승인된 디자인 시스템 | 신규 UI의 컴포넌트·패턴·조합 기준 | 원본에 없는 업무 내용을 임의로 만들지 않음 |
| Notion 기능명세서 | 업무 목적, 정보 출처·관계, 수용가/모드별 조건, 저장 영향 | 옛 배치나 미정 정책을 신규 화면의 정답으로 강제하지 않음 |
| 실제 개발 MES | 사용 위치, 진입 경로, 연결 팝업과 운영상 추가된 상태 참고 | 단일 구현 오류를 표준으로 복사하지 않음 |
| 생성 피드백 | 실제 신규 UI에서 잘못 선택된 자산과 보강 필요성 | 모든 컴포넌트의 사용처를 전수 문서화하지 않음 |

기존 화면 재현과 원본 없는 신규 생성은 같은 입력을 사용하지 않는다.

- `reproduce`, `normalize`, `audit`: Figma와 실제 웹 참고 장부를 함께 대조한다.
- `new`: 승인된 핵심 선택 규칙과 반복된 조합 문법을 사용한다. 화면별 감사 이력과 미검증 수치는 생성 입력에서 제외한다.

## 업무 명세가 새 화면에 도움이 되는 부분

**명세는 무엇을 빠뜨리면 업무가 달라지는지 알려준다. 어디에 얼마나 크게 보여줄지는 새 화면의 목적을 보고 정한다.**

예를 들어 ‘과거 입고를 참고하면서 여러 거래처의 물건을 받는 화면’을 새로 만든다면, 거래처·품목·수량·창고의 관계와 저장 결과는 알아야 한다. 그렇다고 예전의 발주 선택 팝업, 슬라이드 배치, 모든 컬럼을 그대로 옮길 필요는 없다.

| 명세에서 확인한 차이 | 해당 조건을 적용하는 새 화면에서 검토할 의미 |
|---|---|
| 선행 발주/지시 연계와 LOT 관리는 독립 설정 | ‘발주 없음’을 곧바로 ‘간편 등록’으로 해석하지 않기 |
| 자동으로 채워져도 수정 가능한 값이 있음 | 정보 출처와 편집 가능 여부를 분리하기 |
| 간편 입고는 날짜 공통, 거래처·창고 등은 행별 | 공통 입력 하나로 모든 행의 값을 묶지 않기 |
| 하위 저장은 임시 반영일 수도, 즉시 저장일 수도 있음 | 새 배치에서도 저장·취소의 적용 범위 보존하기 |
| 부산물은 생산으로 생긴 결과이며 투입품과 역할이 다름 | 같은 컬럼이어도 정보 관계를 평평하게 합치지 않기 |

출처: [업무운영설정 Part1](https://www.notion.so/3b20e77b201580e69b34e5f9bc919fe4), [입고 간편등록 4장](https://www.notion.so/3b90e77b201580e4a04bc57cc02b4c46), [부산물 4장](https://www.notion.so/39e0e77b201581b0b50ae9e14d402233). 개별 사실의 출처와 절 번호는 JSON의 `sourceRefs`에 있다.

주요/보조 정보는 영구 분류가 아니다. LOT는 간편 입고의 직접 입력 항목은 아니지만 LOT 추적에서는 핵심이다. 부산물 발생량도 단순 생산등록과 ‘부산물이 예상보다 적은 원인 찾기’에서 중요도가 달라진다. 필수 정보라도 이미 결정된 값이면 새 입력창이 필요하지 않을 수 있다.

### AI가 필요한 업무만 읽는 방법

`component-library/`에서 다음 조회를 사용한다. 사용자가 매번 실행할 명령이 아니라 AI가 자료를 좁혀 읽는 진입점이다.

```bash
npm run business:context -- --list
npm run business:context -- --task receiving.register
npm run screen:references -- --query "입고등록" --surface side-slide-panel
npm run screen:references -- --task receiving.register --usage usage.entry-list
```

결과에는 업무 목적·정보 관계·조건·관련 업무·출처·미정 사항이 함께 나온다. `focusCandidates`와 `uiImplication`은 설계 해석으로 표시하며 고정 배치나 승인된 패턴으로 간주하지 않는다. 입고에는 필요성·출처·편집 여부·행/전체 소유 범위를 분리한 상세 예시도 있다.

1. 새 요청의 목적과 기존 명세에서 **계속 적용할 사실 / 달라진 사실 / 미정**을 구분한다.
2. 필요한 정보와 주요·보조 위계를 정한 뒤 MES 자산으로 배치 대안을 구성한다. 답 하나로 중앙/슬라이드나 Table을 고르지 않는다.
3. 채택한 근거 ID와 달라진 조건을 기존 `ScreenRequest.requirements`·`evidence.notes`에 남긴다. 별도의 장문 계획서는 늘리지 않는다.

업무가 달라진다는 이유로 기존 컴포넌트·폰트·간격 규칙까지 바꾸지는 않는다. 반대로 아직 없는 업무를 가장 가까운 옛 화면에 억지로 끼워 넣지도 않는다.

### 전체 페이지·팝업·섹션에 공통으로 적용

목록에서 찾기, 대상/상세 탐색, 분석·모니터링, 선택/반환, 편집, 확인, 커스텀 정보, 검사, 입력/목록, 그룹 권한, 제목 범위, 연결 결과의 맥락을 조회할 수 있다. 기존 사례에서 해석한 고려사항이지 모든 화면의 사용처를 전수 확정한 목록은 아니다.

- 좌측/상단이라고 주요 정보, 우측/하단이라고 보조 정보로 정하지 않는다. 검사에서는 우측 판정이 주 작업일 수 있다.
- 상단 공통값과 다음 한 행의 작성값은 다르다. 빈 행 추가·상단 값 추가·병행과 행 편집 가능 여부도 따로 검토한다.
- 주요/보조 분류, 필수성, 값의 출처, 수정 가능성, 소유 범위, 노출 시점은 현재 업무 조건으로 판단한다. 모든 참고 질문에 답할 필요는 없다.

**프로그램 연결:** 기존 `mes_get_web_generation_context`가 `referenceContext`를 함께 반환한다. `category: references`, 업무/사용 맥락 ID로 좁힐 수 있다. MCP가 없으면 위 CLI를 쓴다. Resolver도 요청 이름과 선택 자산에 맞는 참고 후보를 별도로 첨부한다. 이름 검색은 후보 탐색이지 업무를 확정한 판정이 아니다.

**강제하지 않는 것:** 참고 미선택·미등록·다른 배치는 생성 차단이 아니다. 참고 내용은 필수값·읽기전용·순서·Shell을 변경하지 않는다. 참고 주석만 바뀌어도 화면 검수를 다시 요구하지 않으며, 실제 채택한 조건은 기존 요청에 반영해야 구현·검증에 적용된다. 자료 조회 오류는 부재로 표시하고 임의 대체하지 않는다. 실제 MES 자산·구현 검사는 유지한다.

### 이번 조사 범위와 한계

- [동진 MES 명세](https://www.notion.so/3600e77b2015805fa3ffce780cdde0f5)의 직접 연결 문서들과 추가로 참조된 설비별 생산량 변경안을 업무 의미 중심으로 검토했다. 목록·검토일·원문 시점은 JSON에서 관리한다.
- 발주 사본은 본문이 동일함을 비교했고, 병합 전 문서·수정중 팝업 조사 등 읽지 않은 하위 자료는 `unreviewedLinkedPages`로 분리했다. 이미지·첨부·모든 외부 링크까지 검수한 결과는 아니다.
- 출하 완료 시점, 검사 보류, 기본창고 전환 등 명세 충돌/미정 사항은 `openQuestions`에 보존했다. 전부 해결할 때까지 모든 UI 제작을 막는 목록이 아니다. 해당 동작을 만드는 요청에서 필요한 부분만 확인한다.
- 실제 수용가의 현재 설정과 서버 반영 여부는 이 조사로 검증되지 않았다. 명세에 있다고 운영 중이라고 단정하지 않는다.
- 조회와 출처/참조 무결성 검사, MCP·Resolver의 참고 조회 연결을 구현했다. **자동 업무 확정이나 배치 판정기는 아니다.** AI가 현재 요구에 적용할 내용을 판단해 기존 요청에 반영한다. 무결성 검사 통과는 업무 사실이나 화면 품질 검증이 아니다.

다음 연결 작업은 새 요구 1건에 이 자료를 적용하여 질문·정보 위계가 실제로 나아지는지 확인한 뒤 진행한다. 미완성 입고 파일럿 초안을 이 조사와 함께 완료 처리하지 않는다.

## 실제 웹에서 확인한 범위

2026-08-24 관찰 배치에서는 42개 메뉴, 30개 오버레이 흐름, 3개 중첩 결과를 기록했다. 이 수치는 ‘표준 화면 42개’가 아니라 확인한 사용 위치의 범위다.

같은 배치의 Figma 연결 장부는 최신 원본 후보 38개, 후속 수정 후보 3개, 위치 미확인 1개였다. 당시 픽셀·동작 승인 건수는 0이었으므로 이 연결 수치를 검증 완료 수치로 사용하지 않는다.

관찰 항목은 다음에 한정한다.

- 페이지가 목록·분석·설비·추적 중 어떤 구조인지
- 어떤 액션에서 중앙 팝업 또는 우측 슬라이드가 열리는지
- 선택 팝업 뒤에 등록 슬라이드가 이어지는지
- 섹션이 폼·검색 테이블·마스터 상세·검사항목 중 무엇으로 반복되는지
- 실제 구현에만 존재하는 화면이나 연결이 있는지

업무 권한, API 정책, 내부 데이터 규칙은 이 실제 웹 관찰 인벤토리의 범위가 아니다. 위 Notion 업무 자료는 새 UI에 영향을 주는 조건만 별도로 다루며, 전체 내부 정책이나 API 명세를 재작성하지 않는다.

## 신규 생성에 사용하는 반복 문법

당시 관찰된 페이지 분류는 엔티티 목록 34, 분석 6, 설비 1, 추적 1이었다. 오버레이 흐름은 등록 슬라이드 23, 중앙 검색 4, 중앙 선택 후 슬라이드 2, 분석 중앙 팝업 1이었다. 이 숫자는 자동 생성 계약이 아니라 반복 구조를 찾은 관찰치다.

생성 순서는 다음과 같다.

```text
업무 목적과 플랫폼 결정
→ 적용할 업무 정보 관계·조건 및 새 요구 확인
→ 주요·보조 정보와 전체 컨셉 결정
→ 적용 가능한 페이지·오버레이 흐름 검토
→ Shell 선택
→ Section 순서와 Pattern 선택
→ 핵심 컴포넌트 선택 규칙 적용
→ 상태·취소·저장·스크롤 계약 연결
→ 생성 및 구조·동작·시각 검증
→ 실제 선택 문제가 있으면 필요한 규칙만 보강
```

### 반복되는 기본 형태

- 검색 조건과 고밀도 테이블이 있는 전체 목록 페이지
- 배경 맥락을 유지한 채 오른쪽에서 열리는 등록·상세 슬라이드
- 짧은 검색·선택을 위한 중앙 팝업
- 중앙에서 항목을 선택한 뒤 우측 등록 화면으로 이어지는 흐름
- Shell 안의 폼 그리드, 검색 테이블, 편집 행, 검사항목, 마스터–상세 섹션

한 화면에서만 발견된 연결이나 시각값은 공통 문법으로 올리지 않는다. 두 화면 이상에서 반복되거나, 사용자가 공통 규칙으로 확정하거나, 공식 Figma 공통 명세가 있을 때만 승격한다.

## Figma와 실제 웹이 다를 때

차이는 다음 네 종류로 기록한다.

- `source-error`: Figma 내부의 잘못된 이름·수치·상태
- `implementation-error`: 승인된 원본·규칙과 다른 실제 구현
- `intentional-exception`: 업무 또는 환경상 의도적으로 다른 구현
- `normalization-candidate`: 반복 기준으로 정리할 필요가 있는 고립값

판단 근거가 부족하면 어느 한쪽을 임의로 정답 처리하지 않는다. Figma 외곽 작업 프레임의 크기와 실제 브라우저 viewport도 구분한다. 화면 캡처가 축소된 상태라면 CSS 좌표와 기준 viewport를 함께 확인한다.

### 실제 대조 방법

처음에는 42개 메뉴와 Figma 원본 위치를 연결한다. 이후에는 수정되는 자산과 연결 화면을 중심으로 대조 범위를 갱신한다. 전체 42개 화면을 코드 변경 때마다 다시 확인하지 않는다.

Figma에서는 공통 디자인과 완료된 개선안을 확인한다. 실제 웹에서는 자산의 사용 위치, 주변 컴포넌트, 진입 순서, 선택·편집 뒤 상태 변화를 확인한다. 버튼을 점검할 때는 Figma에서 색상·크기·아이콘·간격을 보고, 웹에서 목록 하단·팝업 Footer 같은 실제 배치와 활성 조건을 본다.

대조 기록은 다음 순서로 쌓는다.

1. 비교할 Figma 실제 UI frame과 웹 화면을 연결한다.
2. 공통 셸, 조회·필터, 테이블, 하단 액션, 오버레이, 상태 변화를 확인한다.
3. 같은 UI의 디자인 차이는 Figma를 기준으로 분류한다.
4. 웹에만 있는 필드·열·데이터는 기존 디자인을 재사용한 내용 확장인지 확인한다.
5. 웹에만 있는 새 모달·패널·배치는 원본이나 승인 근거를 찾는다.
6. 확인한 수준을 원본 위치 확인, 구조 대조, 시각 차이 실측, 실제 상태 관찰로 구분한다.

대표 대조 결과와 남은 항목은 `web-figma-reconciliation.json`에서 관리한다. 현재 생산목표·입고·경향관리·생산분석의 구조를 대조했고, 기본창고 설정 모달의 시각 차이와 창고 행 선택 상태를 실측했다. 설비 모니터링은 고해상도 후보 6개가 있으나 최신 기준이 미확정이며, KPI는 좌측 메뉴 항목만 확인되어 본문 원본이 미확정이다.

## 현재 한계

- 관찰 배치는 실제 MES의 모든 권한·데이터·숨은 상태를 전수 확인한 결과가 아니다.
- Figma 연결 장부는 원본 후보 위치를 찾기 위한 자료이며 모든 화면의 픽셀·동작 승인을 뜻하지 않는다.
- 실제 웹에서 한 번 본 UI는 표준 컴포넌트나 공통 패턴의 충분한 근거가 아니다.
- 신규 UI의 품질은 문서 수가 아니라 첫 생성 결과의 선택·배치·동작 오류로 평가한다.

## 갱신 규칙

1. 실제 웹에서 새 흐름을 발견하면 먼저 관찰 인벤토리에 기록한다.
2. 단일 사례도 출처·한계를 표시해 참고할 수 있지만 공통 규칙으로 자동 승격하지 않는다.
3. 반복·사용자 확정·공식 공통 명세 중 하나가 생기면 공통 규칙 후보로 검토한다.
4. 신규 UI에서 실제 선택 문제가 발생하면 `generation-selection-feedback.json`에 기록한다.
5. 기존 규칙으로 설명되면 구현만 수정하고, 설명되지 않을 때만 관련 계약을 보강한다.
