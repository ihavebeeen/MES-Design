# AI 완료 판정 및 보고 정책

## 왜 이 정책이 필요한가

이 프로젝트에서는 에이전트가 “이번에 수정한 일부 코드가 동작한다”는 뜻으로 `완료`를 사용한 뒤, 사용자가 전체 범위를 물으면 미검수 화면과 후속 작업이 다시 발견되는 일이 반복됐다. 이는 진행 보고의 표현 문제가 아니라 범위와 검증 수준을 섞은 잘못된 완료 판정이다.

앞으로 `완료`는 기분이나 작업 종료 시점이 아니라 아래 상태 계약으로만 판정한다. 기계 판정 원본은 `component-library/src/design-system/registry/completion-policy.json`이다.

## 상태 용어

| 상태 | 사용할 수 있는 조건 | 사용할 수 없는 경우 |
| --- | --- | --- |
| 구현됨 | 코드와 진입 경로가 존재함 | 원본 일치·동작·회귀 검사를 통과했다고 뜻하지 않음 |
| 검증됨 | 선언한 단일 화면/기능이 원본 대조, 브라우저 실측, 상호작용, 시각 회귀 검사를 모두 통과함 | 같은 계열의 다른 화면까지 자동으로 검증된 것으로 확대 금지 |
| 배치 완료 | 작업 전에 명시한 배치 목록의 모든 항목이 검증됨 | 배치 밖의 저장소 전체가 완료됐다고 표현 금지 |
| 전체 완료 | 저장소의 미검수·진행 중·미승인·보류·명시적 TODO가 0개임 | 하나라도 남아 있으면 사용 금지 |

## 작업 시작 규칙

작업을 시작할 때 에이전트는 이번 범위를 항목 목록으로 고정한다. 작업 도중 새 문제가 발견되면 다음 중 하나로 처리한다.

1. 현재 범위에 포함하고 목록을 갱신한다.
2. 범위 밖 남은 작업으로 기록한다.
3. 현재 결과에 영향을 주는 차단 문제라면 검증됨 또는 배치 완료 판정을 보류한다.

## 최종 보고 형식

최종 보고에는 항상 아래 네 가지가 있어야 한다.

1. `이번 범위 상태`: 구현됨 / 검증됨 / 배치 완료 중 하나
2. `검증 근거`: 실행한 원본 대조, 실측, 테스트, 빌드
3. `남은 작업`: 없으면 “이번 범위 내 없음”, 있으면 구체적인 항목
4. `전체 프로젝트 상태`: 진행 중 / 전체 완료

“완료했습니다”처럼 범위 없는 문장은 금지한다. 예를 들어 `출하승인 배치 2개 화면은 검증됨. 전체 프로젝트는 진행 중이며 미검수 원본 4건이 남음.`처럼 쓴다.

## 자동 검사

`npm run check:design-system`의 레지스트리 검사는 다음 상태를 집계한다.

- `source-evidence.json`의 `queued`, `in-progress`
- 승인되지 않은 생성 화면 후보
- 종결되지 않은 Section/Behavior 제안
- composition ledger의 `migration-hold`, `needs-review`
- `footer-action-audit.json`의 `queued`, `implemented-unverified`

이 중 하나라도 남아 있는데 `completion-policy.json`의 `projectState`를 `complete`로 바꾸면 검사가 실패한다. 자동 검사는 대화 문장을 직접 막지는 못하지만, 저장소가 전체 완료인지에 대한 단일 근거를 제공한다.
