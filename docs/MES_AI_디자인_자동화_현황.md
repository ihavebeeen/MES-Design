# MES AI 디자인 자동화 현황

> 기준일: 2026-08-26 · 전체 프로젝트 상태: 진행 중

## 목표

AI에게 “입고 등록 화면을 만들어줘”라고 요청했을 때, 기존 MES의 디자인과 업무 조합 방식을 따라 일관된 화면을 만들게 하는 프로젝트다. 신규 화면 생성뿐 아니라 기존 Figma와 실제 구현의 불일치도 구분할 수 있는 구조를 만든다.

## 왜 컴포넌트 모음만으로 부족했나

초기에는 Figma 화면을 코드화하고 Button, Input, Table, Popup 같은 공용 부품을 만들었다. 하지만 공용 부품을 사용해도 다음 문제가 반복됐다.

- 중앙 팝업과 우측 슬라이드를 잘못 선택함
- MES에 없던 안내 박스와 문구를 임의로 추가함
- 링크를 Badge로 표현하거나 입력 영역을 Table로 만듦
- 섹션 순서, 스크롤과 하단 액션을 임의로 구성함
- 체크·입력·취소 복원이 시각만 있고 실제로 동작하지 않음

따라서 디자인 시스템의 범위를 토큰과 컴포넌트에서 선택 맥락, Shell, Section, Behavior와 검증 절차까지 확장했다.

## 현재 구성

```text
업무 목적과 플랫폼
→ 핵심 선택 규칙
→ Shell
→ Section Frame / Section Pattern
→ Behavior / ActionSet
→ Component
→ Token
```

자산 수와 최신 검사 결과는 README의 자동 요약, `asset-manifest.json`, `full-verification-result.json`을 기준으로 한다. 이 보고서에 수치를 복사해 고정하지 않는다.

현재 제공하는 기반은 다음과 같다.

- 공용 토큰·컴포넌트와 컴포넌트별 API·상태 문서
- 중앙 팝업, 우측 슬라이드와 전체 페이지 Shell
- 폼 그리드, 검색 테이블, 편집 행, 검사항목, 마스터–상세 Section
- 선택, 행 변경, 취소 복원과 ActionSet 계약
- AI 조회용 컴포넌트·패턴·화면 레지스트리
- 생성 화면의 로컬 임시·Git 검토·승인·보관 분리
- 구조·상호작용·시각 회귀·레지스트리 자동 검사
- 다른 PC와 AI 도구에서 사용할 수 있는 저장소 지침과 MCP 인터페이스

## 현재 운영 원칙

> **핵심 선택 규칙을 기본으로 적용하고, 생성 피드백을 통해 필요한 규칙만 추가 보강**

- 모든 컴포넌트의 실제 사용처를 같은 깊이로 문서화하지 않는다.
- Badge와 Link, 중앙 팝업과 우측 슬라이드처럼 신규 UI 선택을 바꾸는 규칙을 우선 관리한다.
- 단순 컴포넌트는 코드 API, 상태와 접근성 문서만 유지한다.
- 실제 MES 웹은 연결과 반복 맥락을 이해하는 참고 자료이며 표준 원본이 아니다.
- 한 화면의 예외는 공통 규칙으로 자동 승격하지 않는다.
- 실제 생성에서 잘못 선택된 자산이 확인되면 기존 규칙으로 설명되는지 먼저 보고, 필요한 계약만 보강한다.

## 현재 검증 수준

현재 코드 전체가 모든 Figma 화면과 완벽히 동일하다고 말할 수는 없다.

| 상태 | 의미 |
|---|---|
| 구현됨 | 코드와 진입 경로가 존재함 |
| 검증됨 | 선언한 범위에서 원본 대조·브라우저 실측·상호작용·시각 검사를 통과함 |
| 생성 시안 | 검토용 결과이며 표준 생성 근거가 아님 |
| provisional | 정식 원장에는 있으나 실제 업무·원본 검증을 더 거쳐야 함 |

시각 회귀는 코드가 이후 달라졌는지 찾는 장치다. 기준 이미지가 실제 Figma 원본과 연결됐을 때만 원본 일치 근거가 된다.

## Figma와 실제 MES가 다를 때

```text
Figma: 설계 의도와 화면 구조
실제 MES: 운영 중인 기능과 연결 흐름
디자인 시스템: 반복 검증된 표준과 승인된 예외
```

차이는 `source-error`, `implementation-error`, `intentional-exception`, `normalization-candidate`, `insufficient-evidence`로 나눈다. 13px 글자나 9px 간격을 발견했다고 자동 반올림하지 않고 동일 역할의 반복값과 업무상 이유를 확인한다.

## 현재 한계

- 모든 MES 원본 화면을 같은 깊이로 전수 검증한 상태는 아니다.
- 실제 MES 웹의 모든 권한·데이터·숨은 상태를 수집하지 않았다.
- 생성 결과가 일정 수준을 넘었다고 판단할 장기 품질 지표와 팀 승인 절차가 더 필요하다.
- provisional 자산은 후보 판정이 끝났어도 실제 업무 사용과 원본 검증을 통해 안정화해야 한다.
- 모바일은 디자인 변경 가능성 때문에 현재 보류 상태다.

## 다음 순서

1. 신규 웹 UI 생성에서 핵심 선택·배치·동작 규칙이 실제로 올바른지 반복 시험한다.
2. 생성 피드백에서 확인된 필요한 규칙만 보강한다.
3. 의미·토큰·조합 위반을 코드 단계에서 잡는 MES 전용 lint를 확대한다.
4. 대표 컴포넌트 문서에 실제 variant와 상호작용 예시를 연결한다.
5. 이후 MCP 확장, 토큰 생성 파이프라인, 배포 변경 관리를 별도 배치로 진행한다.

성과는 컴포넌트 개수보다 첫 시안 시간, 사람의 수정 횟수, 기존 자산 재사용률, 임의 UI 발생 수, 동작 오류와 승인까지 걸린 시간으로 평가한다.

## 기대 효과와 현재 판단

- 신규 화면 초안과 개발자 전달 시간 단축
- 화면별 간격·글꼴·상태 표현의 통일
- 기존 MES에 누적된 구현 오류와 Figma 이상값의 구분
- 개인 기억에 의존하던 UI 판단 근거의 회사 자산화

현재 단계는 모든 MES 화면을 자동 완성하는 시스템이 아니다. 반면 단순 UI 샘플 모음도 아니다. 승인된 자산과 조합 규칙, 생성 경로와 자동 검사까지 연결됐으며, 다음 성과는 실제 신규 요구에서 수정 횟수와 승인 시간을 줄이는지로 판단해야 한다.
