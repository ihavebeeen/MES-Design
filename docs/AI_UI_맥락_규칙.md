# AI UI 맥락 규칙

> 정책 ID: `mes.ai-context-rules`
> 버전: `1.3.0`
> 상태: 공통 정책 확정
> 구조화 원본: `component-library/src/design-system/registry/context-rules.json`

## 1. 왜 별도 맥락 규칙이 필요한가

같은 토큰과 컴포넌트를 사용해도 배치된 부모, 설명하는 대상, 업무의 길이와 상태가 다르면 올바른 디자인 시스템 사용이 아니다. `SectionHeader`가 안정화된 컴포넌트라는 사실은 모달 섹션에서 사용할 수 있다는 뜻이지, 페이지의 모든 제목을 회색 밴드로 만들라는 뜻이 아니다.

AI는 구현 요소를 선택하기 전에 다음을 먼저 판정한다.

1. 이 요소가 무엇을 설명하거나 제어하는가?
2. 어느 부모 안에 놓이는가?
3. 필수인가, 필요할 때만 쓰는 선택 요소인가?
4. 주변 요소와 어떤 포함·상하 관계를 가지는가?
5. 같은 부모와 역할에서 사용된 검증 원본이 있는가?

따라서 선택 순서는 `시각 유사성 → 팝업 유형 → 편한 컴포넌트`가 아니다. `필요한 정보·행동 → 개별 컴포넌트 맥락 대조 → 컴포넌트 연결 관계 → 이를 지원하는 패턴과 셸 → 검증 근거와 구현 참조` 순서다.

### 1.1 화면을 만들기 전의 질문 체계

질문 원본은 [screen-intake-policy.json](../component-library/src/design-system/registry/screen-intake-policy.json)에 둔다. 기존 생성 스킬이 구성 선택 전에 이 파일을 읽는다. 새 MD 설문이나 별도의 계획서를 만들지 않는다.

질문은 특정 답을 특정 레이아웃으로 바꾸는 분기표가 아니다. **화면 전체의 성격을 파악한 다음, 구성에 영향을 주는 빈칸만 확인하는 체계**다.

| 단계 | 확인하는 내용 | 질문을 사용하는 방식 |
|---|---|---|
| 화면 전체 | 주된 작업과 완료 결과, 진입·종료, 주인공과 보조 정보, 지정된 컨셉·참고물의 적용 범위 | 목적과 컨셉이 불명확하면 세부 컨트롤보다 먼저 확인 |
| 정보 구조 | 대등·종속·관련 결과 관계, 사용 환경, 데이터 규모 | 배치·묶음·위계를 바꾸는 불확실성만 확인 |
| 작업별 세부 | 찾기, 상세 탐색, 선택, 값의 소유 범위, 입력 의존성, 항목 변경, 비교, 모니터링, 설정 | 한 화면에 여러 성격이 공존할 수 있으며 해당하는 질문만 사용 |
| 동작·상태 | 확정·취소, 고정/필수/비활성, 빈 상태·실패 후 행동, 문구·값의 의미 | 기존 계약으로 답이 정해진 사항은 묻지 않음 |

각 질문에는 ID, 질문 문장, 필요한 조건, 답에 포함될 정보, 먼저 확인할 자료, 영향을 받는 구성, 기존 요청에 반영할 필드, 미정일 때의 처리가 있다. 사용자에게 이 목록 전체를 작성시키지 않는다.

**질문 순서**

1. 요청·대화·첨부 명세·적용 가능한 계약에서 답을 먼저 찾는다. 사용자 확정, 근거 있음, 가정, 미정, 충돌, 해당 없음을 구분한다.
2. 화면의 주된 목적·컨셉·정보 관계가 불분명하면 먼저 묻는다. 업무 의미나 중요한 동작이 달라지는 미정 사항은 그 부분 구현 전에 확인한다.
3. 한 번에 관련 질문 1~3개만 한다. 이미 답한 항목을 다시 묻거나 폰트·padding·컴포넌트 ID를 사용자에게 고르게 하지 않는다.
4. 컨셉이 미정이면 AI가 전체 맥락과 MES 근거로 제안한다. 둘 이상의 구성이 실질적으로 다를 때만 차이를 짧게 비교한다. 업무 사실을 지어내어 템플릿에 끼워 넣지 않는다.
5. 답이 충분하면 바로 구성으로 넘어간다. 이후 변경에서는 영향을 받는 답과 구성만 다시 확인한다.

**예시**

- `입고등록`: 여러 품목이라는 사실은 배열 방식의 답이 아니다. 목적·기존 형태를 확인한 뒤, 거래처와 창고의 소유 범위나 추가 시 계승값이 불명확할 때만 묻는다.
- `투입정보 + 부산물`: 컬럼이 같아도 업무 역할은 다를 수 있다. 투입품과 부산물이 대등한지, 관련 결과인지 확인한 뒤 위계를 설계한다. 하위 정보라는 이유만으로 중첩 박스를 만들지 않는다.
- `표시 항목 설정`: 표시·합계·순서 기능이 정해졌다면 반복해서 묻지 않는다. 고정 항목이나 합계 가능 대상이 미정일 때만 확인한다. Boolean 값이라는 이유로 토글을 고르지 않는다.
- `기존 팝업의 간격 수정`: 목적·입력·취소를 다시 설문하지 않는다. 현재 계약을 유지하고 해당 배치만 수정한다.

**답변 보존과 구현**

확정 조건은 기존 `ScreenRequest.requirements`에, 중요한 답과 근거·가정은 `evidence.notes`에 질문 ID 및 대상 범위와 함께 기록한다. 모든 질문의 빈 레코드를 만들지 않는다. 실제 배치는 `target`, `webContext`, `composition`, 동작 설정은 `generation` 등 기존 필드에 반영한다.

Resolver는 이 조건과 메모를 보존하지만 문장의 의미를 판정하거나 자동으로 동작을 구현하지 않는다. 생성 AI는 답과 구조·동작 설정이 일치하는지 확인하고, 렌더링 후에는 초점·위계·읽기 순서·밀도·정렬·여백도 검토해야 한다. 질문 기록만 존재한다는 이유로 생성 품질이 검증됐다고 말하지 않는다.

### 1.2 업무 정보와 화면 위계

업무 정보의 주요/보조 여부는 컴포넌트를 고르기 전에 해당 화면의 목적에 맞춰 판단한다. 기존 업무의 관계·조건을 확인할 때는 [Notion 업무 자료 조회 방법](./웹_UI_근거와_신규_생성_맥락.md)을 사용한다. 자동 입력과 읽기전용, 필수값과 항상 노출할 입력창을 동일하게 취급하지 않는다. 이 자료는 기존 질문의 답을 찾는 참고이며, 명세의 옛 배치를 강제하거나 생성기의 계약을 대신하지 않는다.

이 원칙은 슬라이드뿐 아니라 전체 페이지·중앙/확인 팝업·각 섹션에도 적용한다. `usage-contexts.json`의 목적·영역 관계·고려사항과 업무별 주요/보조 후보는 참고용이다. 미등록 업무나 다른 배치도 기존 MES 자산으로 구성할 수 있다. Resolver의 `referenceContext`는 후보 조회 결과이며 현재 요청을 변경하거나 사례 일치를 강제하지 않는다. 연결 방식과 한계는 위 조회 문서에서 관리한다.

`component-usage-contracts.json`은 모든 컴포넌트의 기본 선택 맥락과 선택에 민감한 자산의 상세 계약을 제공하고, `patterns.json`은 모든 패턴의 조합 맥락을 제공한다. `usage-contexts.json#assetSelectionGuide`는 여러 자산이 함께 쓰이는 대표 관계와 판단 기록 순서를 보충한다. `componentRefs`와 `connection`으로 같은 대상·비교 단위·저장 단위·작업 순서 안에서 자산이 연결되는 이유를 확인한 뒤 `patternRefs`를 비교하며, 패턴을 먼저 정한 뒤 Component를 끼워 맞추지 않는다.

### 1.3 전체 페이지와 팝업 배경

일반 MES 웹은 목록·상세·대시보드 모두 좌측 메뉴와 상단 탭을 유지한다. 공통 필수 자산은 `context-rules.json.applicationFrame`에서 관리한다. 팝업은 이 메뉴를 내부에 복제하지 않고 배경 페이지 위에 열린다.

검증 범위는 요청한 작업에 맞춘다. `verificationScope: surface`는 팝업 자체의 디자인·입력·취소·재열기 등을 확인한다. 메인 목록을 몰라도 진행할 수 있으며, 연결된 배경이 없으면 기존 MES 메뉴·탭과 단독 확인 안내만 보여준다. 모르는 업무 목록을 임의로 만들지 않는다. 저장 후 목록 반영이나 목록 선택값 전달을 요청하면 `connected-flow`로 해당 연결까지 확인한다.

`hostPage`는 배경 업무 페이지·열기 버튼·저장 전달 여부이며 연동 검증에만 필수다. 범위를 생략하면 hostPage가 있을 때 연동, 없으면 단독 확인으로 정한다. 이미 배경이 연결된 팝업 자체 수정은 surface를 명시해 그 배경을 유지할 수 있다. 실제 렌더링할 배경의 코드 오류는 무시하지 않는다. 모든 범위에서 MES 자산 검사는 유지하며, 검증 결과에 범위와 연동 제외 여부를 자동 기록한다. 코드·범위 변경 후 과거 통과를 재사용할 수 없다. 단독 확인 통과를 연동 완료로 표현하거나, 연동 요청을 실패 회피 목적으로 임의 축소하지 않는다. 실제 서버 저장은 별도이며 자동 증명되지 않는다.

### 1.4 디자인 시스템 가중치 설계

**상태: 설계 및 스킬의 요청 해석에 반영. 수치별 생성·검사 연결은 후속 작업.** 현재 실행기는 기존 MES 검사 조건을 유지한다. 아래 JSON은 다음 구현을 위한 설계 예시이며 현재 ScreenRequest 입력 필드에 추가하지 않는다.

목적은 화면 전체의 업무 목적·위계를 먼저 정하고, 필요한 영역에서만 MES 디자인의 자유도를 조절하는 것이다. 기본값은 `1`이며, 지정하지 않은 영역은 기존 기준을 따른다. 사용자에게 매번 숫자를 묻지 않는다.

| 구분 | 조절 대상 | 1일 때 |
|---|---|---|
| `foundations` | 색상, 글꼴, 크기, 간격, 테두리, radius | MES 토큰과 허용된 값 사용 |
| `components` | 버튼·입력·선택 등 실제 컨트롤과 variant | 승인 자산과 지원 API 사용 |
| `composition` | 섹션 구분, 정보 묶음, 배치·조합 | 승인 패턴과 지원되는 조합 사용 |

`1`에서도 기존 섹션들을 허용된 방식으로 조합해 새 화면을 만든다. 한 원본 화면을 통째로 복사할 필요는 없다. 슬라이드나 중앙 팝업 유형을 변경하려면 요청한 화면 목적과 변경 범위에 맞는 별도 판단이 필요하다.

**값의 의미**

- `1`: 해당 영역·구분은 승인된 MES 자산과 허용된 조합으로 구성한다. 부족한 기능은 알리고 재사용·확장안을 제안한다.
- `0 < 값 < 1`: MES를 출발점으로 대안을 검토한다. 값이 클수록 기존 형태를 우선하고, 작을수록 새 표현을 폭넓게 탐색한다. `0.8`을 자산 80% 재사용, 오차 20% 허용, 자동 통과 점수로 환산하지 않는다.
- `0`: 해당 범위의 디자인을 자유롭게 탐색한다. 업무 요구·정보 관계·동작은 계속 지키고 결과는 탐색 시안으로 관리한다.

값은 AI의 선택 방향을 나타낸다. 검사 프로그램은 “0.6만큼 창의적인가”를 판정하는 대신, 확정된 영역과 허용 종류를 확인한다. 재현 요청의 원본 보존 범위는 계속 유효하며, 이를 바꾸는 자유도 요청과 충돌하면 적용 범위를 먼저 확인한다.

**적용 범위와 우선순위**

1. 화면 기본값 → 화면 전체의 구분별 지정 → 특정 영역의 구분별 지정 순서로 적용한다. 생략한 구분은 상속한다.
2. 영역은 `screen`, `application-frame`, 실제 `composition.sections[].id`에 대응하는 `section:<id>`로 식별한다. 메뉴명이나 CSS 선택자로 범위를 추정하지 않는다. 하위 요소는 자신이 속한 영역 값을 상속한다.
3. 좌측 메뉴·상단 탭과 이를 제공하는 공통 틀은 `application-frame`으로 분리해 기본 1을 유지한다. 화면 기본값이 낮아져도 이 틀은 보존한다. 사용자가 공통 틀 변경을 명시하면 그 범위도 별도로 설계한다. 팝업 내부에 메뉴를 복제하지 않는다.
4. 같은 영역·구분을 중복 지정하거나 대상 ID가 없으면 확정 전에 해결한다. NaN, 문자열 수치, 0 미만·1 초과는 입력 오류로 처리한다. 구현 변경으로 섹션이 사라지면 범위도 다시 확인한다.
5. AI는 도구 오류·표현의 어려움·검사 실패를 이유로 값을 낮추거나 허용 범위를 넓힐 수 없다. 최신 사용자 합의로 바뀐 부분만 갱신한다.

**신규 자산 허용은 별도 설정**

기본은 `propose-only`다. 정확한 자산 → 의미·동작이 호환되는 기존 자산 → 신규 제안 순서로 찾는다. 사용자가 지정 영역의 신규 제작을 허용하면 그 영역에만 `allow-draft`와 허용 종류(`token`, `component`, `pattern`)를 지정한다. 공용 variant의 새 형태도 해당 종류의 신규 제작으로 다룬다.

가중치가 낮으면 호환 후보와 새로운 표현을 현재 목적에 맞춰 비교할 수 있다. 낮은 값만으로 신규 제작 권한이 생기지는 않는다. 반대로 신규 제작 권한만으로 가중치 1을 해제하지 않는다. 컴포넌트 값 1인데 새 컴포넌트가 꼭 필요하면 해당 값의 변경을 합의하거나, 별도 자산 승인·등록을 거친 뒤 재사용한다. 토큰 값 1을 유지하면서 컴포넌트만 새로 만들 수 있다.

신규 시안은 허용된 로컬 출력 범위에서 구현한다. 공용 컴포넌트 수정, 정식 자산 승격, Git 보관은 각 작업의 승인 범위를 따른다. 자유롭게 만들더라도 단일선택을 다중선택으로 바꾸거나, 취소 시 임시 값을 저장하는 식으로 업무·동작 의미를 바꾸지 않는다.

**설계 예시 — 기본 스타일과 공통 틀은 유지, 부산물 영역만 확장**

```json
{
  "version": 1,
  "defaultWeight": 1,
  "overrides": [
    {
      "scope": "section:byproducts",
      "weights": { "components": 0.6, "composition": 0.6 }
    }
  ],
  "newAssets": [
    {
      "scope": "section:byproducts",
      "mode": "allow-draft",
      "kinds": ["component", "pattern"],
      "reason": "기존 후보와 비교한 뒤 부산물 정보 표현에 필요한 시안 제작 허용"
    }
  ]
}
```

`byproducts`는 실제 구현할 섹션 ID와 맞춰야 한다. 이 예시에서 색상·폰트·간격과 나머지 영역은 1이다. 부산물의 컴포넌트·배치만 탐색 범위가 생긴다. 신규 자산 사용 이유와 사용자 합의는 기존 요구사항·메모에 짧게 남긴다. 영역마다 별도 보고서를 만들지 않는다.

**생성·검사 연결 순서 — 남은 작업**

1. ScreenRequest 스키마에 이 설정을 추가하고, Resolver가 상속을 풀어 영역별 유효 값·허용 종류·사용자 합의 근거를 확정한다. 미지정은 기존 엄격 모드와 동일한 결과를 유지한다. 메모를 권한으로 자동 해석하지 않는다.
2. 생성기와 수동 구현 미리보기 모두 같은 설정을 소비하도록 연결한다. 기본 MES 경로와 신규 후보의 로컬 경로를 구분하고, 실제 코드가 어떤 영역·자산을 쓰는지 감사한다. 영역 밖 교체나 공용 스타일 변경은 허용하지 않는다.
3. CLI·MCP의 감사와 전달 검사에서 코드·의존 파일·설정·승인 범위를 함께 fingerprint에 넣는다. 코드 또는 적용 값이 바뀌면 해당 검사와 필요한 렌더링 확인을 다시 수행한다. 미지원 모드는 설명하고 중단하며, 다른 서버나 원시 HTML 출력으로 우회하지 않는다.
4. 출력에는 `strict / extended / exploratory`와 실제 검증 결과를 따로 표기한다. 모두 1이며 승인 자산만 사용한 범위는 strict, 0 없이 자유도를 넓힌 범위는 extended, 0이 포함된 범위는 exploratory다. 혼합 화면은 영역별 상태와 가장 넓은 자유도를 전체에 표시한다. 기능·오류·넘침 확인, 해당 범위의 스타일·접근성·상호작용 확인은 모두 유지한다. 시안의 검증 통과와 정식 MES 자산 승격은 따로 관리한다.
5. 기본값 유지, 범위 상속, 공통 틀 보호, 0·1 경계와 잘못된 값, 중복/없는 ID, 신규 제작 권한 충돌, 영역 밖 원시 컨트롤·CSS 대체 차단, 코드/설정 변경 후 재검사, CLI/MCP/수동 미리보기의 동일 판정을 회귀 테스트한다. 가중치 의미 전체나 디자인 품질까지 자동 증명한다고 주장하지 않는다.

지금은 요청 값을 기존 `requirements`·`evidence.notes`에 기록하고 적용 가능한 MES 구성으로 해석한다. 요구한 자유도가 현재 지원 범위를 벗어나면 그 차이를 설명하고, MES로 가능한 대안 또는 실행 기능 추가를 합의한다. 기존 검사 조건을 완화한 결과를 지금 제공할 수 있다고 안내하지 않는다. 업무·사용 맥락 자료는 모든 가중치에서 계속 참고 자료다.

## 2. 제목 맥락

| 역할 | 설명 범위 | 사용 조건 | 기본 수량 | 구현 |
|---|---|---|---|---|
| Overlay root heading | 중앙 모달·우측 슬라이드·확인 팝업 전체 | 모든 오버레이 | 정확히 1개 | 각 Shell의 Header 슬롯 |
| Section heading | 본문의 독립적인 논리 묶음 하나 | 서로 다른 섹션이 둘 이상이거나 경계가 필요한 경우 | 0개 이상 | `SectionHeader` + `frame.standard-section` |
| Content region heading | 단일 테이블·리스트·작업영역 | 콘텐츠의 이름만 필요하고 별도 섹션 경계는 불필요한 경우 | 0개 또는 1개 | `ContentRegionHeading` |
| Page section heading | 페이지 안의 설정·관리 영역 하나 | 반복 원본과 전용 계약이 확인된 경우 | 현재 보류 | 자동 선택 금지 |

### 2.1 Modal header

- 모달 전체의 목적과 대상을 설명한다.
- 제목과 닫기 버튼을 포함하는 Shell 책임이다.
- 모든 모달에 반드시 하나만 존재한다.
- 본문의 Section heading이 Modal header를 대체할 수 없다.

### 2.2 Section header

- 모달 전체가 아니라 해당 섹션 내부의 내용을 설명한다.
- 여러 섹션이 모여 하나의 모달 본문을 만들 때 경계를 표현한다.
- 선택 요소이므로 “섹션처럼 보이게 하고 싶다”는 이유만으로 추가하지 않는다.
- 본문이 단일 테이블이나 단일 작업뿐이면 생략하는 것이 기본이다.

### 2.3 Content region title

`생산실적 리스트`나 `품목 재고 리스트`처럼 한 테이블·리스트의 이름만 필요한 경우다. 이때 제목은 Section heading보다 시각 위계가 낮아서가 아니라 설명 대상이 하나의 콘텐츠 영역이기 때문에 선택된다. `ContentRegionHeading`은 16px Bold 일반 텍스트만 소유하며, 모달용 회색 `SectionHeader` 밴드와 제목 행의 높이·padding을 상속하지 않는다.

출하실적 일괄등록 Figma node `19932:67376`에서 모달 루트 제목, 일반 텍스트형 `품목 재고 리스트`, 회색 작업 도구 영역이 서로 다른 역할로 확인된다. 생성기는 “팝업 안에 있다”는 이유만으로 이 세 역할을 하나의 회색 헤더로 합치지 않는다.

### 2.4 Page section heading 보류

페이지형 설정·관리 화면의 반복 원본과 정식 계약은 아직 충분하지 않다. 그 근거가 확보되기 전에는 다음 임시 규칙을 적용한다.

- 모달용 `SectionHeader`를 페이지에 자동 재사용하지 않는다.
- 필요한 경우 일반 제목·얇은 구분선·간격만 가진 최소 로컬 후보를 만든다.
- 후보는 생성 시안으로 격리하고 사용자 승인 전에는 표준 근거로 사용하지 않는다.

업무운영설정 시안의 긴 회색 섹션 헤더가 바로 이 사례다. 사용 토큰과 컴포넌트가 그럴듯했어도 페이지 맥락의 근거가 없었으므로 표준 사용으로 인정하지 않는다.

## 3. 오버레이 맥락

오버레이 셸도 하나의 Component 후보이므로 내부 표현보다 무조건 먼저 확정하지 않는다. 예를 들어 증감 확인에서는 기존값·변경값·차이가 여러 항목에 걸쳐 같은 열로 비교되면 `BeforeAfterComparison`, 결론 하나만 강조하면 `SectionFrame`의 요약 영역을 비교한다. 선택한 자산 조합이 짧은 결정이면 `ConfirmDialog`, 추가 입력·다수 비교·독립 스크롤이 필요하면 `CenterModal` 후보와 연결한다.

| Shell | 참고할 수 있는 MES 조합 | 선택 전 확인 |
|---|---|---|
| CenterModal | 중앙에서 수행하는 선택·조회·비교·편집 조합 | 현재의 전체 컨셉과 적용 가능한 중앙 팝업 계약이 맞는가? |
| SideSlidePanel | 우측 작업 영역에 기본정보·목록·검사항목 등을 조합 | 현재의 전체 컨셉과 적용 가능한 슬라이드 계약이 맞는가? |
| ConfirmDialog | 짧은 메시지와 확인·취소로 끝나는 결정 | 확인창의 범위를 벗어나는 조회·입력·스크롤이 없는가? |

위 표는 사용 장면이며 필요충분조건이 아니다. **배경 화면을 보아야 하는지, 몇 건인지, 입력이 긴지, 표가 넓은지 하나로 중앙/우측을 고르지 않는다.** 사용자 지정, 원본 유지 범위, 화면 목적, 정보 위계, 진입·종료와 적용 가능한 MES 조합을 함께 검토한다. 중앙 배치라는 외형만으로 `CenterModal`과 `ConfirmDialog`를 같은 유형으로 보지도 않는다.

## 4. 액션 맥락

| 역할 | 구현 | 선택 기준 |
|---|---|---|
| 명령 실행 | `Button` | 저장·확인·삭제·조회처럼 현재 작업이나 데이터를 바꿈 |
| 이동·상세 탐색 | `Link` | 다른 화면·팝업·관련 대상으로 이동함 |
| 상태 표시 | `Badge` | 클릭 없이 완료·승인중 같은 상태를 읽기 전용으로 표시함 |
| 아이콘 보조 명령 | `IconButton` | 닫기·삭제·펼치기처럼 의미가 관습적이고 공간이 좁음 |
| 오버레이 종료 액션 | `ActionSet` | 취소·저장·확인·선택의 commit/dismiss 의미 조합 |

버튼, 링크와 배지는 색이나 테두리 모양이 아니라 클릭 결과로 구분한다. 클릭해서 상세로 이동하는 값은 `Badge`가 아니고, 저장·삭제하는 동작은 `Link`가 아니다. 한 영역에는 가장 중요한 primary 명령을 하나만 둔다.

## 5. 입력 방식 맥락

| 질문 | 선택 |
|---|---|
| 미리 정해지지 않은 문자열·수량·설명인가? | `Input` / `NumberInput` / `Textarea` |
| 짧은 알려진 목록에서 하나를 고르는가? | `Select` |
| 많은 거래처·품목·설비에서 검색 후 하나를 고르는가? | `Combobox` |
| 소수의 배타적 옵션을 동시에 비교하는가? | `Radio` |
| 복수 선택·동의·행 선택인가? | `Checkbox` |
| 지속되는 기능 설정의 켜짐·꺼짐인가? | `Switch` |
| 현재 목록을 검색어로 좁히는가? | `SearchInput` |
| 카테고리별 조회 조건을 조합하는가? | `Filter` |
| 날짜·시간·기간 값인가? | 전용 Date/Time 컴포넌트 |

`SearchInput`과 `Combobox`는 둘 다 검색 UI를 포함할 수 있지만 결과가 다르다. 전자는 현재 데이터셋을 좁히는 조회 상태이고, 후자는 검색한 후보 중 선택된 도메인 값이 필드에 저장된다. `Filter`도 검색창으로 대체하지 않는다.

## 6. 콘텐츠 경계 맥락

- 복수의 독립적인 논리 묶음에는 `SectionFrame`을 사용한다.
- 본문이 단일 목록·폼·반복 입력 작업이면 Shell 안에 승인된 Section Pattern을 직접 배치한다.
- 단일 영역을 보기 좋게 만들기 위한 임의 회색 박스·radius·background는 추가하지 않는다.
- 테이블 컬럼과 정렬되는 합계는 `summary.table-total-row`를 사용한다.
- 표와 독립적인 업무 결과만 `summary.result-total-card`로 강조한다.

`SectionFrame`과 결과 요약 카드는 범용 컨테이너가 아니다. “무언가를 담을 박스가 필요하다”는 이유만으로 선택할 수 없고, 각각 논리 섹션과 독립 결과라는 의미가 있어야 한다.

## 7. 테이블 맥락

Table은 같은 컬럼 구조를 공유하는 반복 레코드를 행 단위로 조회·비교할 때만 사용한다.

| 모델 | 조건 | 연결 패턴 |
|---|---|---|
| 읽기 목록 | 반복 레코드를 컬럼 기준으로 조회 | `table.readonly-record-list` |
| 다중 선택 | 여러 행을 선택해 일괄 액션 | `selection.enable-actions` |
| 선택 행 편집 | 선택된 행에서만 입력 컨트롤 노출 | `selection.reveal-inline-editor` |
| Master–detail | 활성 행 하나가 다른 영역을 제어 | `selection.master-detail` |
| 그룹 계층 | 실제 그룹 상태와 접기·합계가 존재 | `table.grouped-list` |
| 반복 입력 | 소수의 행을 직접 추가·삭제 | Table 금지, `section.editable-row-list` |

마지막 구분이 이지모드 입고등록에서 발생했던 오류를 막는다. 품목·수량을 입력한다는 이유만으로 Table을 사용하지 않는다. 컬럼 비교보다 행 추가와 입력 흐름이 중요하면 반복 입력 패턴이다.

## 8. 스크롤 맥락

- 연속적인 긴 폼은 Shell Body가 세로 스크롤을 소유한다.
- 조회 툴바·Footer를 고정하고 목록만 움직여야 하면 콘텐츠가 스크롤을 소유한다.
- 짧은 확인 팝업은 스크롤을 두지 않는다.
- 같은 축에서 Shell과 내부 콘텐츠가 동시에 스크롤하면 안 된다.
- 가로 스크롤은 기본적으로 금지한다. 필수 컬럼을 줄일 수 없고 원본에서도 넓은 데이터 탐색이 확인된 경우에만 Table 내부 예외로 허용한다.

가로 스크롤을 허용하기 전에 `clientWidth`, `scrollWidth`, padding, 고정 폭과 중첩 wrapper를 확인한다. 레이아웃 오류를 스크롤로 숨겨서는 안 된다.

## 9. AI 선택 게이트

새 화면 생성 시 다음 판정을 JSX 작성 전에 실행한다.

### `select.overlay-shell`

1. 사용자 지정 또는 확정 원본에서 유지해야 하는 형태는 무엇인가?
2. 화면 목적·주인공·정보 관계·진입/종료가 어떤 전체 컨셉을 이루는가?
3. 같은 전체 맥락에 적용할 수 있는 승인 Recipe는 무엇이며 그 이유는 무엇인가?
4. 동시 참조·정보량·가용 공간 요구를 후보 안에서 함께 충족할 수 있는가?
5. 중요한 미정 사실은 질문하고, 배치 대안은 근거로 비교했는가? 답 하나로 Shell을 고르지는 않았는가?

### `select.heading-context`

1. 전체 오버레이, 논리 섹션, 단일 콘텐츠 중 무엇의 제목인가?
2. 부모가 페이지, 중앙 모달, 우측 슬라이드 중 무엇인가?
3. 필수 제목인가, 구분이 필요할 때만 쓰는가?
4. 상위 제목이 같은 범위를 이미 설명하는가?
5. 선택할 구현의 원본 사용 위치가 현재 부모와 일치하는가?

추가 판정:

- `select.action-role`: 명령·이동·상태·아이콘·Footer ActionSet 구분
- `select.input-control`: 값의 범위, 선택 수, 검색 목적과 commit 시점 구분
- `select.content-boundary`: SectionFrame·무경계 영역·표 합계·결과 요약 구분
- `select.table-model`: 읽기·다중 선택·인라인 편집·master-detail·그룹·반복 입력 구분
- `select.scroll-owner`: Shell·내부 콘텐츠·없음 중 세로 소유자와 가로 예외 판정

일치하는 활성 규칙이 없으면 임의의 안정화 컴포넌트를 가져오지 않는다. 장식이 가장 적은 로컬 후보를 만들고 `propose-new`와 생성 시안 격리를 적용한다.

## 10. 신규 컴포넌트 판정

이번 맥락 감사 결과는 다음과 같다.

| 후보 | 판정 | 이유 |
|---|---|---|
| 테이블 링크 셀 | 신규 불필요 | Table render 슬롯 안에서 `Link` 합성 |
| 반복 입력 행 | 신규 불필요 | `section.editable-row-list` + `row.mutation-policy` 사용 |
| 별도 스크롤 컨테이너 | 신규 불필요 | Shell `scrollMode`와 콘텐츠 소유권으로 설명 가능 |
| Content region title | 신규 불필요 | 해당 Section Pattern의 제목 슬롯으로 표현 가능 |
| Page section header | 보류 | 페이지 반복 원본과 전용 계약이 부족함 |

즉, 이번 배치에서 새 UI 컴포넌트는 만들지 않는다. 기존 역할로 설명되지 않는 반복 사례가 확인될 때만 신규 후보를 등록한다.

## 11. 코드 사용

```ts
import {
  getContextDecision,
  getGenerationContext,
  getImplementationContext,
} from "@/design-system/registry";

const generationContext = getGenerationContext();
const shellDecision = getContextDecision("select.overlay-shell");
const headingDecision = getContextDecision("select.heading-context");
const actionDecision = getContextDecision("select.action-role");
const inputDecision = getContextDecision("select.input-control");
const tableDecision = getContextDecision("select.table-model");
const implementation = getImplementationContext("material-input-settings");
```

화면 ID가 아직 없는 신규 생성은 `getGenerationContext`로 전체 선택 계약과 보류 항목을 읽는다. 가까운 기존 화면을 찾은 뒤에는 `getImplementationContext`로 화면·패턴·컴포넌트와 해당 구현에 연결된 맥락 규칙을 함께 조회한다. AI는 이 값을 읽은 후에만 JSX 조합을 시작한다.
