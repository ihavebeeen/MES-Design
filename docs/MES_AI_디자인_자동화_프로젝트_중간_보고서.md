# MES AI 디자인 자동화 프로젝트 중간 보고서

> 작성 기준일: 2026-08-19  
> 보고 목적: 현재까지의 추진 내용, 검증 수준, 한계와 다음 단계 공유

## 1. 한눈에 보는 결론

이 프로젝트는 Figma 화면을 단순히 React 코드로 옮기는 작업이 아니다. 사람이 만든 여러 Figma 화면과 실제 MES 구현을 비교해 공통 규칙을 찾고, 그 규칙을 AI가 조회할 수 있는 형태로 구조화하여 다음 세 가지를 가능하게 만드는 것이 목적이다.

1. 신규 MES 화면을 기존 디자인 체계에 맞게 빠르게 생성한다.
2. 기존 MES 화면에서 디자인·구현 오류와 화면 간 불일치를 발견한다.
3. 화면 제작과 검수 과정에서 얻은 판단 근거를 개인의 기억이 아닌 회사 자산으로 축적한다.

현재는 자동 UI 생성을 시험할 수 있는 기반 구조를 마련한 단계다. 다만 **현재 코드 전체가 Figma와 완벽히 동일하다고 말할 수는 없다.** 원본 대조와 브라우저 검증을 모두 통과한 화면, 과거에 구현했지만 아직 같은 수준으로 재검증하지 않은 화면, 의도적으로 표준 영향에서 격리한 AI 시안이 함께 존재하기 때문이다.

## 2. 프로젝트를 시작한 이유

MES의 Figma 파일에는 오랜 기간 동안 최초안, 수정안, 일부 영역만 변경한 안, 선택 전후 상태, 반응형 화면이 함께 누적되어 있다. 이 상태에서 화면을 하나씩 그대로 복제하면 다음 문제가 반복된다.

- 같은 기능의 버튼·입력·팝업이 화면마다 조금씩 다르게 만들어진다.
- 13px 글자, 9px 간격처럼 공통 규칙으로 설명하기 어려운 값이 누적된다.
- Figma의 실수인지, 실제 MES 구현의 실수인지, 업무상 필요한 예외인지 구분하기 어렵다.
- AI가 기존 자산을 찾지 못하고 그럴듯한 UI를 새로 만들어 디자인 일관성을 훼손한다.
- 화면을 만든 사람만 판단 이유를 알고 있어 이후 수정과 개발자 전달 비용이 커진다.

따라서 이번 작업에서는 화면을 복사하는 대신, 화면을 구성하는 토큰·컴포넌트·섹션·행동·팝업 구조를 단계별로 분해하고 다시 조합할 수 있도록 정리했다.

## 3. 현재까지 구축한 내용

### 3.1 디자인 자산의 계층화

현재 구조는 다음 순서로 연결된다.

```text
화면 목적과 맥락
→ 화면 셸(일반 페이지 / 중앙 팝업 / 우측 슬라이드 팝업)
→ 섹션 패턴(폼 / 검색·테이블 / 편집 행 / 검사항목 등)
→ 행동 패턴(선택 / 입력 활성화 / 취소 복원 / 행 추가 등)
→ 컴포넌트(Button / Input / Table / Select 등)
→ 디자인 토큰(색상 / 글꼴 / 간격 / 테두리 등)
```

이 구조를 통해 “같은 컴포넌트를 사용했다”와 “MES에서 맞는 방식으로 조합했다”를 구분할 수 있게 했다. 과거에는 등록된 Button과 Table을 사용했더라도 MES에 없던 카드형 배치를 임의로 만들 수 있었지만, 이제는 화면 셸과 섹션 패턴의 근거까지 함께 기록한다.

### 3.2 AI가 조회할 수 있는 레지스트리

AI와 개발 코드가 기존 자산을 먼저 찾도록 JSON·TypeScript 레지스트리를 구성했다. 현재 등록 현황은 다음과 같다.

| 구분 | 현재 수량 | 의미 |
| --- | ---: | --- |
| UI 컴포넌트 | 88개 | 안정화 40개, provisional 48개 |
| 조합 패턴 | 50개 | 셸·섹션·행동·액션 조합 포함 |
| 화면 Recipe | 17개 | 실제 MES 화면과 패턴의 연결 |
| 시각 회귀 사례 | 31개 | 대표 화면·팝업·테이블 변화 감지 |
| 원본 근거 묶음 | 11개 | 10개 검증, 1개 미검증 종결 |
| 확정 디자인 판단 | 29개 | 반복 오류를 방지하기 위한 결정 기록 |
| 격리된 실험 후보 | 0개 | Tier 3~5 판정 완료, 20개 정식 승격·37개 제외 |

### 3.3 원본 화면 검증 절차

화면이 코드로 존재한다는 이유만으로 “Figma와 동일하다”고 판정하지 않는다. 원본이 있는 화면은 다음 여섯 단계를 모두 통과해야 검증 상태가 된다.

1. 대상 Figma 노드와 필요한 하위 노드를 조회한다.
2. 화면 외곽부터 헤더·본문·섹션·표·셀까지 좌표와 크기를 기록한다.
3. 기존 컴포넌트와 신규 확장 필요 여부를 매핑한다.
4. 실제 브라우저 DOM의 크기와 가로·세로 스크롤을 측정한다.
5. 선택·입력·추가·삭제·취소 복원 등 상태 변화를 직접 조작한다.
6. 기준 화면의 PNG를 확인하고 이후 변경을 시각 회귀 테스트로 감시한다.

이 절차를 통과한 원본 근거는 현재 10개다. 반면 이지모드 입고등록 시안은 일부 장점이 있었지만 MES에 없던 설명 문구와 임의 배치가 포함되어 검증 원본이나 후속 생성 근거로 사용하지 않도록 종결했다.

## 4. 현재 코드가 Figma와 완벽히 동일한가

### 결론

**전체적으로는 아니다.** 다만 모든 화면의 상태가 같은 것은 아니다.

| 상태 | 의미 |
| --- | --- |
| 검증됨 | 지정된 원본 화면에 대해 좌표·구조·상호작용·브라우저 실측·시각 회귀를 통과함 |
| 구현됨 | 코드와 확인 경로는 있으나 같은 수준의 원본 대조를 모두 통과했다고 보장하지 않음 |
| 생성 시안 | AI 자동 생성 실험 결과이며 표준 디자인 근거로 사용하지 않음 |
| 실험 후보 | 향후 필요 가능성을 확인하기 위한 격리 자산이며 운영 화면에 자동 사용하지 않음 |

또한 시각 회귀 테스트는 “현재 코드가 이후에 달라졌는지”를 찾는 장치다. 기준 이미지가 Figma 원본에 올바르게 연결되어 있을 때만 원본 일치의 근거가 된다. 과거에는 코드에서 생성한 이미지를 원본 검증 이미지처럼 취급한 사례가 있었고, 이를 발견한 뒤 실제 Figma 하위 노드 좌표를 다시 확인하도록 절차를 강화했다.

따라서 현재의 정확한 표현은 다음과 같다.

> 일부 대표 원본 화면은 검증 절차를 통과했으며, 나머지 구현 화면 전체에 동일한 수준의 완전 일치를 확대 적용해서는 안 된다.

## 5. Figma와 실제 MES가 서로 다를 때의 판단 방법

Figma만을 절대 기준으로 삼는 것도, 현재 운영 중인 MES 코드만을 정답으로 삼는 것도 위험하다. 앞으로는 세 가지 근거를 함께 비교해야 한다.

```text
Figma: 설계 의도와 화면 구조
실제 MES: 운영 중인 기능과 실제 사용자 행동
정규화 규칙: 여러 화면에서 반복되는 회사의 공통 UI 기준
```

차이는 다음 네 가지로 분류한다.

1. **구현 오류**: Figma와 승인된 규칙은 일치하지만 실제 MES 코드만 다른 경우
2. **Figma 예외 또는 실수**: 대부분 12px 간격을 쓰는데 근거 없이 특정 화면만 9px인 경우
3. **업무상 필요한 예외**: 정보 밀도, 장비 환경, 데이터 구조 때문에 다른 값이 필요한 경우
4. **판단 근거 부족**: 최신안·구현 의도·업무 요구를 확인해야 하는 경우

13px 글자나 9px 간격을 발견했다고 자동으로 12px 또는 8px로 바꾸지는 않는다. 반복 빈도, 같은 역할의 다른 화면, 업무상 이유, 실제 사용 환경을 확인한 뒤 “원본 유지”, “표준으로 정규화”, “의도된 예외 등록”, “추가 확인” 중 하나로 결정해야 한다.

## 6. 기존 MES 오류도 자동으로 찾을 수 있는가

이 프로젝트의 장기 목표에는 포함되어야 하며, 기술적으로도 가능하다. 신규 UI 생성만 자동화하고 기존 화면의 불일치를 방치하면 디자인 시스템이 실제 제품 품질로 연결되지 않기 때문이다.

다만 현재 저장소에는 실제 운영 MES 프론트엔드 전체 코드와 화면 경로가 연결되어 있지 않다. 따라서 지금 단계에서 가능한 것은 재구현한 기준 화면과 등록된 사례의 오류를 찾는 것이며, 운영 MES 전체를 자동 검사하는 기능은 아직 완성되지 않았다.

운영 MES 검사에는 다음 연결이 추가로 필요하다.

1. 실제 MES 프론트엔드 저장소 또는 검사 가능한 빌드 연결
2. 운영 화면과 디자인 시스템 화면 Recipe의 매핑
3. 동일한 데이터·권한·화면 크기에서 캡처할 수 있는 테스트 환경
4. DOM의 폰트·간격·색상·컴포넌트 사용 여부 수집
5. Figma·정규화 규칙·실제 구현의 차이를 분류하는 리포트

이 구조가 완성되면 “Figma와 다르다”만 출력하는 것이 아니라, “실제 MES 구현 오류”, “Figma의 비정상 값”, “승인된 예외”, “사람의 판단 필요”로 구분해 담당자가 바로 조치할 수 있게 된다.

## 7. 시행착오와 개선된 점

프로젝트 초반에는 다음 문제가 반복됐다.

- Figma 화면을 충분히 실측하지 않고 비슷한 UI를 추정해 구현했다.
- 디자인 시스템을 컴포넌트 목록으로만 보고, 컴포넌트가 결합되는 맥락과 패턴을 놓쳤다.
- 화면 단위 패턴만 만들어 팝업 내부의 섹션과 행동을 재사용하기 어려웠다.
- 업무 화면의 이름을 독립 컴포넌트 이름으로 잘못 등록했다.
- 코드가 존재하는 상태와 원본 검증이 끝난 상태를 모두 “완료”라고 표현했다.
- AI가 만든 시안이 다음 자동 생성에 영향을 주어 잘못된 판단이 반복될 가능성이 있었다.

이에 따라 다음과 같이 개선했다.

- 화면을 셸·섹션·행동·컴포넌트로 분해했다.
- Figma 상위 프레임뿐 아니라 실제 화면과 하위 상태 노드를 확인하도록 했다.
- 브라우저 크기·스크롤·상호작용을 수치로 검증했다.
- AI 생성 시안과 실험 후보는 표준 레지스트리에서 격리했다.
- “구현됨”, “검증됨”, “배치 완료”, “전체 완료”를 구분했다.
- 107개 실험 후보를 재검토하여 기존 조합으로 설명 가능한 48개와 범위 밖 2개를 먼저 제거했다. 이후 Tier 3~5 사용자 판정을 반영해 제외하지 않은 20개를 정식 provisional 컴포넌트·패턴으로 승격하고 37개를 제외했다. 현재 격리 후보는 0개다.

## 8. 현재 한계와 위험

- Figma에 존재하는 모든 MES 화면을 전수 검증한 상태가 아니다.
- 검증 화면 10개에서 얻은 규칙을 모든 메뉴와 업무 상황에 그대로 적용할 수는 없다.
- 실제 운영 MES 코드와 자동 비교하는 연결이 아직 없다.
- 88개 컴포넌트 중 48개는 정식 레지스트리에 속하지만 안정화 전 provisional 상태다.
- Tier 3~5 Experimental 유지 후보는 0개다. 승격 자산의 실제 업무·원본 검증은 후보 판정이 아니라 provisional→stable 안정화 작업으로 관리해야 한다.
- API·권한·실데이터가 연결되지 않은 화면은 실제 운영 흐름 전체를 보장하지 않는다.
- 자동 생성 결과의 품질을 평가할 장기 지표와 승인 운영 체계가 아직 확정되지 않았다.

## 9. 다음 추진 단계

### 1단계. 세 기준 비교 구조 확정

Figma, 정규화된 디자인 시스템, 실제 MES 구현을 하나의 화면 ID로 연결한다. 차이는 구현 오류·정규화 제안·승인된 예외·판단 대기로 기록한다.

### 2단계. 운영 MES 대표 화면 진단

사용 빈도와 오류 영향이 큰 대표 화면을 선정하여 실제 코드와 DOM을 수집하고, 현재 디자인 시스템 규칙으로 진단 리포트를 만든다.

### 3단계. 단계별 자동 검수

단건 문제 하나로 화면 생성 전체를 실패시키지 않는다.

- 안내: 더 적합한 기존 컴포넌트·패턴 추천
- 경고: 하드코딩 값, 원시 요소, 근거가 약한 로컬 조합
- 수정 필요: 잘못된 상태 처리, 접근성·상호작용 오류
- 승격 차단: 빌드 불가, 핵심 기능 고장, 미승인 실험 자산의 운영 코드 유입

AI는 먼저 자동 수정을 시도하고, 해결하지 못한 항목만 사람에게 보고한다. 문제 있는 화면도 폐기하지 않고 “검토 필요” 상태로 보존하며, 심각한 문제가 남아 있을 때만 표준 승격과 배포를 보류한다.

### 4단계. 블라인드 신규 UI 생성 시험

기존 화면을 직접 복사하지 않은 신규 요구사항으로 UI를 생성하고 다음 지표를 기록한다.

- 첫 시안 생성 시간
- 사람의 수정 횟수와 수정 시간
- 기존 컴포넌트·패턴 재사용률
- 임의 UI와 하드코딩 값 발생 건수
- Figma 또는 승인 기준과의 시각 차이
- 상호작용·스크롤·상태 오류 건수

### 5단계. 팀 운영 체계화

새 디자인과 화면이 추가될 때 같은 검증 절차를 반복하고, 승인된 판단만 AI 조회 자산으로 승격한다. 디자인 변경과 개발 변경이 발생하면 시각 회귀와 실제 MES 진단을 함께 실행하도록 개발 프로세스에 연결한다.

## 10. 기대 효과

- 신규 화면의 초안 제작과 개발자 전달 시간 단축
- 화면마다 다르게 적용되던 간격·글꼴·상태 표현의 통일
- 기존 MES에 누적된 UI 구현 오류의 체계적 발견
- 디자이너의 실수와 개발 구현 오류를 구분할 수 있는 판단 근거 확보
- 특정 담당자의 경험에 의존하지 않는 회사 차원의 UI 지식 자산 축적
- AI가 임의로 화면을 만드는 것이 아니라 회사의 승인된 규칙 안에서 생성·수정하도록 통제

## 11. 경영진 관점의 현재 판단

현재 단계는 “AI가 모든 MES 화면을 자동으로 완성하는 시스템”이 완성된 상태는 아니다. 반면 단순한 UI 샘플 모음도 아니다. 실제 화면을 구조적으로 분해하고, 재사용 가능한 규칙과 검증 절차를 코드로 축적했으며, 잘못된 시안이 다음 결과에 영향을 주지 않도록 격리하는 기반까지 마련했다.

다음 성과 판단의 기준은 컴포넌트 개수가 아니라 다음 두 가지가 되어야 한다.

1. 신규 요구사항을 기존보다 얼마나 빠르고 정확하게 화면으로 만들 수 있는가
2. 기존 MES에서 사람이 놓친 UI 불일치와 구현 오류를 얼마나 자동으로 찾아낼 수 있는가

향후 대표 운영 화면 진단과 블라인드 생성 실험을 통해 시간 절감률, 수정 횟수, 규칙 재사용률, 오류 탐지 건수를 수치화하면 회사 차원의 투자 효과를 설명할 수 있다.
