# MES AI UI 자동화 진행 현황과 향후 계획

> 기준일: 2026-08-24
>
> 대상: 프로젝트 참여자, 의사결정자, 새로 저장소를 사용하는 AI·개발자
>
> 전체 상태: `in-progress`
>
> 모바일 상태: `deferred` — 디자인 변경 가능성이 정리될 때까지 추후 진행

## 1. 한 문장으로 설명하면

이 프로젝트는 MES 화면을 React로 많이 옮겨놓는 작업이 아니다. 기존 Figma와 구현 화면에서 MES의 디자인 언어와 업무 UI 문법을 추출하고, AI가 그 문법을 사용해 새 화면을 생성하며, 잘못된 기존 화면까지 찾아낼 수 있도록 만드는 작업이다.

현재는 웹 자산을 상당 부분 모았고, 핵심 컴포넌트와 패턴의 사용 맥락을 기계가 읽는 계약으로 만들었으며, 대표 구조 3종은 같은 요청에서 같은 코드 구조가 나오도록 결정형 생성 경로까지 구성했다. 다만 모든 화면이 동일한 깊이로 구조화됐거나 모든 원본 화면의 픽셀 검증이 끝난 상태는 아니다.

## 2. 왜 이 작업을 시작했는가

기존 MES에는 이미 많은 화면과 컴포넌트가 있다. 그런데 사람이 오랜 기간 Figma와 실제 웹을 수정하면서 다음 문제가 함께 쌓였다.

- 같은 의미의 버튼·입력·테이블인데 화면마다 크기나 간격이 조금씩 달랐다.
- Figma가 잘못된 경우와 실제 구현 코드가 잘못된 경우가 섞여 있었다.
- 특정 화면의 3px, 9px, 13px 같은 값이 의도된 예외인지 단순 제작 오차인지 알기 어려웠다.
- 컴포넌트가 존재해도 어떤 맥락에서 무엇을 사용해야 하는지가 명시되지 않았다.
- AI가 Figma를 보고 그럴듯한 화면을 만들 수는 있었지만, 기존 MES 패턴과 다른 카드·헤더·안내 문구를 임의로 추가했다.
- 같은 요청을 다른 AI나 다른 컴퓨터에서 실행했을 때 결과가 달라질 수 있었다.

따라서 목표를 “원본 화면 코드화”에서 끝내지 않고 다음까지 확장했다.

1. 원본을 증거로 보존한다.
2. 반복 규칙과 이상값을 구분한다.
3. 토큰·컴포넌트·패턴의 표준을 정한다.
4. 컴포넌트를 언제, 어디에, 왜 사용하는지 구조화한다.
5. AI가 승인된 조합 안에서 화면을 생성하게 한다.
6. 생성 화면과 기존 화면을 같은 규칙으로 검사한다.

## 3. 진행하면서 발견한 핵심 시행착오

### 3.1 “등록된 컴포넌트를 사용했다”는 것만으로 부족했다

초기에는 Button, Input, Table 같은 공용 자산을 사용하면 디자인 시스템을 따른 것으로 생각했다. 하지만 공용 컴포넌트로도 기존 MES에 없던 큰 카드, 도움말 박스, 잘못된 섹션 헤더와 테이블형 입력 영역을 만들 수 있었다.

이 문제를 통해 디자인 시스템의 범위를 다음처럼 다시 정의했다.

```text
Design System
  = Token
  + Component
  + Component Usage Context
  + Shell
  + Section Frame
  + Section Pattern
  + Behavior
  + Action Set
  + Composition Grammar
  + Evidence / Validation
```

즉 부품뿐 아니라 부품의 선택 조건과 조합 방식까지 디자인 시스템이다.

### 3.2 패턴을 화면 단위로만 관리해서 재사용 단위가 너무 컸다

우측 슬라이드 팝업 전체나 중앙 팝업 전체를 하나의 패턴으로 보면, 내부의 기본정보·반복 입력·검색 테이블·검사항목 같은 구조를 새 화면에서 안전하게 다시 조합하기 어렵다.

그래서 화면을 다음 단위로 분해했다.

```text
ScreenSpec
  = Context Decision
  + Shell
  + ordered SectionInstance[]
  + BehaviorReference[]
  + ActionSet

SectionInstance
  = SectionFrame
  + SectionPattern
  + 화면별 데이터·문구·필드 설정
```

중앙 모달의 Header/Footer는 Shell 책임이고, 그 사이에 어떤 Section Pattern을 넣느냐에 따라 실제 업무 팝업이 달라진다. 우측 슬라이드도 같은 방식으로 설명한다.

### 3.3 원본 충실도와 표준화를 한 단계에서 처리하면 판단 근거가 사라졌다

Figma의 모든 픽셀값을 그대로 표준으로 만들면 사람의 실수까지 시스템에 고착된다. 반대로 원본을 보면서 바로 정규화하면 실제 원본이 무엇이었는지 사라진다.

그래서 다음 두 층을 분리했다.

- 원본 증거층: Figma의 구조·문구·상태·실측값을 보존
- 표준 규칙층: 반복 근거와 토큰 체계를 토대로 승인된 값과 조합을 관리

둘이 다를 때는 `source-error`, `implementation-error`, `intentional-exception`, `normalization-candidate` 중 하나로 이유를 기록하도록 했다.

### 3.4 AI에게 문서를 읽으라고만 해서는 같은 결과가 보장되지 않았다

자연어 문서는 방향을 이해시키는 데는 좋지만, 누락된 섹션이나 잘못된 셸을 자동으로 차단하지 못한다. 그래서 규칙을 JSON/TypeScript 계약과 검사 스크립트로 옮겼다.

현재 AI는 화면을 만들기 전에 ScreenRequest를 만들고 resolver를 통과해야 한다. Resolver는 선택 결과뿐 아니라 왜 선택했고 어떤 후보를 제외했는지를 `decisionTrace`로 반환한다. 구현 감사는 이 계약과 실제 TSX를 대조한다.

### 3.5 모바일은 웹의 축소판이 아니었다

모바일은 별도 파운데이션, 컴포넌트, 화면 유형과 업무 흐름이 필요하다는 점을 확인하고 전용 인벤토리와 원본 화면을 구성했다. 다만 모바일 디자인이 크게 바뀔 가능성이 높다는 사용자 결정에 따라 현재는 산출물을 보존한 채 `deferred` 상태로 멈췄다. 현재 웹 표준을 확정할 때 모바일 시안을 근거로 사용하지 않는다.

## 4. 지금까지 실제로 한 일

### 4.1 원본·자산·화면 코드화

- MES 파운데이션과 시맨틱 토큰을 정리했다.
- Button, Input, Select, Checkbox, Radio, Filter, SearchInput, Table 등 공용 UI를 구성했다.
- 중앙 모달과 우측 슬라이드 패널을 별도 Shell로 분리했다.
- 폼 그리드, 검색·테이블, 편집 행 목록, 검사항목, 그룹형 테이블과 선택 동작을 패턴으로 분리했다.
- 주요 원본 화면과 팝업을 코드화하고, 팝업을 업무 메뉴명이 아니라 위치와 본문 성격으로 분류했다.
- 체크박스 선택, 선택 행 편집, 숫자 입력, 필터, 취소·닫기 복원, 행 추가·삭제 등 실제 동작을 보강했다.
- AI 생성 시안과 원본 자산을 분리하고, 승인 전 시안이 다음 화면의 표준 근거가 되지 않도록 격리했다.

### 4.2 표준 후보와 실험 자산 정리

- Tier 3~5 후보를 실제 컴포넌트인지, 패턴인지, 단순 업무 예시인지 다시 판정했다.
- 단건 업무명에 불과한 항목과 기존 컴포넌트 조합으로 설명되는 항목을 제거했다.
- 유지 대상으로 승인된 항목은 정식 자산으로 승격하고, 제외 항목은 생성 근거에서 제거했다.
- 원시 `<button>`, `<input>`, `<select>`, `<table>` 사용과 no-op 상호작용을 검사하도록 구성했다.

### 4.3 AI UI 조합 문법 구축

- 화면과 패턴의 1:1 관계를 없애고 `Shell + Section + Behavior + ActionSet + Recipe` 조합으로 이관했다.
- 액션, 입력, 섹션 경계, 테이블 적합성, 스크롤 소유자와 헤더 위계의 맥락 규칙을 구조화했다.
- 취소와 우상단 닫기가 변경 전 상태를 복원하는 `dismiss.restore-committed` 계약을 등록했다.
- 반복 입력 행과 읽기·선택 테이블을 구분하고, 정렬을 위해 Table을 사용하는 것을 금지했다.

### 4.4 핵심 웹 맥락 계약 구축

2026-08-24 배치에서 다음을 추가했다.

| 계약 | 현재 범위 | 역할 |
|---|---:|---|
| 컴포넌트 사용 계약 | 핵심 20개 | 사용·금지 조건, 부모, 상태, 제약, 대안과 근거 |
| 패턴 계약 | 핵심 10개 | 슬롯, 상태 모델, 동작 대상, 스크롤, action set과 구현 marker |
| 순서형 ScreenSpec | 대표 3개 | 실제 섹션 순서, 슬롯, 컴포넌트, 동작과 스크롤 책임 |
| 생성 템플릿 | 3개 | 같은 계약에서 같은 TSX 생성 |

대표 ScreenSpec은 다음 세 구조다.

1. 우측 슬라이드: 기본정보 + 편집 가능한 품목 목록 + 선택 정보
2. 중앙 모달: 필터·검색 + 선택 테이블 + 취소 복원
3. 전체 페이지: 조회 조건 + 그룹형 데이터 목록

### 4.5 Resolver·감사·MCP·이식성

- 동일한 ScreenRequest와 동일한 Git 커밋에서 같은 registry fingerprint와 조합 결과가 나오도록 했다.
- Resolver가 셸, 순서형 섹션, 동작, 액션, 컴포넌트의 선택·제외 이유를 `decisionTrace`로 반환한다.
- 감사기가 섹션 ID와 순서, 패턴 marker, ActionSet, 셸, 원시 control, 미등록 import와 임의 px를 검사한다.
- 로컬 `mes-ui` MCP를 만들어 Codex와 Claude Code가 같은 조회·해석·생성·감사 엔진을 사용하게 했다.
- MCP가 컴포넌트 목록만이 아니라 사용 계약, 패턴 슬롯 계약과 순서형 ScreenSpec 상세를 반환하도록 했다.
- 다른 컴퓨터에서도 저장소 clone → `npm ci` → AI 도구의 프로젝트 MCP 승인 후 같은 흐름을 실행할 수 있게 했다.

### 4.6 문서와 AI 실행 규칙

- README를 단순 컴포넌트 라이브러리 설명에서 AI UI 자동화 프로젝트 설명으로 확장했다.
- 공통 조합 정책, 맥락 규칙, 이식성 가이드, 적용 TODO와 완료 표현을 정리했다.
- 저장소 전용 AI Skill과 `AGENTS.override.md`에 ScreenRequest → Resolve → Generate/Audit → Verify 순서를 강제했다.
- `구현됨`, `검증됨`, `배치 완료`, `전체 완료`의 의미를 분리해 아직 검증되지 않은 결과를 완료로 보고하지 않도록 했다.

## 6. 지금 보장되는 것과 아직 보장되지 않는 것

### 보장되는 것

- 같은 ScreenRequest와 같은 커밋이면 같은 화면 조합 계약과 fingerprint가 나온다.
- 대표 ScreenSpec에서는 섹션 순서와 스크롤·동작 책임이 구조화된다.
- 핵심 계약 범위에서는 AI가 선택한 자산과 제외한 후보의 이유를 확인할 수 있다.
- 결정형 템플릿 3종은 같은 입력에서 같은 TSX source hash를 생성한다.
- 잘못된 셸, 섹션 누락·순서 오류, 원시 control, 잘못된 ActionSet 등은 구현 감사에서 차단된다.
- 다른 컴퓨터와 다른 지원 AI에서도 같은 저장소 계약과 로컬 MCP를 사용할 수 있다.

### 아직 보장되지 않는 것

- 등록된 28개 화면 전체가 순서형 ScreenSpec으로 이관된 것은 아니다. 현재 3개가 대표 명세다.
- 88개 컴포넌트 전체가 20개 핵심 자산과 같은 깊이의 사용 계약을 가진 것은 아니다.
- 모든 Recipe가 결정형 코드 생성 템플릿을 가진 것은 아니다.
- 결정형 코드가 나온다는 사실만으로 Figma 픽셀이 완전히 일치하는 것은 아니다.
- 중앙 검색 테이블 stable 템플릿은 계약·결정성·감사를 통과했지만 실제 대표 Figma와 브라우저 시각 검증을 더 해야 한다.
- 페이지 엔티티 목록은 Pagination 성숙도와 정확한 원본 근거가 남아 있어 provisional이다.
- 기존 Figma와 실제 MES 웹 중 어느 쪽이 잘못됐는지 모든 화면에서 판정된 상태는 아니다.
- 프로젝트 전체가 완료된 것은 아니다.

## 7. 앞으로 해야 할 일

### 우선순위 1. 지금 만든 생성 경로를 실제 원본으로 검증

1. 중앙 검색·선택 테이블 대표 화면을 실제 Figma와 대조한다.
2. 위치·크기·간격·색상·radius의 구조 오차를 측정한다.
3. 텍스트와 SVG의 렌더링 오차를 별도로 확인한다.
4. 검색, 필터, 체크박스, 행 선택, 입력 전환, 취소·닫기 복원을 실제로 조작한다.
5. 구조·동작·시각 검증이 모두 통과한 경우에만 해당 템플릿을 `검증됨`으로 기록한다.

### 우선순위 2. 페이지 엔티티 목록을 stable로 승격

1. 실제 MES 페이지 원본에서 헤더, 조회 영역, 테이블, Pagination과 하단 배치를 확정한다.
2. provisional인 Pagination 의존성과 생성 코드의 임의 px 경고를 해결한다.
3. 전체 페이지의 가로·세로 overflow와 viewport별 동작을 검증한다.
4. 원본·계약·브라우저 검증 후 `page-entity-list.v1`을 stable로 승격한다.

### 우선순위 3. 실제 요청이 생기는 화면부터 계약 범위 확장

나머지 25개 화면과 68개 컴포넌트를 형식적으로 한 번에 채우지 않는다. 새 화면 생성 또는 기존 화면 수정 요청이 들어오는 순서로 다음을 수행한다.

1. 가장 가까운 기존 화면과 원본 근거를 선택한다.
2. 기존 사용 계약과 패턴 계약으로 설명되는지 확인한다.
3. 필요 화면을 순서형 ScreenSpec으로 이관한다.
4. 계약 밖 자산이 실제로 사용되면 해당 자산의 사용 맥락을 구조화한다.
5. 기존 패턴으로 표현할 수 없다면 기존 패턴의 불완전성부터 검토한다.
6. 그래도 의미·상태·행동이 본질적으로 다를 때만 새 proposal을 격리한다.
7. 반복 근거와 사람 승인 후에만 표준으로 승격한다.

### 우선순위 4. 기존 UI 오류 감사로 확장

신규 화면 생성과 같은 계약을 기존 구현에도 적용한다.

- Figma와 실제 MES 웹의 차이를 자동 수집한다.
- 컴포넌트 우회, 잘못된 variant, 섹션 순서, 스크롤 소유자와 상호작용 누락을 검사한다.
- 차이를 Figma 오류, 구현 오류, 의도된 예외, 정규화 후보로 분류한다.
- 자동 수정은 근거가 명확하고 영향 범위가 제한된 경우에만 수행한다.
- 수정 전후 시각 회귀와 업무 동작을 함께 검증한다.

### 우선순위 5. 운영 지표와 보고 체계 구축

자동화 성과는 단순히 화면 개수로 평가하지 않는다. 다음 지표를 누적하는 편이 적절하다.

- 요구 입력부터 첫 검토 가능한 시안까지 걸린 시간
- 첫 시안에서 구조·동작·시각 검증을 통과한 비율
- 사용자 수정 요청 횟수와 원인
- 미등록 자산·새 proposal 발생률
- 기존 컴포넌트·패턴 재사용률
- Figma·코드 불일치 탐지 및 수정 건수
- 같은 요청의 반복 생성 구조 일치율

## 8. 앞으로 화면 하나를 만드는 표준 흐름

```text
업무 요구 또는 Figma 원본
  → ScreenRequest 작성
  → 가장 가까운 ScreenSpec·패턴·컴포넌트 계약 조회
  → Resolver 실행 및 decisionTrace 검토
  → blocker 해결
  → 지원 템플릿이면 결정형 TSX 생성
  → 미지원이면 해결된 계약 범위 안에서만 구현
  → 구현 감사
  → 브라우저 DOM·overflow·상호작용 측정
  → Figma 시각 비교
  → 결과 기록 및 사람 승인
  → 필요한 계약만 확장
  → Git 커밋
```

핵심은 AI가 바로 JSX를 쓰지 않게 하는 것이다. 먼저 조합 계약을 만들고, 선택 근거를 남기고, 구현을 계약에 대조한 뒤 원본과 검증한다.

## 9. 사람이 제공하거나 판단해야 하는 것

새 화면마다 원본 전체를 다시 제공할 필요는 없다. 현재 근거로 설명 가능한 구조는 기존 계약을 사용한다. 다만 다음 경우에는 사람의 정보나 승인이 필요하다.

- 기존 규칙으로 설명할 수 없는 새로운 업무 흐름
- 선택 후 어떤 필드가 편집 상태로 변하는지처럼 정적 화면만으로 확정하기 어려운 동작
- Figma의 여러 수정안 중 어느 것이 최신인지 불명확한 경우
- Figma와 실제 MES 웹이 다르고 어느 쪽이 올바른지 업무 판단이 필요한 경우
- 새 패턴 승격 또는 기존 패턴 의미 변경
- 원본에 없는 안내·요약·추가 기능을 새 화면에 넣을지에 대한 제품 결정

AI는 후보와 영향 범위를 제안할 수 있지만, 새로운 표준의 최종 승인을 대신하지 않는다.

## 10. 다음 권장 배치

다음 작업은 새 화면을 더 많이 추가하는 것이 아니라 아래 두 가지를 먼저 끝내는 것이 효율적이다.

1. 중앙 검색 테이블 stable 템플릿을 실제 대표 Figma·브라우저와 검증
2. 페이지 엔티티 목록의 Pagination·시각 근거를 정리해 provisional에서 stable로 승격

이후 실제 업무 요청이 들어오는 화면부터 ScreenSpec과 계약 범위를 확장한다. 모바일은 디자인 방향이 확정될 때 별도 트랙으로 재개한다. Figma Code Connect와 Figma 내 컴포넌트 연결 작업도 현재 Git 기반 자동화와 분리된 별도 작업으로 다룬다.

## 12. 완료 상태 표현

- `구현됨`: 코드와 계약은 존재하지만 원본 대조 또는 전체 검증이 남아 있음
- `검증됨`: 원본 대조, 브라우저 실측, 상호작용과 시각 회귀를 통과함
- `배치 완료`: 시작 전에 선언한 해당 배치 전체가 검증됨
- `전체 완료`: 레지스트리의 진행·보류·미승인·TODO가 모두 0이고 프로젝트 목표가 달성됨

현재 상태를 정확히 표현하면 **핵심 웹 맥락 계약과 결정형 생성 경로 확장 배치는 구현·자동 검사까지 완료됐고, 실제 원본 기반 검증과 적용 범위 확장은 계속 진행 중**이다.
