# MES AI UI 자동화 진행 요약

> 기준일: 2026-08-24 · 전체 상태: `in-progress` · 모바일: `deferred`

## 1. 왜 하는가

목표는 기존 MES 디자인을 코드로 보존하고, AI가 같은 규칙으로 새로운 화면을 만들게 하는 것이다.

초기에는 원본 화면과 컴포넌트를 코드화하는 데 집중했다. 그러나 공용 컴포넌트를 사용해도 AI가 기존 MES에 없는 카드, 헤더, 안내 문구와 배치를 임의로 추가했다. 컴포넌트 목록만으로는 다음을 결정할 수 없었기 때문이다.

- 어떤 상황에 어떤 컴포넌트를 쓰는가
- 중앙 모달과 우측 슬라이드를 어떻게 구분하는가
- 섹션을 어떤 순서로 배치하는가
- 선택·입력·취소·저장과 스크롤이 어떻게 동작하는가

그래서 디자인 시스템의 범위를 `토큰 + 컴포넌트 + 사용 맥락 + 조합 패턴 + 동작 + 검증`으로 확장했다.

## 2. 지금까지 한 일

### 원본과 공용 자산

- 주요 Figma 화면과 팝업을 코드화했다.
- Button, Input, Select, Checkbox, Radio, Filter, Table, Modal 등 공용 자산을 구성했다.
- 원본 자산과 AI 생성 시안을 분리해, 미승인 시안이 다음 화면의 기준이 되지 않게 했다.

### 조합 문법

- 화면 전체를 하나의 패턴으로 보지 않고 `Shell + Section + Behavior + ActionSet + Recipe`로 분해했다.
- 중앙 모달, 우측 슬라이드, 폼, 검색 테이블, 편집 목록, 검사항목과 선택 동작을 구분했다.
- 대표 화면 3종을 실제 섹션 순서를 가진 ScreenSpec으로 만들었다.

### AI 판단과 자동 검사

- 핵심 컴포넌트의 사용·금지 조건, 허용 부모, 상태와 대안을 구조화했다.
- 패턴의 슬롯, 스크롤, 동작 대상과 하단 액션을 구조화했다.
- Resolver가 선택한 자산과 제외한 후보의 이유를 `decisionTrace`로 반환하게 했다.
- 잘못된 셸, 섹션 누락·순서 오류, 원시 HTML control, 잘못된 ActionSet을 자동 검사한다.

### 반복 생성과 이식성

- 우측 슬라이드, 중앙 검색 테이블, 페이지 목록의 결정형 생성 템플릿을 만들었다.
- 저장소 Skill과 로컬 MCP를 구성해 다른 PC와 지원 AI에서도 같은 계약·생성·감사 도구를 사용할 수 있게 했다.

## 3. 현재 상태

| 항목 | 현재 수치 |
|---|---:|
| 컴포넌트 | 88개 |
| 패턴 | 62개 |
| 화면 정의 | 28개 |
| 상세 사용 계약 | 컴포넌트 20개·패턴 10개 |
| 순서형 ScreenSpec | 대표 3개 |
| 결정형 생성 템플릿 | 3개 |

생성 템플릿 상태:

- 우측 슬라이드 폼 + 편집 목록: `stable`
- 중앙 검색 + 선택 테이블: `stable`
- 페이지 엔티티 목록: `provisional`

전체 디자인 시스템 검사, 화면 계약 fixture, MCP 연결·생성·감사, 린트, TypeScript와 프로덕션 빌드는 통과했다.

## 4. 지금 가능한 것과 남은 한계

가능한 것:

- 같은 ScreenRequest와 같은 커밋에서 같은 조합 계약을 만든다.
- 대표 화면은 섹션 순서와 동작·스크롤 책임을 고정한다.
- 결정형 템플릿은 같은 입력에서 같은 TSX를 생성한다.
- 주요 구조 오류를 구현 전에 차단한다.

아직 남은 것:

- 화면 28개 전체가 순서형 ScreenSpec인 것은 아니다.
- 컴포넌트 88개 전체가 상세 사용 계약을 가진 것은 아니다.
- 모든 화면 유형이 결정형 생성기를 가진 것은 아니다.
- 같은 코드가 생성돼도 Figma 픽셀 검증까지 끝났다는 뜻은 아니다.
- 페이지 목록은 원본 근거와 Pagination 검증이 남아 있다.

## 5. 앞으로 할 일

1. **중앙 검색 테이블 검증**

   실제 Figma와 배치·간격을 대조하고 검색, 필터, 선택, 취소·닫기와 overflow를 검증한다.

2. **페이지 목록 안정화**

   Pagination과 화면 배치 근거를 확정한 뒤 `provisional`에서 `stable`로 승격한다.

3. **필요한 화면부터 계약 확장**

   나머지 화면을 한꺼번에 채우지 않고 실제 생성·수정 요청이 들어오는 순서로 ScreenSpec과 사용 계약을 확장한다.

4. **기존 MES 화면 감사**

   Figma와 실제 구현의 차이를 수집하고 Figma 오류, 구현 오류, 의도된 예외, 정규화 후보로 분류한다.

모바일은 디자인 변경 가능성 때문에 현재 상태를 보존하고 추후 재개한다. Figma Code Connect는 별도 작업으로 진행한다.

## 6. 앞으로 화면을 만드는 순서

```text
업무 요구 또는 Figma
→ ScreenRequest
→ 기존 계약 조회와 Resolver 판정
→ 결정형 생성 또는 계약 기반 구현
→ 구현 감사
→ 브라우저 동작·overflow 검증
→ Figma 시각 비교
→ 사람 승인과 Git 반영
```

핵심은 AI가 바로 JSX를 만들지 않고, 먼저 조합 계약을 확정한 뒤 구현과 검증을 진행하는 것이다.

## 7. 결론

핵심 웹 맥락 계약과 결정형 생성 기반은 구성했다. 이제 새 화면 수를 늘리기보다 현재 생성기를 실제 원본으로 검증하고, 실제 요청이 들어오는 순서대로 계약 범위를 넓혀야 한다.
