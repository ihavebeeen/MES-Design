# AI 에이전트라서 구조적으로 반복되는 문제 유형

## 0. 배경

`docs/외부_에이전트_작업_실수_기록_Figma재현.md`가 "리포 밖(Figma 등)에 결과물을
만들 때" 생긴 구체적 사고 하나(폰트/아이콘/행높이)를 기록한 문서라면, 이 문서는
범위를 좀 더 넓혀서 "이 에이전트가 AI라서 구조적으로 반복하기 쉬운 문제 유형"을
정리한다. 개별 사고 하나하나를 다 적진 않고, 여러 사고를 관통하는 패턴을 정리해서
다음에 낯선 문제를 만났을 때도 "이거 그 패턴이잖아"라고 알아챌 수 있게 하는 게
목적이다.

2026-08-05, 담당자가 "AI라서 생기는 어쩔 수 없는 문제들이 있잖아, 그런 것도 구조화해서
적어보고 싶다"고 요청해서 시작. 같은 세션에서 실제로 겪은 사례(페이지 라우팅 리팩터링
중 배너 3개 중 2개만 고치고 "다 고쳤다"고 답했던 것)를 계기로 만들었다.

이 문서도 `외부_에이전트_작업_실수_기록_Figma재현.md`와 같은 원칙으로 운영한다:
새로운 패턴이 발견되면 기존 항목을 지우지 않고 이어 붙인다. 다만 매 작업마다 이
체크리스트를 전부 훑는 무거운 절차로 쓰지는 않는다 — 원인 대부분이 "확인을 안 한
것" 하나로 수렴하듯, 대응도 대체로 "그 순간에 확인하고, 확인 못 했으면 확인 못
했다고 먼저 말한다"는 가벼운 습관 하나로 커버된다(자세한 논의는 4번 참고).

## 1. 확인 안 된 걸 확인됐다고 단정

**무엇**: 실제로 검증하지 않은 것을 "맞다/됐다"고 확정적으로 말하는 것.

**사례**: 2026-08-05, 페이지 분할(라우팅) 리팩터링 중 "Foundation/Components 배너가
`activeGroup`과 무관하게 항상 뜬다"는 리포트를 받고 코드를 고친 뒤 "로직 다시 봐도
맞는데?"라고 재검토 없이 답했다가, 사용자가 스크린샷을 보여줘서야 세 번째(놓쳤던)
배너가 있었다는 게 드러남.

**왜 생기나**: 코드를 눈으로 읽고 "이 로직이면 이렇게 동작해야 한다"고 추론하는 것과,
실제로 그 코드가 그 환경에서 그렇게 동작하는지 관찰하는 것은 다른 종류의 확인이다.
AI는 전자(추론)는 잘하고 확신도 높게 말하지만, 후자(관찰)는 도구가 없으면 아예 못
한다 — 그런데 말투는 둘 다 "확인했다"처럼 나온다.

**대응**: 실제로 관찰(브라우저 렌더링, 실행 결과 등)한 게 아니라 코드만 읽고 판단한
거라면 "코드상 이렇게 되어야 한다"와 "실제로 확인했다"를 언어적으로 구분해서 말한다.

## 2. 실행 환경이 다르면 같은 로직도 다른 결과가 나옴

**무엇**: "같은 알고리즘/같은 값"이라고 생각하고 다른 환경에서 재현했는데, 실제로는
그 환경의 세부 구현 차이 때문에 결과가 달랐던 경우.

**사례**:
- JS `String.prototype.localeCompare(str, "ko")`(가나다 정렬)를 Python으로 흉내
  냈다가 정확한 한글 로케일 정렬을 재현하지 못함 — 실제 Node.js를 실행해서 진짜
  `.sort()` 결과를 뽑아내야 했음.
- Figma 자동화 스크립트(`use_figma`)의 `loadFontAsync`가 접근 가능한 폰트 목록은
  Figma 데스크탑 앱에서 사람이 직접 텍스트 도구로 타이핑할 때 보이는 폰트 목록과
  다름(로컬 OS 설치 폰트는 자동화 쪽에서 접근 불가) — 앱에서 보인다고 스크립트에서도
  될 거라고 가정하면 틀림(자세한 내용은 Figma재현 문서 5번).

**왜 생기나**: "비슷한 도구로 재현한 결과"를 "그 환경에서 직접 실행한 결과"와 동일시하기
쉽다. 특히 두 도구가 같은 언어/같은 이름의 기능을 제공하면(Python도 정렬 함수가
있으니까, Figma 앱도 폰트 목록을 보여주니까) 세부 구현이 다를 수 있다는 걸 간과하기
쉽다.

**대응**: 결과가 미묘하게 정확해야 하는 값(정렬 순서, 폰트 가용성처럼)은 "비슷한 걸로
재현"하지 말고 실제 그 환경(진짜 Node.js, 진짜 Figma 자동화 실행 컨텍스트)에서 직접
실행해서 확인한다.

## 3. 그 순간엔 알았지만 코드 짤 때 다시 안 봄

**무엇**: 대화 초반에 정확한 값을 이미 읽고 사용자에게 설명까지 했는데, 실제로 코드를
작성하는 시점에는 그 값을 다시 대조하지 않고 기억(추정)으로 다른 값을 씀.

**사례**: Figma재현 사고의 직접 원인. `table.tsx` 주석에 "행 높이 30px"라고 적혀 있는
걸 이미 읽었고 담당자에게 "30px로 명시돼 있다"고 설명까지 했는데, 정작 Figma 코드를
쓸 때는 34px/40px 같은 눈대중 숫자를 씀.

**왜 생기나**: 대화가 길어질수록 "이전에 읽은 값"과 "지금 쓰고 있는 값"이 컨텍스트
안에서 멀어진다. 사람도 그렇지만, AI는 특히 "그럴듯한 숫자"를 그 자리에서 바로
만들어낼 수 있어서(환각) 다시 찾아보는 수고를 생략하고 싶은 유혹이 더 크다.

**대응**: 나중에 코드/값으로 옮겨 쓸 구체적인 수치·이름을 발견하면, 그 자리에서 바로
받아적어 두고(새 문서 말고 그 결과 안에), 실제로 쓸 때는 기억이 아니라 그 메모를
복붙한다.

## 4. 눈으로 못 보는 것에 대한 과신

**무엇**: 이 작업 환경(샌드박스)에는 브라우저가 없어서 실제 렌더링 결과를 볼 수
없는데도, 코드가 논리적으로 맞으면 화면도 맞을 거라고 단정.

**사례**: 1번과 같은 사고 — `npm run dev`도 샌드박스 리소스 제약으로 확인이 안 되고,
Claude in Chrome 같은 브라우저 도구도 이 프로젝트 세션엔 없어서, 결국 코드 로직
추론 → "됐다" 선언 → 사용자가 실제로 켜보고 리포트, 의 순환이 반복됨.

**왜 생기나**: 1번과 근본 원인은 같지만, 이 경우는 애초에 확인할 방법 자체가 없다는
점이 다르다 — "깜빡하고 확인 안 함"이 아니라 "확인할 도구가 없음". 그런데도 말투는
확인한 것처럼 나가기 쉽다.

**대응**: 시각적/런타임 검증이 필요한 변경은 "이 환경에서는 직접 확인할 방법이 없다"는
걸 결과물과 함께 먼저 밝히고, tsc/grep처럼 실제로 할 수 있는 검증(타입, 텍스트 패턴)이
무엇이고 무엇이 아닌지를 구분해서 말한다.

## 5. 부분적으로 고치고 "다 고쳤다"고 선언(불완전한 전수 조사)

**무엇**: 같은 종류의 문제가 여러 군데 있을 수 있는데, 기억나는 만큼만 찾아 고치고
"이제 다 고쳤다"고 말하는 것.

**사례**: 2026-08-05 페이지 분할 작업에서 "Foundation 배너"와 "Components 배너" 2개를
찾아 조건부 렌더링을 고치고 완료라고 답했는데, 실제로는 목록 중간에 물리적으로 끼어
있던 "예정" 배너가 하나 더 있었음(61차에 추가된 것이라 62~64차 작업 때 존재 자체를
몰랐음). 사용자 재신고 이후 `grep`으로 같은 패턴(`border-l-8`) 전체를 검색해서야
정확히 3개였다는 걸 확인.

**왜 생기나**: "이런 종류의 요소가 몇 개 있었지"를 기억/추정으로 판단하고, 그 추정을
검색으로 재확인하지 않음. 리팩터링처럼 파일 전체에 흩어진 동일 패턴을 다뤄야 하는
작업에서 특히 위험하다.

**대응**: "같은 종류가 더 있을 수 있는" 구조적 변경(리팩터링, 전역 치환, 조건 추가
등)을 할 때는 "몇 개인지 기억으로 판단"하지 말고, 그 패턴을 검색(grep 등)해서 개수를
직접 세고 전부 확인했는지 대조한다. 처음부터 매번 이렇게 하면 좋지만, 최소한 사용자가
"그래도 안 된다"고 재신고했을 때는 반드시 전수 검색으로 넘어간다.

## 6. 지적받으면 재검토 대신 자기 논리를 방어함

**무엇**: 사용자가 실제 증거(스크린샷, 재현 결과)를 제시했는데도, 코드를 다시 훑어보고
"이래도 로직상 맞는데?"라며 자기 추론을 우선하는 것.

**사례**: 1번/5번과 같은 사고에서, 사용자가 "여전히 이렇게 뜨는데?"라고 스크린샷을
보내기 전까지 "조건식 다시 계산해봐도 맞다"고 코드만 재확인하며 답변함 — 실제
원인(놓친 세 번째 배너)은 스크린샷을 받고 나서야 찾음.

**왜 생기나**: 자기가 방금 짠 코드의 정당성을 언어로 재구성(재추론)하는 게, 파일
전체를 처음부터 다시 훑는 것보다 훨씬 쉽고 빠르다. 그래서 사용자의 실제 관찰보다
자기 추론을 먼저 신뢰하게 되는 경향이 생긴다.

**대응**: 사용자가 실제 재현 결과(스크린샷, 로그, 에러 메시지)를 들고 오면, 그건
"내 추론이 맞는지 다시 계산"하는 것보다 우선순위가 높은 증거로 취급한다. 재추론으로
답하지 말고 그 증거를 출발점 삼아 다시 찾는다(추측이 아니라 검색으로).

## 7. 샌드박스 자체의 구조적 제약(실수는 아니지만 반복되는 한계)

**무엇**: 이 작업 환경 자체의 한계 — `git push`용 GitHub 인증이 없어 항상 로컬
커밋까지만 되고 push는 사용자가 GitHub Desktop으로 해야 함, `npm run build`/
`npm run dev`가 샌드박스 리소스 제약(Bus error, 응답 없음)으로 끝까지 실행이 안 됨.

**왜 다른 항목과 다른가**: 위 1~6번은 "AI가 다르게 행동했으면 막을 수 있었던" 것들인
반면, 이건 환경 자체의 한계라 행동을 바꿔도 없앨 수 없다. 다만 같은 설명을 세션마다
반복하다 보면 "어차피 환경 탓"이라며 다른 실수(1~6번)까지 안일하게 환경 탓으로
돌릴 위험이 있어서 별도로 적어둔다.

**대응**: 환경 제약으로 못 하는 것(실행 검증)과, 그 안에서도 할 수 있는 것(tsc, grep,
정적 분석)을 매번 구분해서 말한다. "빌드가 원래 안 되는 환경이니까"를 다른 검증까지
생략하는 핑계로 쓰지 않는다.

## 8. 자식 컴포넌트가 부모 레이아웃의 배치 책임을 침범

**무엇**: 툴바가 `items-center`로 정확히 가운데 정렬되어 있어도 자식 컴포넌트 루트의
`self-start`가 이를 덮어써, 특정 입력창만 위쪽에 붙는 문제.

**사례**: 2026-08-10 투입품목 설정/조회 팝업. 48px 조회 툴바 안에서 Filter는 32px
높이로 가운데 정렬됐지만 SearchInput은 상단에 붙었다. 조립부에는 이미
`flex h-12 items-center`가 있었으므로 화면별 정렬값 누락이 아니었다. 공용
`SearchInput` 루트에 남아 있던 `self-start`가 부모 정렬을 우선순위로 이긴 것이
직접 원인이었다.

**왜 반복됐나**: 이전에 세로형 데모 부모의 `align-items: stretch` 때문에 hug-width
컴포넌트가 가로로 늘어나는 문제를 고치면서, 너비 계약 대신 교차축 정렬 속성인
`self-start`를 사용했다. 그 결과 한 화면에서는 너비 문제가 사라졌지만 다른 툴바에서는
수직 정렬 문제가 생겼다. 호출부마다 `items-center`를 다시 넣어도 자식의 `align-self`가
계속 이기므로 같은 수정이 효과가 없었다.

**대응**: 공용 입력·조회 컴포넌트는 높이와 폭만 소유하고 `self-start`/`self-center`로
자기 배치를 고정하지 않는다. hug-width는 `w-fit`+`shrink-0`으로 표현하고, 교차축 배치는
부모 slot의 `items-start`/`items-center`가 결정한다. 정렬 오류가 재발하면 호출부에
클래스를 덧붙이기 전에 자식 루트의 `align-self`부터 전수 검색한다.
