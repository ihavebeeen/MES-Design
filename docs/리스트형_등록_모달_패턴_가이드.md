# 리스트형 등록 모달(SideSlidePanel 패턴) — 설계 규칙 & 재사용 가이드

## 0. 이 문서의 목적

사이트에서는 이 패턴을 별도 최상위 메뉴로 분리하지 않고 `팝업` 카탈로그의
`우측 슬라이드 → 상하 분할 · 추가 + 하단 리스트` 유형으로 제공한다. 아래의
`리스트형 등록 모달`은 메뉴명이 아니라 재사용할 내부 구조 패턴의 이름이다.

`component-library/src/app/[...slug]/client-page.tsx`의 "리스트형 등록 모달"
Section(공정 등록/생산지시 등록 두 예시)을 만드는 과정에서 총 9차례
수정(71차~79차 커밋)을 거쳤다. 같은 실수 유형이 반복됐고, 그때마다 사용자가
직접 짚어줘야 했다. 이 문서는 (1) 지금까지 확정된 이 패턴의 구조 규칙과
(2) 다음에 똑같은 형태의 템플릿 화면(리스트 붙은 등록/수정 모달)을 만들 때
같은 실수를 반복하지 않기 위한 체크리스트를 남긴다.

`docs/AI_에이전트_구조적_한계_기록.md`가 이 리포 전반의 구조적 실수 패턴을
다룬다면, 이 문서는 "리스트형 등록 모달"이라는 구체적 화면 유형 하나에 좁혀서
쓴 실전 가이드다.

## 1. 확정된 구조 규칙

### 1-1. 모달 컨테이너: `CenterModal`이 아니라 `SideSlidePanel`

- 우측 고정, 세로 100vh, **radius 없음**(모서리가 사각형), 그림자만 있음
  (`drop-shadow(0px 0px 12px rgba(0,0,0,.2))`).
- 판단 기준: Figma 노드를 볼 때 레이어 이름(`"슬라이드 팝업"` 같은)이나 육안
  스크린샷 대조보다, **`get_design_context`로 뽑은 루트 컨테이너 클래스에
  radius 클래스가 있는지 없는지**가 가장 확실한 신호다. radius 클래스가
  없으면 SideSlidePanel, `rounded-[16px]` 같은 게 있으면 CenterModal.
- 폭은 기본값 960px가 아니라 **`get_screenshot`으로 프레임 실측 필요** —
  이 두 예시는 실측 결과 948px였다(`className="max-w-[948px]"`로 오버라이드).

### 1-2. 최상단 "기본정보" 구획

- 회색 필(pill) 배경(`PatternGroupHeader`)은 **`w-full`로 행 전체 폭을
  채워야 한다.** hug-width(텍스트 길이만큼만)로 만들면 틀린다 — 이 프로젝트
  스크린샷 육안 대조로는 hug/full 구분이 잘 안 보여서 여러 번 잘못
  판단했었다. 배경색은 Gray-30(`#e4e7ee`), radius는 4px(`rounded-mes-control`,
  3px `-sm`이 아님), 높이 28px, 좌우 padding 10px.
- 이 구획 전체는 `border-b border-mes-gray-30`로 아래쪽에 구분선이 있고,
  그 아래 두 번째 구획(회색 카드)과는 별도의 여백(20px)만 있을 뿐 divider
  선을 추가로 긋지 않는다.

### 1-3. 두 번째 구획: 회색 카드로 감싸진 "품목 등록/생산지시 정보" 폼

- `bg-mes-gray-20 rounded-lg(8px) px-4(16px) pt-3(12px) pb-8(32px)` 카드로
  전체를 감싼다 — 이 카드 래퍼 자체가 없는 채로 시작했다가 나중에 "흐린
  배경이 안 보인다"는 지적을 받았다. 처음부터 카드로 감싸는 걸 기본으로
  가정할 것.
- 이 구획의 제목("품목등록"/"생산지시 정보")은 **PatternGroupHeader(회색
  필)가 아니라 그냥 16px bold 텍스트**다 — "기본정보"만 필 배경, 나머지는
  플레인 타이틀. 이 두 개를 헷갈리기 쉽다.
- "추가" 버튼은 이 카드의 **하단 경계에 절반 걸치도록** 배치한다
  (`absolute -bottom-4 left-1/2 w-[160px] -translate-x-1/2`, 카드 자체의
  `pb-8`이 이 버튼이 들어갈 자리를 미리 확보해 둔 것).
- "리스트 조회/선택" 같은 보조 버튼이 있다면 카드 밖(제목과 같은 줄)에
  둔다. 두 예시 화면 중 하나는 이 버튼이 있고(공정 등록) 하나는 없다(생산지시
  등록) — Figma를 노드별로 각각 확인해야지 두 예시가 같은 구조라고
  넘겨짚으면 안 된다.

### 1-4. 세 번째 구획: 리스트 표 (카드 밖, 별도 구획)

- 이 파일의 공용 `Table` 컴포넌트(체크박스 칼럼 + 점선 칼럼 구분선 +
  Gray-10 헤더 배경)를 그대로 재사용하지 못하는 경우가 많다 — 체크박스가
  없는 단순 표라서. 하지만 **헤더 배경(Gray-10)과 칼럼 사이 점선
  구분선(Gray-40 dashed)은 공용 Table과 동일하게 유지해야 한다.** 처음엔
  "Figma 원본 마크업엔 이게 없다"는 이유로 뺐다가, 실제 서비스 화면 기준으로
  다시 추가해야 했다 — **이 리포에서 반복 확인된 우선순위: 실제 배포 화면 >
  Figma 원본 마크업.** Figma의 개별 예시 프레임은 단순화된 목업일 수 있다.
- 칼럼 정렬은 컬럼마다 다를 수 있다(가운데/왼쪽 섞여 있음) — 전 칼럼을
  일괄로 가운데 정렬하면 틀릴 확률이 높다. `get_design_context`를 표
  노드 하나에만 좁혀서 다시 호출해 칼럼별 `justify-center` 유무를
  직접 대조하는 게 가장 정확하다(스크린샷 육안 정렬 판독은 신뢰도 낮음).
- 칼럼 폭은 데이터 내용을 고려해서 정한다. 짧은 값(단위, 포장인원, 근무조,
  상태, 삭제)은 좁게, 길어질 수 있는 값(품목명, 증분 표기가 붙는 수량
  "2,600 (+600)")은 넉넉하게 — 균등폭으로 두면 특정 값이 줄바꿈된다.
  셀 텍스트에 `whitespace-nowrap`을 기본으로 걸어두고, 표 wrapper에
  `overflow-x-auto`를 둬서 폭이 부족하면 줄바꿈 대신 가로 스크롤이
  나오게 한다.
- "리스트 정보가 없을 때"(빈 상태) 화면도 같이 준비한다. 표 헤더는
  그대로 두고 본문 영역에 `EmptyState` 컴포넌트로 안내 문구를 보여준다
  (`components/ui/empty-state.tsx` 재사용, 아이콘 없이 title만 써도 됨).
  이 상태에서는 위 폼의 선택 필드들도 전부 미선택(placeholder만 노출),
  파생 필드(품목구분/단위/규격 등 disabled 필드)도 빈 값이어야 자연스럽다.
- **표 박스 자체는 hug-height가 아니라 남은 세로 공간을 다 채워야 한다
  (flex-1).** 처음엔 "행 개수만큼만" 박스 높이를 잡아서, 데모 데이터가
  2~4행뿐일 때 표 테두리 아래로 큰 빈 공간이 남는 채로 만들었다가
  지적받았다. 모달 콘텐츠 최상위 wrapper부터 표 박스까지 `flex-1`/
  `min-h-0`을 끊기지 않게 연쇄로 걸어야 실제로 남는 공간이 전달된다
  (하나라도 빠지면 hug로 되돌아간다). 행 높이(30px) 자체는 그대로 두고,
  행 목록만 별도 스크롤 컨테이너로 분리해서 헤더를 `sticky top-0`로
  고정하면 행이 많아져도 자연스럽게 스크롤된다. **모달 상단(기본정보 +
  회색 카드 폼) 영역은 hug 그대로 둔다** — hug/fill을 구분해야 하는
  대상은 "리스트 표"뿐이고, 폼 영역까지 늘리면 안 된다.

### 1-5. 하단 푸터

- `SideSlidePanel` 컴포넌트 자체에 이미 내장돼 있다(취소=Gray-40 배경,
  확인=Gray-130 배경, 각각 160px 폭, 40px 높이) — 직접 만들지 말고
  `cancelLabel`/`confirmLabel`/`onCancel`/`onConfirm` prop만 넘길 것.
- **확인 버튼 텍스트는 화면마다 다를 수 있다.** 기본값은 "저장"인데, 어떤
  화면은 실제로 "등록"을 쓴다(공정 등록) — Figma 텍스트만 믿지 말고 실제
  화면 스크린샷으로 한 번 더 확인. 근거 없이 "등록"으로 통일하는 임의
  판단을 했다가 나중에 되돌린 적이 있다.

### 1-6. 필드 스타일 3종 구분

값을 보여주기만 하는 필드가 전부 같은 스타일은 아니다. 배경색/텍스트색이
다른 두 가지 "비활성처럼 보이는" 스타일이 있으니 구분해서 써야 한다.

| 상태 | 배경 | 텍스트색 | 코드 |
|---|---|---|---|
| 일반 입력 | 흰색 | Gray-130 | `<Input />` |
| 읽기전용(값은 있지만 못 고침) | Gray-20 | Gray-130(안 흐려짐) | `<Input readOnly />` |
| 비활성(다른 선택에 따라 파생됨) | Gray-30 | Gray-70(흐려짐) | `<Input disabled />` |

두 예시 화면에서 실제로 이 두 스타일이 섞여 쓰였다(같은 "파생 필드"처럼
보여도 어떤 필드는 readOnly, 어떤 필드는 disabled) — 배경색과 텍스트색을
동시에 보고 판단해야지, "회색이니까 readOnly겠지"로 뭉뚱그리면 안 된다.

## 2. 반복된 실수 유형과 근본 원인

이번 작업에서 총 9차례 수정 중 최소 6번은 "이전 판단이 틀렸다"는 지적을
받고 뒤집었다. 원인을 정리하면:

1. **증거 우선순위를 매번 다시 헷갈렸다.** 확정해야 할 순서는:
   실제 배포 화면 스크린샷 > `get_design_context`로 뽑은 Figma 원본
   마크업(dev-mode 리터럴 텍스트/클래스) > `get_variable_defs` 실측 색상값
   > 고해상도 Figma 스크린샷 육안 대조 > Figma 레이어/인스턴스 이름 >
   저해상도 스크린샷 육안 대조. 레이어 이름("슬라이드 팝업")이나 육안
   스크린샷만 보고 판단했다가 뒤집힌 사례가 여럿이다.
2. **Figma 목업과 실제 서비스가 다를 수 있다는 걸 매번 다시 학습해야
   했다.** 라벨 텍스트("작업지시"↔"생산지시"), 필수 표시(*), 버튼 색,
   테이블 헤더 배경 등 상당수가 Figma 원본과 실제 배포 화면이 달랐다.
   Figma는 "설계 의도"이고 실제 화면이 "최종 진실"이라는 전제를 깔고
   시작해야 한다.
3. **표(Table)처럼 반복 요소가 많은 영역은 전체를 한 번에 눈대중으로
   처리하면 안 되고, 요소 하나하나(칼럼별 정렬, 폭, 구분선)를 원본
   코드에서 직접 대조해야 한다.** "대충 다 가운데 정렬이겠지" 같은
   일괄 처리가 반복적으로 틀렸다.
4. **한 번 틀렸다고 지적받으면 다음번엔 반대쪽으로 과잉 정정하는
   패턴이 있었다.** (예: hug-width가 틀렸다고 w-full로 바꿨다가, 다시
   hug-width로, 다시 w-full로.) 지적을 받으면 "왜 이번 근거가 이전
   근거보다 더 신뢰할 만한가"를 먼저 판단하고 고쳐야지, 최신 지적을
   무조건 이전 판단보다 우선시하면 이랬다저랬다 하게 된다. 이 문서
   1절의 확정 규칙들은 그 판단 결과를 고정해 둔 것이니, 새 근거 없이
   다시 뒤집지 말 것.

## 3. 다음번 유사 템플릿 화면을 만들 때 체크리스트

1. Figma 노드가 있다면 `get_design_context`를 **전체 모달 노드 한 번 +
   표(Table)처럼 반복 요소가 있는 하위 노드는 따로 한 번 더** 호출한다.
   전체 노드만 보고 하위 표의 칼럼별 세부 스타일을 넘겨짚지 않는다.
2. 실제 배포 화면 스크린샷이 있으면(또는 사용자가 제공하면) 그게 항상
   최종 근거다. 라벨 텍스트, 버튼 색/문구, 정렬은 스크린샷과 다시 대조.
3. 모달 컨테이너는 radius 유무로 CenterModal/SideSlidePanel을 먼저
   판별하고 시작한다.
4. "기본정보" 필은 w-full, 그 아래 구획 제목은 plain bold 텍스트,
   구획 전체를 감싸는 회색 카드 래퍼를 빠뜨리지 않는다.
5. 표는 공용 `Table` 컴포넌트의 헤더 배경(Gray-10)/점선 구분선
   컨벤션을 기본값으로 깔고 시작한다 — Figma 예시 프레임에 없어도.
6. 칼럼 폭은 내용 길이를 감안해서 정하고(균등폭 금지), 셀에
   `whitespace-nowrap` + 표 wrapper에 `overflow-x-auto`를 기본으로 건다.
7. 빈 리스트 상태(EmptyState) 화면을 처음부터 같이 만든다 — 나중에
   추가 요청받고 만들지 않는다.
8. 확인 버튼 문구("저장"/"등록" 등)는 화면마다 다를 수 있으니 기본값에
   의존하지 말고 실제 화면 기준으로 확인한다.
9. 값 표시 필드는 `readOnly`/`disabled` 중 어느 쪽인지 배경색+텍스트색
   둘 다 보고 판별한다.

## 4. 아직 판단값으로 남아있는 것

- "설정" 버튼 아이콘: Figma의 `mes/icon-setting`이 이 저장소에 없어서
  lucide `Settings`로 대체(모양이 100% 같지 않을 수 있음).
- 작업지시/생산지시 리스트 표의 행별 하이라이트 배경(파란/주황 톤):
  Figma 예시 프레임엔 있었지만 장식적 요소로 판단해 반영 보류.
- DatePicker 내부 아이콘 여백(pl/pr 비대칭): 이 페이지 여러 곳에서
  재사용하는 공용 컴포넌트라 이 패턴 하나만을 위해 내부 패딩을 새로
  만들지 않음 — Figma 실측과 완전히 일치하지 않을 수 있음.
