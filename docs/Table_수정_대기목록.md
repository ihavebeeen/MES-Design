## 1. 체크박스는 항상 가장 왼쪽 고정, 그 오른쪽에 그룹 열기/접기 — 순서가 깨짐

담당자 원문: "체크박스가 가장 좌측에 잇어야 하고 체크박스영역은 고정. 그 우측으로
그룹화 열기/접기가 나와야되는데"

- 그룹 행(`GroupHeaderRow`) 자체는 [체크박스] → [펼침 아이콘 + 라벨] 순서라 이 규칙을
  지키고 있음.
- 문제는 **헤더 행**: 3차 작업에서 depth별 "전체 접기/펼치기" 마스터 버튼(그룹이 3단이면
  3개)을 추가하면서, 체크박스보다 **왼쪽에** 배치해버림 — 담당자가 말한 "체크박스가 항상
  가장 왼쪽"이라는 규칙에 위배됨. 마스터 버튼들은 체크박스 오른쪽으로 옮겨야 함.
- 이때 순서를 바꾸는 김에 2번 항목(헤더-바디 정렬)도 같이 고려해서 구조를 짜야 함(아래
  참고) — 순서만 바꾸면 2번 버그가 또 재발할 수 있음.

## 2. (신규 버그) 헤더 컬럼과 바디 컬럼 위치가 안 맞음

담당자 원문: "합계열이랑 그냥 열이랑 위치는 맞는데 이번에는 헤더 그러니까 컬럼명이랑
열이랑 위치가 안맞아"

- 원인: 헤더 행에만 depth별 마스터 토글 버튼(18px × depth 수, 예: 3단이면 54px)을
  추가했는데, 그룹 행/데이터 행/총계 행에는 그만큼의 여백을 안 넣어줌 — 그 결과 헤더의
  체크박스+컬럼들이 다른 모든 행보다 마스터 버튼 폭만큼 오른쪽으로 밀려서 컬럼명과
  실제 값 컬럼이 어긋남.
- 2차 라운드에서 "헤더/데이터행/그룹행/총계행이 전부 같은 Cell 폭 배열을 공유해야 한다"는
  원칙을 세워놓고(재발 방지 규칙 6번, `신규_컴포넌트_설계_프로세스.md` 참고), 정작 3차에서
  새 요소(마스터 토글 버튼)를 추가할 때 이 원칙을 다시 어김. 즉 "라벨/버튼처럼 특정 행에만
  등장하는 요소를 추가할 때마다, 그 요소가 차지하는 폭만큼 다른 모든 행 종류에도 빈
  스페이서로 예약해줘야 한다"는 원칙을 이번에도 재차 지켜야 함.
- 수정 방향: "체크박스 → depth별 마스터 토글 영역" 을 하나의 고정폭 블록으로 취급해서,
  헤더는 이 블록 안에 실제 버튼을 그리고, 그룹행/데이터행/총계행은 이 블록 안을 비워두되
  폭은 정확히 동일하게 예약(`groupLevelCount * 18px`만큼 빈 `<div>` 등)해야 함.

## 3. 그룹 펼침 버튼 디자인을 요청 범위 밖에서 임의로 바꿈

담당자 원문: "왜 이번엔 회전만 바꾸라니까 그거 접기 버튼 디자인까지 바꿈????"

- 직전 요청은 "펼침/접힘 회전을 90도에서 180도로 바꿔달라"는 것뿐이었는데, 그 작업을 하며
  펼침 버튼의 테두리·배경 박스까지 같이 제거함(2차 때 "체크박스가 겹쳐 보인다"는 지적을
  임의로 "버튼 디자인 자체가 문제"라고 해석해서 미리 손댄 것 — 회전 요청 시점엔 이미
  반영돼 있었음). 결과물이 담당자가 대조 이미지로 제공한 원본 화면과 비슷해 보이긴 하지만,
  범위를 벗어난 변경이었다는 지적을 받음.
- 다음 세션 조치: (a) 담당자가 제공한 원본 스크린샷(테두리 없는 화살표만 있는 버전)과
  다시 정확히 대조해서 박스 유무를 확정하고 그 근거를 코드 주석에 남길 것. (b) 요청받은
  범위를 벗어나는 변경이 필요하다고 판단되면, 먼저 그 변경이 왜 필요한지 설명하고 확인을
  구한 뒤 진행할 것 — 회전 하나 요청했는데 디자인까지 같이 바뀌면 안 됨.

## 4. 그룹 라벨 텍스트가 잘려 보임 — 실제 버그인지 뷰포트 문제인지 확인 필요

담당자가 공유한 스크린샷에서 그룹 라벨이 "지시일: 2025-10-30"이 아니라 "시일:
2025-10-30"처럼 앞글자가 잘려 보임. 다만 담당자 본인도 "화면이 좁다보니까 제대로
안보이는거같기도 한데"라고 언급함 — 즉 좁은 뷰포트에서 가로 스크롤 때문에 왼쪽 끝이
잘려 보인 것일 수도 있고, 실제 렌더링 버그일 수도 있음. **넓은 화면(또는 스크린샷)에서
재확인 후 실제 버그면 원인 파악할 것.**

## 5. 데모 페이지가 좁아서 테이블이 한눈에 안 보임

담당자 원문: "지금 화면이 좁다보니까 제대로 안보이는거같기도 한데, 이거 걍 테이블
영역만 화면 쫙 늘려서 풀로 보여주거나, 아니면 그냥 쓸모없는컬럼 몇개 지워봐."

- `component-library/src/app/page.tsx`의 Table 데모 섹션이 `max-w-[1100px]`로 제한돼
  있어서, 컬럼이 많은 이 표는 가로 스크롤 없이 한 화면에 다 안 보임.
- 둘 중 하나(또는 둘 다) 적용:
  (a) Table 데모 섹션만 `max-w-[1100px]` 제약을 풀어서 전체 폭으로 표시,
  (b) 데모용 컬럼 수를 실제로 줄여서 시연 시 스크롤 없이 확인 가능하게.

## 6. 컬럼 폭이 전부 고정 px 절대값 — 가변폭 지원 검토

담당자 원문: "그니까지금 컬럼들이 다 절대값으로 들어간거야 설마그리고 다 가변값이면
너가 작업하기 더 편하지 않을까 싶은데."

- 현재 `TableColumn.width`는 항상 고정 px 숫자 하나뿐(`width: number`). 실측 기준으로는
  정확하지만, 화면 폭에 따라 유연하게 줄어들거나 늘어나지 않아서 데모/실사용 모두 가로
  스크롤이 잦음.
- 검토할 옵션(다음 세션에서 결정):
  - 컬럼별로 `width`(고정 px) 외에 `minWidth` + `flex`(비율) 조합을 선택적으로 쓸 수
    있게 타입 확장 — 예: 숫자 그대로면 기존처럼 고정폭, `{ flex: 1, minWidth: 100 }`
    같은 객체면 가변폭.
  - 전부 가변폭으로 바꾸면 Figma 실측 픽셀과의 정합성이 깨질 수 있어서, "이 컬럼은
    실측 그대로 고정, 저 컬럼은 가변" 식의 혼합 지원이 현실적일 가능성이 높음 — 실제
    화면에서 어떤 컬럼이 실측상 고정이어야 하는지(예: 시간/단위처럼 짧은 값) vs 가변이어도
    되는지(예: 품목명처럼 긴 텍스트) 담당자 확인 필요.
