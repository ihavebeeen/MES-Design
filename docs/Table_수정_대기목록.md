# Table 컴포넌트 — 수정 대기목록 (2026-07-28 8차 갱신)

원래 "지금은 토큰이 부족하니 기록만 해두라"는 요청으로 작성된 문서였는데, 담당자가
"수정 고고"라고 해서 2026-07-28에 1~5번을 전부 코드에 반영함(5차). 이후 결과물을 다시
보고 3건을 추가로 지적(6차), 다시 3건을 추가로 지적(7차), 이어서 데모 구성 관련 3건을
추가 요청(7차 후속), 그리고 합본 데모가 "시선강탈"이라는 지적(8차). **현재 시점 기준
미해결 항목은 없음** — 새 지적이 들어오면 이 문서에 이어서 추가할 것.

관련 파일: `component-library/src/components/ui/table.tsx`,
`component-library/src/app/page.tsx`(데모), `component-library/src/components/ui/checkbox.tsx`

배경: Table을 같은 날 안에 1차(Figma 실측) → 2차(실사용 화면 피드백 5건) → 3차(재검토
피드백 4건) → 4차(문서화만) → 4차 후속(버튼 디자인 정정) → 5차(1·2·4·5·6번 일괄 반영)
→ 6차(7·8·9번) → 7차(10·11·12번) → 7차 후속(13·14·15번) → 8차(아래 16번)까지 진행.
상세 경위는 `AGENTS.md`의 "Table 작업 회고" 섹션 참고.

## 1. (해결됨, 5차) 체크박스는 항상 가장 왼쪽 고정, 그 오른쪽에 그룹 열기/접기

담당자 원문: "체크박스가 가장 좌측에 잇어야 하고 체크박스영역은 고정. 그 우측으로
그룹화 열기/접기가 나와야되는데"

- 원인: 헤더 행에서 depth별 마스터 토글 버튼을 체크박스보다 **왼쪽에** 렌더링하고 있었음.
- 수정: 헤더 렌더 순서를 [체크박스] → [마스터 토글 영역]으로 교체. 그룹행(`GroupHeaderRow`)
  은 원래도 [체크박스] → [펼침 아이콘+라벨] 순서라 문제 없었음.

## 2. (해결됨, 5차) 헤더 컬럼과 바디 컬럼 위치가 안 맞던 버그

담당자 원문: "합계열이랑 그냥 열이랑 위치는 맞는데 이번에는 헤더 그러니까 컬럼명이랑
열이랑 위치가 안맞아"

- 원인: 헤더에만 마스터 토글 버튼 영역이 있고 그룹행/데이터행/총계행엔 그만큼의 여백이
  없어서, 헤더의 체크박스+컬럼들이 다른 행보다 오른쪽으로 밀렸던 것(2차에서 세운 "여러
  행 종류가 새 요소를 반영할 땐 전부 같은 폭을 예약해야 한다" 원칙을 3차에서 다시 어긴
  사례 — 재발 방지 규칙 6번).
- 수정: "체크박스 → 마스터 토글 영역"을 `MASTER_TOGGLE_SLOT_WIDTH`(24px) × depth 수로
  계산되는 고정폭 블록(`masterToggleAreaWidth`)으로 취급. 헤더는 이 블록 안에 실제
  버튼을 그리고, `DataRow`/`GroupHeaderRow`/`TotalsRow`는 전부 이 폭만큼 빈 스페이서를
  렌더링하도록 prop을 추가해서 통일. `renderGroupNode`까지 이 값을 재귀로 전달함.

## 3. (해결됨, 4차 후속) 그룹 펼침 버튼 디자인을 요청 범위 밖에서 임의로 바꿨던 것

담당자가 정확한 값(22x22px, 배경 `bg-mes-gray-0`, radius 3px, 테두리
`border-mes-gray-50` inside 1px)을 줘서 그룹행 펼침 버튼과 헤더 마스터 토글 버튼 둘 다
원상 복구함. 상세는 `table.tsx` 주석 7번.

## 4. (확인 완료, 5차) 그룹 라벨 텍스트 잘림 — 코드 버그 아님으로 잠정 결론

담당자가 공유한 스크린샷에서 그룹 라벨 앞글자가 잘려 보였던 것("지시일" → "시일").
코드 구조상(`overflow-visible` + `whitespace-nowrap`) 라벨이 잘릴 이유가 없고, 담당자
본인도 좁은 화면 때문일 수 있다고 언급했던 점을 종합해 뷰포트 폭에 의한 시각적 잘림으로
결론. 넓은 화면에서 다시 재현되면 별도로 조사할 것.

## 5. (해결됨, 5차) 데모 페이지가 좁아서 테이블이 한눈에 안 보이던 문제

`component-library/src/app/page.tsx`의 Table 데모 섹션 `max-w-[1100px]` 제약을 풀어서
(`max-w-none`) 화면 전체 폭을 쓰도록 변경. 컬럼 자체가 많아서 여전히 가로 스크롤은 필요할
수 있음(컨테이너 제약으로 인한 불필요한 압박만 제거한 것).

## 6. (기능 추가 완료, 실제 적용은 보류) 컬럼 가변폭 지원

담당자 원문: "그니까지금 컬럼들이 다 절대값으로 들어간거야 설마그리고 다 가변값이면
너가 작업하기 더 편하지 않을까 싶은데."

- `TableColumn.width`를 `number | { min: number; grow?: number }` 유니온 타입으로
  확장. 숫자면 기존과 100% 동일(고정 px), 객체면 `min`px 이상 유지하며 남는 공간을
  `grow` 비율로 나눠 갖는 가변폭 컬럼이 됨. `Cell` 컴포넌트가 두 형태를 모두 처리하도록
  수정.
- **아직 안 한 것**: 실제 데모 컬럼(`productionColumns`)을 가변폭으로 바꾸는 작업은
  안 함 — 어떤 컬럼을 고정으로 유지하고 어떤 컬럼을 가변으로 바꿀지는 실제 화면 기준
  판단이 필요해서(예: 시간/단위처럼 짧은 값은 고정, 품목명처럼 긴 텍스트는 가변) 담당자
  확인 후 진행하는 게 맞다고 판단함. 필요하면 말해주면 바로 적용함.

## 7. (해결됨, 6차) 헤더 마스터 토글 버튼 3개와 각 depth 그룹행 자체 토글 버튼 위치가 안 맞음

담당자 원문: "컬럼 헤더에 접기 버튼 3개, 그리고 각각 그룹화 1단계 2단계 3단계 행마다
하나씩 있지? 그거 위치를 맞춰야지."

- 원인: 헤더의 마스터 토글 버튼 3개는 체크박스 오른쪽의 한 블록에 나란히 모여 있었고,
  그룹행 자체의 펼침 버튼은 라벨 앞에 `paddingLeft: depth*20`으로 들여쓰기만 해서
  컬럼0(column0) 안에 떠 있었음 — 두 시스템이 서로 다른 좌표 기준을 쓰고 있어서 세로로
  안 맞았음.
- 수정: 헤더와 그룹행 둘 다 "폭 `MASTER_TOGGLE_SLOT_WIDTH`(24px)의 슬롯을 depth 수만큼
  나란히 배치"하는 동일한 구조로 통일. 헤더는 슬롯마다 실제 마스터 버튼을 넣고, 그룹행은
  자기 depth에 해당하는 슬롯에만 실제 펼침 버튼을 넣고 나머지 슬롯은 비워둠 — 그 결과
  그룹행의 펼침 버튼이 항상 헤더의 해당 depth 마스터 버튼과 정확히 같은 x 위치에 옴.
  그룹 라벨의 시각적 들여쓰기는 별도로 유지(`paddingLeft: depth*12`, 이제 라벨 전용).

## 8. (해결됨, 6차) 신규행 빨간 점이 체크박스 왼쪽에 있던 것

담당자 원문: "새로 추가한 경우 빨간 점 추가는 맞는데, 그거 위치가 지금 체크박스
왼쪽인데 체크박스 오른쪽으로."

- 원인: `absolute left-[13px]`로 행 자체의 왼쪽 padding 영역(체크박스보다 왼쪽)에
  절대 위치시켰던 것.
- 수정: 체크박스를 감싸는 래퍼(`pr-[12px]`로 이미 체크박스 오른쪽에 12px 여백이 있음)를
  `relative`로 만들고, 그 여백 안에 `absolute right-[3px]`로 점을 넣어서 체크박스
  오른쪽에 오도록 이동. 새 컬럼/스페이서를 예약할 필요가 없어서 다른 행 종류의 정렬에
  영향 없음.

## 9. (개선, 6차) 컬럼 정렬이 여전히 제멋대로로 보이던 문제 — 2건 원인 확인

담당자 원문: "여전히 컬럼들이 지금 뭐 좌측정렬 우측정렬이 지 멋대로야."

- 원인 1(구조적): `GroupHeaderRow`/`TotalsRow`의 라벨("지시일: ...", "총계")이 자기가
  속한 첫 번째 컬럼(column0)의 `align` 설정(예: 가운데)을 그대로 물려받아서, 라벨
  길이가 서로 다른 각 행마다 "컬럼 중앙 기준으로 시작 위치"가 매번 달라 보였음(예:
  "지시일: 2025-10-30" vs "설비: 성형기 1호" vs "담당기사: 김수현" — 길이가 다 달라서
  중앙 정렬하면 시작 x가 매번 다름) — 이게 "제멋대로"로 보이는 가장 큰 원인이었을
  가능성이 높음. 수정: 그룹 라벨/총계 라벨 셀은 컬럼 자체의 align 설정과 무관하게 항상
  좌측 고정(`{ ...col, align: "left" }`)으로 강제.
- 원인 2(데이터): 데모 컬럼 중 `equipment`(설비)만 유독 좌측 정렬이었고, 비슷한 성격의
  `manager`/`itemType`/`warehouse`는 전부 가운데 정렬이라 서로 안 맞았음. 수정:
  `equipment`도 가운데로 통일 — "링크 없는 짧은 값은 가운데, 자유 텍스트(품목명)만
  좌측, 숫자류만 우측"이라는 규칙을 페이지 주석에 명시적으로 다시 정리함.

## 10. (해결됨, 7차) 신규행 빨간 점 위치를 "체크박스 우측 10px"로 정확히 지정 + 숨어있던 정렬 버그 발견

담당자 원문: "빨간 점은 그 머냐 체크박스 우측으로 10px 떨어진 위치에 배치."

- 6차에서 이미 "체크박스 오른쪽"으로 옮기긴 했지만 정확히 몇 px 간격인지는 지정값이
  아니라 여백 크기에 얹혀가는 값이었음 → 체크박스 칼럼 전체를
  `CHECKBOX_COLUMN_WIDTH = 40`(체크박스 24 + 간격 10 + 점 6) 상수로 고정하고, 점은
  `left: 24 + NEW_DOT_GAP_FROM_CHECKBOX(10)`으로 명시적 배치.
- 이 작업 중 `TotalsRow`(총계행)의 체크박스 칼럼 자리 표시자가 `pr-[12px]` 클래스와
  명시적 `width: 24`를 함께 쓰고 있어서, border-box 특성상 실제로는 24px만 차지하고
  있었던(다른 행들은 명시적 width가 없어 체크박스 24 + padding 12 = 36px로 자동
  계산됨) **선행 버그를 발견**함. 6차례의 정렬 수정 동안 한 번도 지적되지 않았던
  숨은 불일치. 네 가지 행 종류(헤더/그룹행/데이터행/총계행) 전부
  `style={{ width: CHECKBOX_COLUMN_WIDTH }}`로 통일해서 해결.

## 11. (해결됨, 7차) 숫자 컬럼의 "헤더 라벨"까지 우측정렬되던 것 — 헤더는 항상 가운데로

담당자 원문: "테이블 내부가 공통정책으로 숫자는 우측정렬이잖아? 근데 그렇다고 그 숫자
컬럼명은 숫자가 아닌데 왜 우측정렬을 하는거야. 생산수량이 2000이라고 하면 2000은
우측정렬이 맞는데 맨 위에 '생산수량'이라고 적힌 헤더는 가운데정렬 쌔려야지."

- 원인: 헤더 셀이 데이터 셀과 동일하게 컬럼의 `align`을 그대로 물려받고 있어서, 숫자
  컬럼(`align: "right"`)의 헤더 라벨(텍스트)까지 우측정렬되고 있었음.
- 수정: 헤더 행의 `columns.map`에서 매 컬럼을 `{ ...col, align: "center" }`로 강제해서
  데이터 셀의 정렬 규칙과 분리. 데이터 셀(그룹행/데이터행/총계행)의 정렬은 기존 그대로
  컬럼별 `align`을 따름 — 숫자는 계속 우측정렬.

## 12. (해결됨, 7차) 숫자에 1000단위 콤마 추가

담당자 원문: "그리고 숫자에 100단위 콤마 넣어줘." (의도: 천 단위 구분 콤마)

- `page.tsx`의 `productionColumns` 중 `packCount`/`qty`/`defectQty`/`packQty`에
  `toLocaleString("ko-KR")` 기반 `render` 함수를 추가해서 데이터 행 값에 콤마 적용.
- 그룹 `summary` 집계값과 `totals` prop에 들어가는 숫자 리터럴에도 동일하게
  `fmt = (n: number) => n.toLocaleString("ko-KR")` 헬퍼를 적용해서, 데이터 행뿐 아니라
  집계/총계 행도 전부 콤마가 일관되게 보이도록 함.

## 13. (해결됨, 7차 후속) 창고명/품목구분 컬럼 제거로 데모 폭 축소

담당자 원문: "그리고 뭐 컬럼중에 필요없는컬럼 창고명 품목구분 이런거는 빼서 그냥 테이블
가로 너비를 좀 줄여줘봐 다른거랑 너무 안어울려서그래."

  같이 제거함(컴포넌트 `table.tsx` 자체는 변경 없음 — 데모 데이터/컬럼 구성만 조정).

## 15. (해결됨, 7차 후속) 합본 테이블 외에 구조 요소별 분리 데모 4종 추가

담당자 원문: "테이블 합본도 필요한데 테이블 컴포넌트 하나하나당 찢는것도 필요해.
예를들면, 헤더는? 그룹화는? 컬럼이 두개이상일경우는? 총계행은? 이거를 따로따로
보고싶을수도 있잖아."

- 기존 15개 컬럼짜리 합본 Table 데모는 그대로 유지.
- 그 아래에 별도 3컬럼(`근무조`/`담당기사`/`생산수량`)짜리 단순 데이터(`flatColumns`/
  `flatRows`/`miniGroups`)로 구성한 미니 데모 4개를 추가: (1) 헤더만(rows/groups/totals
  전부 없이 `columns`만 전달), (2) 그룹화만(1단 그룹, 총계행 없음), (3) 컬럼 2개 이상 +
  그룹화 없는 평범한 플랫 테이블(`rows`만 전달), (4) 총계행만(`rows`+`totals`).
- `Table`의 `groups`/`rows`/`totals`/`selectedIds`/`onSelectedIdsChange`가 전부
  optional이라는 걸 활용 — 컴포넌트 코드 변경 없이 데모 페이지 구성만으로 각 구조
  요소를 격리해서 보여줌.

## 16. (해결됨, 8차) 합본 Table 데모가 "시선강탈" — 기본 접힘 + 토글로 변경

담당자 원문: "테이블이 너무 시선강탈이야 테이블 자체를 그냥 아예 접었다폈다할수있게
숨겨줘 걍."

- 대상 범위는 담당자에게 직접 확인: 5개 Table 데모 블록(합본 1개 + 미니 데모 4개) 중
  화면을 가장 많이 차지하는 **합본 데모 1개만** 접기/펼치기 대상으로 하고, 미니 데모
  4개는 원래도 작아서 그대로 둠.
- `page.tsx`에 `productionTableOpen`(기본값 `false`, 즉 기본 접힘) state를 추가하고,
  합본 Table 섹션의 제목을 클릭 가능한 `<button>`으로 바꿔서 클릭할 때마다 펼침/접힘을
  토글. 펼쳐진 상태를 나타내는 시각 신호로 `lucide-react`의 `ChevronRight`를
  `productionTableOpen`이 true일 때 `rotate-90`(오른쪽→아래) 처리. 접힌 상태에서는
  설명 문단과 `<Table>` 자체를 렌더링하지 않아서(조건부 렌더, `display:none`이 아님)
  페이지 로드 시 불필요한 DOM/레이아웃 비용도 같이 줄임. 컴포넌트(`table.tsx`) 자체는
  변경 없음 — 데모 페이지 구성만 조정.
