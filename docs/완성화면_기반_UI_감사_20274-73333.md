이 문서는 클라우드 MES의 완성 화면 묶음을 기준으로 현재 코드 디자인 시스템이 실제 화면을 생성하기에 충분한지 감사한 결과다. 사람용 설명서이면서 동시에 AI가 화면 생성 전에 읽을 수 있는 구조화된 근거 문서다.

## 1. 이 자료의 사용 규칙

이 노드는 개별 컴포넌트 명세 페이지가 아니라 **완성 화면에서 컴포넌트가 실제로 조합된 결과**다. 따라서 다음 우선순위를 적용한다.

1. 화면 구조, 팝업 크기, 컴포넌트 조합, 액션 배치는 이 노드를 실제 사용 근거로 삼는다.
2. 버튼·입력창 같은 원자 컴포넌트의 내부 색상과 상태값은 전용 컴포넌트 명세를 우선한다.
3. 완성 화면에서 반복적으로 확인된 크기 차이는 임의 오버라이드로 버리지 않고 `variant` 또는 상위 패턴의 규칙으로 등록한다.
4. 같은 역할·같은 시각 언어인데 너비만 다른 버튼은 신규 버튼 컴포넌트로 만들지 않는다.
5. 화면마다 반복되는 조합은 원자 컴포넌트가 아니라 `pattern` 또는 `archetype`으로 등록한다.
6. Figma 캔버스에 비교용으로 나란히 놓인 두 팝업은 동시에 열리는 UI가 아니라 상태·방식의 대안 specimen으로 해석한다.

AI의 분류 결과는 다음 다섯 값 중 하나여야 한다.

```ts
type AuditDecision =
  | "reuse"          // 현재 코드 그대로 재사용
  | "extend"         // 기존 컴포넌트에 size/state/slot 추가
  | "refactor"       // 기존 API 구조를 실제 화면군에 맞게 수정
  | "create-pattern" // 기존 컴포넌트를 조합하는 화면 패턴 신규 등록
  | "create";        // 대체할 기존 컴포넌트가 없는 신규 컴포넌트
```

## 3. 팝업 크기 체계

완성 화면에서 확인된 팝업 폭은 임의값 모음이 아니라 콘텐츠 유형과 대응한다.

```yaml
overlay_sizes:
  center:
    compact-400: [production-quantity, work-time]
    compact-480: [item-detail, cancel-return]
    medium-600: [defect-quantity, receiving-quantity]
    standard-960: [label-confirm, bom-stock-analysis, weight-inspection]
    large-1100: [bulk-purchase]
    wide-1400: [cooler-checklist, bulk-shipment, bulk-work-order, material-lookup, shipping-history]
  side:
    narrow-760: [self-inspection, custom-information, operation-log]
    standard-900: [production-result, receiving-registration]
  anchored:
    column-settings-460: [table-column-settings]
```

현재 `CenterModal`은 960px, `SideSlidePanel`은 960px로 고정되어 있어 이 계약을 표현하지 못한다. `className`으로 화면마다 폭을 덮는 방식은 AI가 일관된 화면을 생성하기 어렵게 하므로 명시적 size prop이 필요하다.

권장 API 형태:

```ts
type CenterModalSize = "compact-400" | "compact-480" | "medium-600" |
  "standard-960" | "large-1100" | "wide-1400";

type SidePanelSize = "narrow-760" | "standard-900" | "legacy-960";

type DialogAction = {
  id: string;
  label: string;
  tone: "main" | "gray" | "black" | "danger" | "outline";
  width?: "content" | "fill" | 79 | 125 | 160 | 200 | 360;
};
```

높이는 콘텐츠가 결정하고 중앙 모달은 `max-height: 80vh`를 유지한다. 400·436·444·456 같은 specimen 높이를 각각 height variant로 만들지는 않는다.

## 4. 실제 인스턴스 사용 결과

### 4.1 Button

완성 화면에서 확인된 Button의 높이는 현재 코드와 같은 세 계열이다.

| 계열 | 높이 | 실제 예 | 결론 |
|---|---:|---|---|
| basic | 40 | 하단 취소/저장 160px, 주요 액션 200/360px | 기존 size 재사용 |
| small | 32 | 조회 50px, 설정/다운로드 67~91px, 적용 125px 등 | 기존 size 재사용 |
| xsmall | 22 | 테이블 내부 Tag/소형 액션과 조합 | 기존 size 재사용 |

확인된 tone은 `fillMain`, `fillGray`, `fillBlack`, `lineMain`, `lineBlacktxt`, `opacityMain`, disabled다. 새로운 색상 버튼은 발견되지 않았다.

**결론:** 버튼 너비 50·67·69·79·82·91·125·160·165·200·360을 각각 variant로 만들지 않는다. Button은 현재 컴포넌트를 재사용하고 폭은 Modal action 또는 Toolbar slot의 레이아웃 계약이 소유한다.

### 4.2 Input/Select/Search

- 기본 입력 높이: 32px
- 테이블 내부 소형 입력 높이: 22px
- `textbox`, `selectbox`, `search`, `search-white`, `textbox-label`, `selectbox-label`, `textbox-icon` 사용 확인
- readonly/default/입력완료/disable 상태 확인
- Search는 대부분 200×32지만 한 화면에서 327×32 사용 확인

`Input`과 `Select`의 size 체계는 재사용한다. `SearchInput`의 현재 200px 고정폭은 기본값으로 유지하되 `width="fill"` 또는 명시적 layout slot 폭을 허용해야 한다.

### 4.3 선택 컨트롤

| 컴포넌트 | 완성 화면 실측 | 현재 코드 | 판정 |
|---|---|---|---|
| Checkbox | 주로 24×24, 일부 20×20 | 24×24 고정 | `extend`: 20/24 size |
| Radio | 20×20과 24×24 모두 사용 | 24×24 고정 | `extend`: 20/24 size |
| Switch/Toggle | 12개 모두 40×20 | 44×24 판단값 | `refactor`: 기본을 40×20 실측값으로 교체 |

### 4.4 Tag

기본 Tag는 높이 22px이며 `fill-main`, `fill-gray`, `fill-red`가 확인됐다. 추가로 `opacity main` 62×18 specimen 2개가 확인됐다.

- 기존 main/gray/red: 재사용
- `opacityMain` + compact 18px: variant 추가
- Figma의 `fill-gray`/`fill_gray` 표기 차이는 코드에서 하나의 `gray`로 정규화

### 4.5 Icon

현재 코드에 이미 있는 주요 아이콘: arrow, calendar, trash, x, plus, group-down, bell, 검사 ○/△/×, exclamation, reload, trend, flat status, x-circle.

완성 화면에서 확인됐지만 전용 React 아이콘이 없는 항목:

- printer
- dots-six-vertical / drag handle
- calculator
- eye-on-mono
- setting의 MES 원본 벡터
- `icon-24-left`라는 불명확한 12px 인스턴스

Lucide 임시 아이콘이 있는 항목도 Registry에서는 `judgement`가 아니라 `missing-asset`으로 기록하고, 실제 Figma 벡터를 확보한 뒤 교체한다.

## 6. ScreenSpec에 추가할 구조

완성 화면을 AI가 안정적으로 생성하려면 `ScreenSpec`이 JSX className이 아니라 의미를 가져야 한다.

```ts
type ScreenSpec = {
  schemaVersion: 1;
  archetype:
    | "entity-list"
    | "master-detail"
    | "dashboard"
    | "side-record-editor"
    | "lookup-selection-dialog"
    | "inspection-dialog"
    | "quantity-entry-dialog";
  navigation?: { collapsed: boolean };
  query?: {
    dateRange?: boolean;
    groupingLevels?: number;
    filter?: boolean;
    search?: { width: 200 | "fill" };
  };
  table?: {
    selectable?: boolean;
    groupingDepth?: number;
    headerRows?: number;
    editable?: boolean;
    tree?: boolean;
    progressCells?: boolean;
    columnSettings?: boolean;
  };
  overlay?: {
    kind: "center" | "side" | "anchored";
    size: CenterModalSize | SidePanelSize | "column-settings-460";
    contentPattern: string;
    actions: DialogAction[];
  };
};
```

금지 규칙:

- 화면 생성 코드에 `w-[1400px]` 같은 값이 직접 등장하면 안 된다. Registry의 modal size를 사용한다.
- `조회/설정/다운로드` 조합을 개별 화면에서 새로 만들면 안 된다. `QueryToolbar` slot으로 선언한다.
- 동일한 테이블을 펼침/접힘 상태 때문에 두 화면 컴포넌트로 복제하면 안 된다.
- modal specimen 두 개가 한 캔버스에 있다는 이유로 동시에 렌더링하면 안 된다.
- Button의 고정 너비 차이를 새로운 Button variant로 등록하면 안 된다.

## 7. 발견된 Figma 정리 이슈

이 항목들은 코드에 그대로 옮기지 않는다.

1. `11210:52919` 불량수량 팝업은 캔버스 내부 좌표가 `x=-2193, y=3125`로 화면 밖에 있다. 크기 600×400과 내부 구성은 유효하지만 위치는 Figma 편집 오류로 취급한다.
2. `11210:52829` 취소/반품과 `11210:52992` 생산수량 입력은 한 캔버스에 두 specimen이 나란히 있다. 상태 예시이지 동시 overlay가 아니다.
3. `tag` 속성명이 `fill-gray`와 `fill_gray`로 혼재한다. Registry에서는 `gray` 하나로 정규화한다.
4. `정보유형 팝업` 캔버스의 상위 제목과 내부 `커스텀 정보 등록` 제목은 2-depth 흐름을 보여준다. 별도 “중첩 모달 컴포넌트”는 만들지 않고 기존 overlay stack으로 처리한다.
