# 모바일·웹 대응 및 조합 규칙

## 핵심 원칙

웹과 모바일은 업무 의미를 공유하지만 동일한 화면 패턴을 공유한다고 가정하지 않는다. `입고등록`이라는 이름이 같아도 웹에서는 SideSlidePanel, 모바일에서는 날짜 리스트 → 등록 상세 → 하단 팝업의 흐름일 수 있다.

## AI 선택 순서

1. 업무 의도와 사용자 행동을 선택한다.
2. 플랫폼을 `web` 또는 `mobile`로 고정한다.
3. 모바일이면 `main-list`, `detail-form`, `quality-step`, `bottom-sheet`, `full-search` 중 셸을 고른다.
4. 화면 유형 보드에서 같은 성격의 기존 화면을 찾는다.
5. 운영 화면에서 섹션 순서·콘텐츠·상태·예외를 확인한다.
6. 모바일 컴포넌트 registry에서 필요한 component ID를 선택한다.
7. 원본과 충돌하는 고립값은 임의 정규화하지 않고 네 가지 분류 중 하나로 기록한다.

## 금지

- 웹 `Button`, `Input`, `SideSlidePanel`에 작은 class를 덧붙여 모바일 자산으로 부르지 않는다.
- 모바일 표 대신 웹 Table을 가로 스크롤로 넣지 않는다.
- Bottom Sheet를 중앙 모달로 바꾸지 않는다.
- 화면 이름만 같다는 이유로 웹과 모바일의 섹션 순서를 복사하지 않는다.
- Figma 레이어명을 업무 의미보다 우선하지 않는다. 복사된 잘못된 이름이 존재한다.
- 개발범위 제외·미진행 결정을 활성 생성 근거로 사용하지 않는다.

## 공유 가능한 것과 분리할 것

공유 가능: 색의 의미, 필수값, 선택 상태, 저장·취소 의미, 데이터 검증, 업무 용어, API 계약.

분리: viewport, navigation, shell, list/table 표현, 입력 overlay, CTA 위치, safe area, 터치 크기, 단계 분할.

## 신규 화면 생성 판정

기존 모바일 화면 유형으로 표현 가능하면 같은 pattern을 재사용한다. 표현할 수 없는 이유가 업무 흐름·정보 위계·상호작용 차이로 입증될 때만 `propose-new`로 격리한다. 단순한 콘텐츠명·필드 수·간격 차이는 새 패턴 근거가 아니다.
