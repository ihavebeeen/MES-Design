# 디자인 시스템 레지스트리 및 시각 회귀 테스트

> AI 조합 계층의 공통 기준은 [AI UI 조합 문법 공통 정책](./AI_UI_조합_문법_공통정책.md)이다. 화면 레지스트리의 복수 `patternRefs` 이관은 완료됐다.

## 목적

화면 구현 전에 AI와 개발자가 기존 컴포넌트와 패턴을 먼저 조회하도록 강제하고, 대표 화면의 시각적 변경을 자동으로 감지한다.

레지스트리는 설명 문서의 복사본이 아니다. 다음 연결 관계를 코드가 검사하는 기준 데이터다.

```text
Screen → ContextDecision → PatternDecision → Pattern[] (shell/content/behavior) → Component → Source file
```

## 파일 구조

```text
component-library/
├─ src/design-system/registry/
│  ├─ components.json          # 활성 UI 컴포넌트 1:1 등록
│  ├─ patterns.json            # 합성 패턴과 필수 컴포넌트
│  ├─ screens.json             # 실제 MES 화면과 패턴 연결
│  ├─ visual-regression.json   # 시각 회귀 대표 사례
│  ├─ source-evidence.json      # 제공받은 Figma 원본과 화면별 품질 게이트
│  ├─ generated-screen-evaluations.json # AI 생성 시안의 평가와 표준 영향 격리
│  ├─ context-rules.json       # 의미 역할·부모 맥락에 따른 선택·제외 조건
│  ├─ registry.types.ts        # 레지스트리 타입
│  └─ index.ts                 # 조회 함수
├─ scripts/
│  ├─ check-pattern-component-reuse.mjs
│  └─ check-design-system-registry.mjs
├─ src/app/visual-regression/  # 실제 컴포넌트를 렌더링하는 테스트 전용 경로
├─ tests/visual/               # Playwright 테스트
└─ playwright.config.ts
```

## AI 구현 절차

새 화면을 만들거나 수정할 때 다음 순서를 지킨다.

1. `screens.json`에서 동일하거나 가장 가까운 화면을 찾는다.
2. `context-rules.json`으로 헤더·팝업·액션·입력·경계·테이블·스크롤의 의미 역할, 부모 맥락, 업무 구조와 사용 제외 조건을 판정한다.
3. 현재 `patternRefs`와 가장 가까운 shell·section·behavior·action-set 후보를 `patterns.json`에서 조회한다.
4. 후보의 `requiredComponents`를 `components.json`에서 조회하고 실제 source와 rules를 읽는다.
5. 기존 조합과 요구사항의 차이를 `reuse`, `compose`, `extend`, `propose-new`, `normalize` 중 하나로 판정한다.
6. `extend`와 `propose-new`는 사용자 승인 전 표준 레지스트리에 반영하지 않는다.
7. 기존 컴포넌트의 props로 해결되지 않는 차이만 optional prop 또는 variant로 확장한다.
8. 패턴 파일에서 raw `button`, `input`, `select`, `table`, `a`를 만들지 않는다.
9. TypeScript, ESLint, 레지스트리 검사, 패턴 조합 검사와 시각 회귀 테스트를 실행한다.

현재 `screens.json`은 화면마다 복수 `patternRefs`를 가지며 Shell·Section·Behavior·ActionSet을 함께 참조한다. 기존 popup/screen/table 크기의 항목은 Recipe 호환 계층으로 남아 있을 수 있지만, 화면 전체를 규정하는 1:1 템플릿으로 해석하지 않는다.

새 원본은 구현 화면 레지스트리에 곧바로 섞지 않고 `source-evidence.json`에 먼저 등록한다. 각 원본은 다음 여섯 게이트를 화면 단위로 통과해야 `verified`가 된다.

AI 생성 결과도 자동으로 `screens.json`이나 `patterns.json`에 넣지 않는다. 먼저 `generated-screen-evaluations.json`에 등록하고 `/generated-screens/`에서 생성일, 사용자 점수, 잘한 점, 못한 점, 승격 조건을 검토한다. `approved`가 아니면 `influence: quarantined`로 유지하여 다음 AI 생성의 근거에서 제외한다.

1. `designContext`: 대상 node와 필요한 하위 node를 `get_design_context`로 조회함
2. `metadataLedger`: 외곽부터 내부까지 좌표·크기 장부를 확인함
3. `componentMapping`: 기존 컴포넌트와 신규 확장 필요 여부를 매핑함
4. `browserMeasurement`: 실제 DOM 크기와 overflow를 브라우저에서 측정함
5. `interactionTest`: 선택·입력·추가·삭제·취소 복원 상태를 조작함
6. `visualBaseline`: 원본 기준 viewport의 PNG를 직접 확인하고 고정함

`verified`인데 하나라도 `false`이거나 시각 회귀 case가 없으면 `check:registry`가 실패한다. 따라서 코드만 그려 놓고 완료 처리하거나, 현재 렌더를 확인하지 않은 채 기준 이미지를 추가할 수 없다.

TypeScript 코드에서는 신규 생성 전체 맥락과 기존 화면 구현 맥락을 각각 조회할 수 있다.

```ts
import {
  getGenerationContext,
  getImplementationContext,
} from "@/design-system/registry";

const generation = getGenerationContext();
const context = getImplementationContext("material-input-settings");
```

반환값에는 화면 규칙, 패턴 규칙, 필수 컴포넌트의 source와 사용 규칙, 연결된 Context Rule·Decision과 전역 선택 게이트가 함께 들어 있다. 화면 ID가 없는 신규 생성은 `getContextDecision("select.overlay-shell")`과 `getContextDecision("select.heading-context")`를 먼저 조회한다.

## 자동 검사

```bash
cd component-library
npm run check:design-system
npx tsc --noEmit
npm run lint:design-system
npm run test:visual
```

`npm run lint:design-system`은 레지스트리·패턴 변경 범위를 빠르게 검사하고, 최종 커밋 전에는 전체 `npm run lint`도 통과해야 한다.

`check:registry`가 실패하는 경우는 다음과 같다.

- `src/components/ui/*.tsx`에 파일을 추가하고 `components.json`에 등록하지 않음
- 레지스트리 source 경로가 실제 파일과 다름
- 패턴이 등록되지 않은 컴포넌트를 참조함
- 화면이 등록되지 않은 패턴을 참조함
- 화면 코드가 선택한 shell·content·behavior 조합과 PatternDecision이 일치하지 않음
- 미승인 `extend` 또는 `propose-new`가 표준 패턴·화면 레지스트리에 유입됨
- 시각 회귀 사례가 등록되지 않은 화면 또는 패턴을 참조함
- 대표 popup 또는 table 시각 사례가 사라짐

## 시각 회귀 기준

현재 대표 기준은 다음 두 계열이다.

| 기준 | 검출 대상 |
|---|---|
| 투입품목 설정/조회 | 1400×800 중앙 팝업, 탐색 레일, 조회 toolbar 정렬, 선택 행, 입력 영역, 결과 테이블, footer |
| 그룹화 테이블 | 선택/부분선택 체크박스, 선택 행 배경, 2단 그룹, 신규 행 표시, 컬럼 정렬, 총계 |

테이블 행을 직접 선택한 뒤 찍는 상호작용 기준 이미지도 별도로 유지한다.

## 의도한 디자인 변경 시

기준 이미지는 테스트를 통과시키기 위해 무조건 갱신하면 안 된다. 브라우저에서 변경 결과를 확인한 뒤 의도한 변경일 때만 다음 명령을 실행한다.

```bash
npm run test:visual:update
npm run test:visual
```

커밋 전에 변경된 PNG를 직접 열어 원본 기준과 비교한다.

## 항목 추가 규칙

- 새 UI 컴포넌트: `components.json`에 source, status, category, rules를 등록한다.
- 새 사용 맥락: `context-rules.json`에 의미 역할, 허용 부모, 사용·제외 조건, 관계와 구현 참조를 등록한다.
- 새 합성 방식: 기존 패턴의 재사용·조합·확장 가능성을 먼저 기록하고, 사용자 승인을 받은 신규 행동·상태·정보 위계만 `patterns.json`에 추가한다.
- 새 MES 화면: `screens.json.patternRefs`에 shell·section·behavior·action-set 조합 근거를 기록한다. 화면과 pattern을 1:1로 강제하지 않는다.
- 새 Figma 원본: 구현 전 `source-evidence.json`에 정규화 대상과 여섯 품질 게이트를 등록한다.
- 대표성이 높은 새 팝업/테이블: `visual-regression.json`, 테스트 경로, Playwright spec, 기준 PNG를 함께 추가한다.

Figma 전체 URL은 레지스트리에 저장하지 않는다. 필요한 경우 원본 대조 키로 node ID만 기록한다.
