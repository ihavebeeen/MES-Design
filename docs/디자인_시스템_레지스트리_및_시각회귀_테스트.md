# 디자인 시스템 레지스트리 및 시각 회귀 테스트

## 목적

화면 구현 전에 AI와 개발자가 기존 컴포넌트와 패턴을 먼저 조회하도록 강제하고, 대표 화면의 시각적 변경을 자동으로 감지한다.

레지스트리는 설명 문서의 복사본이 아니다. 다음 연결 관계를 코드가 검사하는 기준 데이터다.

```text
Screen → Pattern → Component → Source file
```

## 파일 구조

```text
component-library/
├─ src/design-system/registry/
│  ├─ components.json          # 활성 UI 컴포넌트 1:1 등록
│  ├─ patterns.json            # 합성 패턴과 필수 컴포넌트
│  ├─ screens.json             # 실제 MES 화면과 패턴 연결
│  ├─ visual-regression.json   # 시각 회귀 대표 사례
│  ├─ source-evidence.json      # 제공받은 Figma 원본과 화면별 품질 게이트
│  ├─ registry.types.ts        # 레지스트리 타입
│  └─ index.ts                 # 조회 함수
├─ scripts/
│  ├─ check-pattern-component-reuse.mjs
│  └─ check-design-system-registry.mjs
├─ src/app/visual-regression/  # 실제 컴포넌트를 렌더링하는 테스트 전용 경로
├─ tests/visual/               # Playwright 테스트
└─ playwright.config.ts
```

## AI 구현 절차

새 화면을 만들거나 수정할 때 다음 순서를 지킨다.

1. `screens.json`에서 동일하거나 가장 가까운 화면을 찾는다.
2. 연결된 `patternId`를 `patterns.json`에서 조회한다.
3. `requiredComponents`를 `components.json`에서 조회하고 실제 source와 rules를 읽는다.
4. 기존 컴포넌트의 props로 해결되지 않는 차이만 optional prop 또는 variant로 확장한다.
5. 패턴 파일에서 raw `button`, `input`, `select`, `table`, `a`를 만들지 않는다.
6. TypeScript, ESLint, 레지스트리 검사, 시각 회귀 테스트를 실행한다.

새 원본은 구현 화면 레지스트리에 곧바로 섞지 않고 `source-evidence.json`에 먼저 등록한다. 각 원본은 다음 여섯 게이트를 화면 단위로 통과해야 `verified`가 된다.

1. `designContext`: 대상 node와 필요한 하위 node를 `get_design_context`로 조회함
2. `metadataLedger`: 외곽부터 내부까지 좌표·크기 장부를 확인함
3. `componentMapping`: 기존 컴포넌트와 신규 확장 필요 여부를 매핑함
4. `browserMeasurement`: 실제 DOM 크기와 overflow를 브라우저에서 측정함
5. `interactionTest`: 선택·입력·추가·삭제·취소 복원 상태를 조작함
6. `visualBaseline`: 원본 기준 viewport의 PNG를 직접 확인하고 고정함

`verified`인데 하나라도 `false`이거나 시각 회귀 case가 없으면 `check:registry`가 실패한다. 따라서 코드만 그려 놓고 완료 처리하거나, 현재 렌더를 확인하지 않은 채 기준 이미지를 추가할 수 없다.

TypeScript 코드에서는 다음과 같이 화면 구현 컨텍스트를 한 번에 조회할 수 있다.

```ts
import { getImplementationContext } from "@/design-system/registry";

const context = getImplementationContext("material-input-settings");
```

반환값에는 화면 규칙, 패턴 규칙, 필수 컴포넌트의 source와 사용 규칙이 함께 들어 있다.

## 자동 검사

```bash
cd component-library
npm run check:design-system
npx tsc --noEmit
npm run lint:design-system
npm run test:visual
```

전체 저장소 `npm run lint`에는 이번 변경과 무관한 기존 예제 페이지 lint 문제가 남아 있다. 레지스트리 자동 검사는 우선 이번 구조와 테스트 코드의 lint를 `lint:design-system`으로 차단하며, 전체 lint 문제는 별도 정리한다.

`check:registry`가 실패하는 경우는 다음과 같다.

- `src/components/ui/*.tsx`에 파일을 추가하고 `components.json`에 등록하지 않음
- 레지스트리 source 경로가 실제 파일과 다름
- 패턴이 등록되지 않은 컴포넌트를 참조함
- 화면이 등록되지 않은 패턴을 참조함
- 시각 회귀 사례가 등록되지 않은 화면 또는 패턴을 참조함
- 대표 popup 또는 table 시각 사례가 사라짐

## 시각 회귀 기준

현재 대표 기준은 다음 두 계열이다.

| 기준 | 검출 대상 |
|---|---|
| 투입품목 설정/조회 | 1400×800 중앙 팝업, 탐색 레일, 조회 toolbar 정렬, 선택 행, 입력 영역, 결과 테이블, footer |
| 그룹화 테이블 | 선택/부분선택 체크박스, 선택 행 배경, 2단 그룹, 신규 행 표시, 컬럼 정렬, 총계 |

테이블 행을 직접 선택한 뒤 찍는 상호작용 기준 이미지도 별도로 유지한다.

## 의도한 디자인 변경 시

기준 이미지는 테스트를 통과시키기 위해 무조건 갱신하면 안 된다. 브라우저에서 변경 결과를 확인한 뒤 의도한 변경일 때만 다음 명령을 실행한다.

```bash
npm run test:visual:update
npm run test:visual
```

커밋 전에 변경된 PNG를 직접 열어 원본 기준과 비교한다.

## 항목 추가 규칙

- 새 UI 컴포넌트: `components.json`에 source, status, category, rules를 등록한다.
- 새 합성 방식: 기존 패턴으로 표현할 수 없을 때만 `patterns.json`에 추가한다.
- 새 MES 화면: `screens.json`에서 반드시 하나의 pattern에 연결한다.
- 새 Figma 원본: 구현 전 `source-evidence.json`에 정규화 대상과 여섯 품질 게이트를 등록한다.
- 대표성이 높은 새 팝업/테이블: `visual-regression.json`, 테스트 경로, Playwright spec, 기준 PNG를 함께 추가한다.

Figma 전체 URL은 레지스트리에 저장하지 않는다. 필요한 경우 원본 대조 키로 node ID만 기록한다.
