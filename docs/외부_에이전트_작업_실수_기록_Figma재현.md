# 외부 AI 에이전트(Cowork/Claude)가 이 리포 기반으로 화면을 만들 때 지킬 것

## 0. 배경

2026-08-05, Cowork(Claude) 에이전트가 이 리포(MES-Design)의 실측 스펙을 참고해서
"품목별 생산량 관리" 화면을 (1) HTML 목업 → (2) Figma 새 파일 순서로 만드는 작업을
진행했다. Figma 1차 결과물이 리포의 실측값과 다르게 나온 것을 담당자가 지적했고,
그 원인 분석과 재발 방지 절차를 기록한다. `AGENTS.md`가 "이 리포 안에서" 작업하는
에이전트의 규칙이라면, 이 문서는 "이 리포를 참고해서 리포 밖(Figma 등)에 결과물을
만드는" 에이전트가 추가로 지켜야 할 규칙이다.

## 1. 무엇이 틀렸었나 (1차 Figma 결과물)

| 항목 | 리포의 실측값 | 1차로 실제 사용한 값 |
|---|---|---|
| 폰트 | Pretendard (globals.css, public/fonts) | Inter (확인 없이 임의 사용) |
| 아이콘 | icon-x.tsx/icon-search.tsx/icon-reload.tsx/icon-filter.tsx의 실제 SVG path | 유니코드 글자(✕, ⟳)로 대체 |
| 테이블 행 높이 | table.tsx 주석: "행 높이 30px(헤더/그룹행/일반행/총계행 전부 동일)" | 34px(품목 리스트), 40px(설비 리스트, 인풋 수용 목적으로 임의 확대) |

## 2. 왜 틀렸나 (원인 분석)

- **색상/radius/spacing처럼 파일에서 그대로 복붙 가능한 hex·px 값은 정확히 옮겼다.**
  반면 폰트 패밀리·아이콘 벡터처럼 "별도로 찾아서 가져와야 하는 자산"은 확인 절차
  없이 흔히 쓰는 대체값(Inter, 유니코드 글자)으로 편의상 채웠다. 즉 "복붙 가능한
  값"과 "탐색이 더 필요한 값"에 대해 검증 강도가 서로 달랐던 것이 1차 원인.
- **테이블 행 높이는 이미 읽었고, 담당자에게 직접 "30px로 명시돼 있다"고 설명까지
  했던 값**인데도, 실제로 Figma 코드를 작성하는 시점에 다시 대조하지 않고 눈대중
  숫자(34/40)를 썼다. 데이터가 없어서가 아니라 "그 순간에 다시 확인하지 않은 것"이
  직접 원인 — 대화 맥락에 있던 값을 코드 작성 시점까지 이어서 참조하지 못했다.
- **공통 원인**: "일단 그럴듯하게 완성된 화면을 빨리 보여주는 것"을 우선 목표로
  삼아서, 값 하나하나에 대해 "이게 어느 파일 어느 줄에서 나온 값인가"를 확인하는
  절차를 생략했다. `AGENTS.md` 5번 원칙("값 하나당 실측 하나가 원칙, 임의로 다른
  값 유추해서 채우지 않는다")을 이 리포 자체에는 적용하면서, 이 리포를 참고 자료로
  쓰는 바깥 작업에는 같은 원칙을 적용하지 않았다.

## 3. Pretendard가 Figma에서 왜 안 되는가 (GitHub과는 무관)

- 이 리포의 Pretendard는 `component-library/public/fonts/*.otf`를 `@font-face`로
  **자체 호스팅한 웹 폰트**다. Next.js 앱(브라우저)에서만 인식되고, OS에 설치된
  시스템 폰트가 아니다.
- Figma(와 이를 조작하는 MCP 툴)가 "사용 가능한 폰트 목록"을 가져오는 기준은
  **Figma 클라이언트가 실행 중인 컴퓨터에 실제로 설치된 시스템 폰트 목록**이다.
  GitHub 저장소에 otf 파일이 들어있다는 사실 자체는 Figma 쪽에 아무 영향을 주지
  않는다 — "GitHub에서 뭘 더 해야 하는" 문제가 아니라 로컬 OS 설치 문제다.
- 해결하려면: `component-library/public/fonts` 안의 otf 8종(ExtraLight~Black)을
  더블클릭해서 **로컬 OS 폰트로 설치** → Figma 재시작. 그러면 그 다음부터 Figma
  폰트 목록에 Pretendard가 나타난다.
- 이번 세션에서는 이 설치가 안 되어 있는 상태였고(`listAvailableFontsAsync` 조회
  결과 0건), 대안으로 이 환경에서 실제 존재가 확인된 한글 폰트 중 Noto Sans KR로
  대체했다. 완전한 대체는 아니다 — 특히 Pretendard SemiBold(600)에 대응하는 굵기가
  Noto Sans KR엔 없어서(Regular/Medium/Bold/Black만 존재) Medium으로 다운시프트
  했다. Pretendard 설치 후 Figma에서 전체 텍스트를 선택해 폰트만 일괄 교체하면
  정확한 값으로 바꿀 수 있다.

## 4. 재발 방지 — 가벼운 버전 (2026-08-05 수정: 최초 버전이 매번 표를 만들고
4단계를 거치는 무거운 절차라 담당자가 "토큰/노력 낭비 아니냐" 지적 → 아래로 대체)

핵심 원인은 "확인을 안 하고 넘어간 것" 하나였다. 그러니 대책도 매번 문서화하는
무거운 절차가 아니라, 이미 하는 작업 흐름 안에서 습관 하나만 지키면 된다:

1. 리포를 읽다가 나중에 쓸 구체적인 값(폰트명, 행 높이, 아이콘 파일 경로 등)을
   발견하면, 그 즉시 원문 그대로 메모해 둔다(새로 만드는 문서 말고, 그냥 그 값을
   찾은 시점의 결과에 남겨두면 됨). 코드를 쓸 때는 그 메모를 복붙하지, 기억으로
   다시 쓰지 않는다. → 이번 실수(30px를 알면서도 34/40을 씀)는 이 습관 하나로
   막을 수 있었다.
2. 폰트 설치 여부처럼 "된다/안 된다"가 명확히 갈리는 것은 작업 시작 전에 **딱 한
   번만** 확인한다(반복 확인 불필요, 값 하나하나 표로 만들 필요도 없음).
3. 확인 결과 대체값을 써야 했다면, 결과물을 내놓을 때 한 줄로 바로 밝힌다
   ("Pretendard 대신 Inter 사용 — 확인 안 함" 처럼). 지적받은 뒤에 설명하지 않는다.

표를 만들고 추출·확인·빌드·검증 4단계를 거치는 무거운 방식은 이번처럼 사고 원인을
기록해 두는 회고 문서에서나 쓸 것 — 화면 하나 만들 때마다 반복할 절차는 아니다.
정말 크고 리스크 큰 작업(컴포넌트 라이브러리 자체를 실측하는 작업 등)에서만
선택적으로 표 형태를 쓴다.

## 5. Pretendard 관련 최종 결론 (2026-08-05, 최초 진단이 틀렸음을 정정)

최초에는 "OS에 폰트로 설치가 안 되어 있을 것"이라고 추측했는데, 담당자가 Figma의
Fonts 검색창에서 "Installed by you" 아래 Pretendard가 정상적으로 뜨는 스크린샷을
보여줘서 이 추측이 틀렸다는 게 확인됨.

실제 원인은 다른 데 있었다: `figma.loadFontAsync({family:"Pretendard", ...})`를
이 자동화 툴(use_figma의 Plugin API 실행 환경)에서 직접 호출해보면 다음 에러가
난다 —

```
The font "Pretendard Regular" could not be loaded. The font family "Pretendard" does not exist.
...
To upload a local font, see: https://help.figma.com/hc/articles/360039956894-Add-a-font-to-Figma
```

즉 **로컬 OS 설치 여부와 무관하게, 이 자동화 실행 환경은 Figma가 자체 호스팅하는
폰트 목록(구글 폰트 등) + 파일에 별도로 "업로드"된 로컬 폰트만 로드할 수 있고,
순수 OS 설치 폰트는 애초에 접근 대상이 아니다.** 담당자가 Figma 데스크탑 앱에서
텍스트 도구로 직접 타이핑할 때 Pretendard가 보이는 것은 Figma 앱이 그 순간
로컬 렌더링을 하기 때문이고, 스크립트로 노드를 만들고 폰트를 지정하는 것과는
별개의 경로다.

**결론**: 이 종류의 작업(자동화 스크립트로 폰트 지정)에서 Pretendard 같은
로컬 전용 폰트는 애초에 자동으로 적용할 수 없다. 해결책은 둘 중 하나뿐:
(a) 담당자가 Figma에서 직접 전체 텍스트를 선택해 폰트를 Pretendard로 교체하거나,
(b) Figma의 "Add a font to Figma" 기능으로 파일에 폰트를 업로드해서 자동화 툴도
접근 가능한 상태로 만드는 것(플랜에 따라 지원 여부 다름, 미확인).
자동화 쪽에서는 매번 Noto Sans KR 등 대체 폰트로 만들고, 폰트 교체는 담당자
쪽 작업으로 넘기는 게 현실적이다.

## 6. 이 문서대로 해도 또 다른 문제가 생길 수 있다 — 그때를 위한 원칙

이 문서는 2026-08-05에 실제로 벌어진 실수(폰트/아이콘/행높이)만 근거로 쓴 것이라,
여기 안 적힌 종류의 문제는 못 막는다. 다음에 만나는 문제가 이 문서에 있는 것과
비슷하지 않다면 아래 원칙으로 대응한다:

1. **모르면 넘겨짚지 말고 멈춰서 확인하거나 물어본다.** 이 문서에 없는 상황을
   만났다고 해서 "이 정도면 되겠지"로 판단해 채우지 않는다 — 그게 애초에 이번
   사고의 원인이었다. 확인 방법이 있으면 확인하고, 확인 방법이 없거나 담당자만
   답할 수 있는 판단(예: 어떤 값이 맞는지, 어느 쪽으로 대체할지)이면 작업을
   멈추고 먼저 물어본다.
2. **대체값·판단값을 썼다면 결과물과 함께 반드시 먼저 밝힌다.** "이건 확인 못 해서
   OO로 대신했다"는 한 줄이 없으면, 담당자 입장에선 실측인지 대체값인지 구분할
   방법이 없다 — 이번 사고도 그 한 줄이 없어서 나중에야 드러났다.
3. **이 문서는 고정된 규칙집이 아니라 계속 갱신되는 기록이다.** 새로운 종류의
   실수가 발견되면(이번처럼 폰트/아이콘/행높이가 아닌 다른 것), 이 문서에 새
   사례로 추가한다 — 기존 항목을 지우지 않고 이어 붙이는 방식(이 리포
   `AGENTS.md`의 "Table 작업 회고" 섹션과 같은 방식).

2026-08-05 추가 — 이 문서는 "리포 밖에 결과물을 만들 때"로 범위가 좁은데, 여기서
발견된 패턴(확인 안 된 걸 확인됐다고 단정 등)이 리포 안 작업(예: 페이지 라우팅
리팩터링)에서도 똑같이 반복되는 걸 확인해서, 범위를 넓힌 자매 문서
`docs/AI_에이전트_구조적_한계_기록.md`를 새로 만들었다. 특정 결과물(Figma 재현) 관련
디테일은 이 문서에, AI 에이전트 전반의 구조적 패턴은 그쪽에 정리한다.
