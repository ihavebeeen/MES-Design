# 웹 UI 맥락 체계화 현황

## 결론

웹 컴포넌트와 대표 패턴은 상당 부분 모였고, 2026-08-24 배치에서 핵심 자산의 사용 계약, 패턴 슬롯·상태 계약, 대표 화면의 순서형 명세와 결정 추적까지 구현했다. 이제 대표 3개 구조에서는 **“AI가 어느 화면의 어느 위치에 왜 이 자산을 쓰는가”를 기계가 설명하고 감사할 수 있다.** 다만 이 계약이 전체 28개 화면과 88개 컴포넌트에 동일한 깊이로 확장된 상태는 아니다.

현재 수준을 나누면 다음과 같다.

| 영역 | 현재 판단 | 근거 |
|---|---|---|
| 자산 인벤토리 | 강함 | 컴포넌트 88개와 패턴 62개가 레지스트리에 등록됨 |
| 화면-패턴 연결 | 기본 구조 있음 | 화면 28개가 모두 `patternRefs`와 상태 규칙을 가짐 |
| 공통 맥락 규칙 | 기본 구조 있음 | 활성 규칙 34개, 공통 결정 7개, 보류 0개 |
| 컴포넌트 선택 계약 | 핵심 범위 구현 | 오류가 반복된 핵심 20개 자산이 명시적 사용·금지·부모·상태·제약·대안 계약을 가짐 |
| 패턴 조합 계약 | 핵심 범위 구현 | 핵심 10개 Shell·Section·Behavior가 슬롯·상태·스크롤·action set 계약을 가짐 |
| 화면 내부 조합 순서 | 대표 3종 구현 | 우측 슬라이드, 중앙 검색 테이블, 페이지 그룹 목록은 순서형 ScreenSpec을 가짐. 나머지 25개는 기존 평면 참조 유지 |
| 선택 근거·감사 | 구현됨 | Resolver `decisionTrace`와 섹션 ID·순서·marker·action set 구현 감사 연결 |
| 자동 생성 | 확장 파일럿 | 결정형 생성 템플릿 3종: stable 2종, provisional 1종 |
| 원본·동작 검증 연결 | 부분적 | 28개 화면 모두 상호작용 감사가 있으나, 화면 ID에 직접 연결된 시각 회귀 사례는 21개 |
| 실제 웹 사용 맥락 | 관찰 진행 중 | 개발 MES 메뉴 42개와 주요 진입 흐름 30개를 기록 |
| 실제 웹-Figma 대응 | 참고 위치 연결 | 최신 원본 38개, 후속 수정 3개, 위치 미확인 1개. 픽셀·동작 검증은 0개 |

따라서 다음 단계는 화면을 더 많이 추가하는 일이 아니라, 이번 핵심 계약을 실제 대표 Figma·브라우저 검증으로 안정화하고 화면 요청이 생기는 순서대로 적용 범위를 넓히는 일이다.

## 2026-08-24 구현 배치

- `component-usage-contracts.json`: 핵심 컴포넌트 20개의 사용·금지·허용 부모·필수 상태·대안·근거 계약
- `pattern-contracts.json`: 핵심 패턴 10개의 슬롯·상태 모델·동작 대상·스크롤 소유자·허용 action set 계약
- `screen-specs.json`: 대표 화면 3개의 순서형 SectionInstance, 컴포넌트, 동작과 스크롤 명세
- Resolver: ScreenSpec 상속과 `decisionTrace` 출력
- 구현 감사: `data-section-id` 순서, 패턴 marker, action set과 컴포넌트 부모 계약 검사
- 생성기: 우측 슬라이드 폼·편집 목록과 중앙 검색 테이블 stable 템플릿, 페이지 엔티티 목록 provisional 템플릿

이 배치는 코드 계약과 결정성 fixture를 구현한 상태다. 원본이 있는 모든 화면의 픽셀·동작 검증이 끝났다는 의미는 아니다.

## 2026-08-25 실제 웹 관찰 배치

현재 개발 MES의 메뉴 화면 42개, 주요 등록·편집·조회 진입 흐름 30개와 연결 결과 3개를 `web-ui-usage-inventory.json`에 기록했다. 이 자료는 컴포넌트가 실제로 쓰이는 위치와 팝업 연결 구조를 찾기 위한 근거다. 개발 웹의 수치와 구조를 그대로 표준으로 복사하지 않도록 권한을 `observed-not-canonical`로 고정했다.

이 배치의 범위는 디자인 시스템과 UI 조합이다. 권한, API, 데이터 처리 조건 같은 내부 업무 정책은 구조화하지 않는다. 상세 범위와 남은 항목은 [실제 MES 웹 UI 사용 맥락 인벤토리](./실제_MES_웹_UI_사용_맥락_인벤토리.md)에 정리했다.

같은 날 실제 웹 42개 메뉴를 최신 Figma 원본 위치와 연결했다. 38개는 최신 화면설계서, 3개는 후속 수정 구역에서 후보를 찾았고 KPI 1개는 원본 위치를 찾지 못했다. 이 수치는 원본 후보의 위치를 연결한 결과이며 시각·동작 일치 검증 수치는 모두 0이다. 상세 판단은 [실제 MES 웹과 Figma 대조 참고](./실제_MES_웹_Figma_대조_참고.md)를 따른다.

## 지금 갖추어진 것

현재 생성 문법은 아래 계층을 구분한다.

```text
ScreenSpec
  = ContextDecision
  + Shell
  + SectionInstance[1..n]
  + BehaviorReference[0..n]
  + ActionSet

SectionInstance
  = SectionFrame
  + SectionPattern
  + ScreenData / Copy / FieldConfig
```

이 방향은 맞다. 중앙 팝업과 우측 슬라이드 팝업을 구분하고, 표준 섹션 프레임과 검색·테이블·폼·편집 목록 같은 내부 패턴을 분리했으며, 저장·취소·스크롤·선택 같은 동작 규칙도 별도 레지스트리에서 조회할 수 있다. 과거처럼 화면 전체를 하나의 거대한 패턴으로만 취급하는 문제는 많이 줄었다.

또한 `getImplementationContext(screenId)`는 화면이 참조한 패턴, 그 패턴이 요구하는 컴포넌트, 관련 맥락 규칙과 공통 결정을 한 번에 반환한다. 즉 AI가 근거 없이 임의 UI를 만드는 것을 막을 재료는 이미 있다.

## 남아 있는 경계

### 1. 컴포넌트 사용 계약이 핵심 20개에 집중되어 있다

핵심 20개는 다음 정보가 타입과 독립 데이터로 존재한다. 나머지 컴포넌트는 실제 화면 조합에서 사용 근거가 생길 때 같은 깊이로 확장한다.

- 언제 사용하고 언제 사용하지 않는가
- 허용되는 부모 셸과 섹션 패턴
- 필수 상태와 허용 variant
- 크기·내용·행동 제약
- 대체 가능한 컴포넌트와 선택 우선순위
- 접근성·키보드·포커스 계약
- 이를 입증하는 원본 화면과 대표 예시

`Button`, `Badge`, `Link`와 핵심 입력·테이블·Shell은 자유문장 추론만으로 고르지 않는다. 다만 핵심 계약 밖 자산은 아직 공통 context rule과 기존 레지스트리 설명에 의존한다.

### 2. 순서형 ScreenSpec은 대표 3개에 우선 적용됐다

대표 3개는 아래 항목을 `screen-specs.json`에서 확정한다. 나머지 25개 화면의 `patternRefs`는 여전히 호환용 평면 목록이므로 수정·생성 요청이 생기는 순서로 이관한다.

- 섹션의 실제 표시 순서
- 각 패턴이 들어갈 셸의 슬롯
- 섹션 제목·필드·표 컬럼과 연결되는 컴포넌트
- 선택 행, 인라인 편집, 필터 추가가 적용되는 정확한 대상
- 본문과 내부 표 중 누가 스크롤을 소유하는가
- 화면별 action set과 취소 시 복원 범위

대표 3개에서 resolver는 렌더링 가능한 순서형 조합 명세와 결정 근거를 반환한다. 미이관 화면에서는 기존 규칙 묶음을 반환한다.

### 3. 패턴 슬롯·경계 계약도 핵심 10개부터 적용됐다

핵심 10개는 `slots`, `stateModel`, `behaviorTargets`, `useWhen`, `doNotUseWhen`, `evidence`, `goldenScreenIds`, `implementationMarkers`를 가진다. 나머지 패턴은 표준 생성 경로에 들어오기 전에 같은 계약을 갖춰야 한다.

### 4. 실제 사용 근거가 모든 자산에 연결되지는 않았다

- 패턴의 `requiredComponents`에서 직접 참조되는 컴포넌트는 88개 중 37개다.
- 화면에서 직접 참조되지 않는 패턴은 15개다.
- 화면 ID로 연결된 시각 회귀 사례가 없는 화면은 7개다.

참조되지 않았다고 곧바로 불필요한 자산은 아니다. `Tooltip`, `Toast`, `EmptyState`처럼 상황에 따라 등장하는 원자 컴포넌트도 있다. 문제는 현재 데이터만으로는 **의도적으로 독립적인 것인지, 아직 맥락 연결이 빠진 것인지**를 AI가 구분하기 어렵다는 점이다.

### 5. 생성기는 의도적으로 범용 자유 JSX가 아니다

현재 결정형 템플릿은 우측 슬라이드 폼 + 편집 목록, 중앙 검색 테이블, 페이지 엔티티 목록의 세 종류다. 앞의 두 종류는 stable이고 페이지 목록은 provisional이다. 중앙 비교/확인, 마스터-상세 등 미지원 Recipe는 레지스트리 계약을 AI에게 제공한 뒤 감사하는 방식이므로, 동일 TSX까지 보장하지 않는다.

## 이번에 적용한 진행 순서

### 1단계. 핵심 웹 컴포넌트의 선택 계약 강화 — 구현됨

화면을 더 추가하기 전에 사용 빈도가 높은 안정 컴포넌트부터 레지스트리 스키마를 확장한다.

우선 대상은 Button, Link, Badge, Input, NumberInput, SearchInput, Select, Checkbox, Radio, Filter, Table, Modal, SideSlidePanel, SectionHeader, SectionFrame, DialogFooter처럼 지금까지 오류가 반복된 자산이다.

각 항목에 다음 필드를 둔다.

```ts
type ComponentUsageContract = {
  capabilities: string[];
  variants: string[];
  requiredStates: string[];
  useWhen: string[];
  doNotUseWhen: string[];
  allowedParents: string[];
  constraints: string[];
  accessibility: string[];
  evidence: string[];
};
```

88개를 한 번에 형식적으로 채우지 않는다. 먼저 실제 화면 조합에 반복 사용되는 핵심 자산을 완료하고, 나머지는 사용 근거가 생길 때 확장한다.

### 2단계. 핵심 섹션 패턴을 구조화한다 — 구현됨

다음 패턴부터 슬롯과 상태 모델을 명시한다.

- 표준 섹션 프레임
- 폼 그리드
- 필터·검색·테이블
- 선택 행 + 인라인 편집 테이블
- 편집 가능한 행 목록
- 검사항목 목록
- 조회 조건 영역

각 패턴은 허용 자식, 필수 슬롯, 선택 슬롯, 스크롤 소유자, 동작 대상, 허용 action set, 사용/금지 맥락, 원본 근거와 대표 화면을 가져야 한다.

### 3단계. 대표 화면을 순서가 있는 ScreenSpec으로 이관한다 — 3종 구현됨

처음부터 28개 전체를 바꾸기보다 서로 다른 구조를 대표하는 3개를 골든 명세로 만든다.

1. 우측 슬라이드: 폼 + 편집 목록
2. 중앙 팝업: 검색 + 선택 테이블 + 인라인 편집
3. 전체 페이지: 조회 조건 + 그룹형 테이블

각 화면은 아래처럼 섹션을 순서대로 소유한다.

```json
{
  "shell": "shell.side-slide",
  "sections": [
    {
      "id": "basic-information",
      "frame": "frame.standard-section",
      "pattern": "section.form-grid",
      "slot": "body",
      "behaviorRefs": []
    },
    {
      "id": "items",
      "frame": "frame.standard-section",
      "pattern": "section.editable-row-list",
      "slot": "body",
      "behaviorRefs": ["behavior.row-edit"]
    }
  ],
  "actionSet": "action-set.cancel-save"
}
```

### 4단계. 맥락을 안내가 아니라 검사로 바꾼다 — 구현됨

resolver는 선택된 셸·섹션·컴포넌트마다 적용된 규칙과 제외된 후보의 이유를 `decision trace`로 출력해야 한다. 구현 감사는 다음을 실패로 처리한다.

- 허용되지 않은 부모 안의 컴포넌트
- 패턴에 없는 임의 wrapper와 장식
- 원시 HTML control 사용
- 잘못된 action set과 취소 복원 누락
- 잘못된 스크롤 소유자와 가로 overflow
- ScreenSpec의 섹션 순서·필수 슬롯 불일치

이후 대표 3개 화면을 같은 요청으로 반복 생성해 구조 해시, 동작 테스트, 시각 회귀가 안정적으로 반복되는지 확인한다.

### 5단계. 검증된 문법만 생성 템플릿으로 승격한다 — 2종 stable, 1종 provisional

중앙 조회 팝업은 stable 템플릿으로 추가했다. 전체 페이지 조회 목록은 구조 결정성까지 구현했으나 `Pagination` 성숙도와 실제 원본 근거가 남아 provisional로 유지한다. 새 템플릿은 기존과 동일하게 검증된 문법만 승격한다.

## 완료 판정 기준

웹 맥락 체계화는 다음 조건을 모두 충족할 때 해당 범위가 완료됐다고 판단한다.

- 핵심 컴포넌트가 명시적 사용·금지·상태·부모·제약 계약을 가진다.
- 표준 패턴이 슬롯, 자식, 상태, 동작 대상, 스크롤, action set, 근거 화면을 가진다.
- 대표 ScreenSpec이 섹션 순서와 슬롯까지 구조적으로 표현된다.
- AI가 선택한 자산과 제외한 후보의 이유를 decision trace로 설명한다.
- 잘못된 조합은 렌더링 전에 감사 단계에서 실패한다.
- 같은 요청을 반복했을 때 셸·섹션·action set·동작 구조가 동일하다.
- 원본이 있는 화면은 구조·렌더링·동작 검증을 각각 통과한다.

## 바로 다음 작업

다음 배치는 원본 후보 위치가 연결된 화면을 한 번에 하나씩 같은 viewport로 대조한다. 행 선택 후 활성화되는 편집·출력·승인, 선행 입력 뒤 열리는 중첩 팝업, 행별 상세 링크도 해당 화면을 검증할 때 함께 본다. 결과는 곧바로 표준으로 승격하지 않고 `구현 오류`, `원본 오류`, `의도적 예외`, `정규화 후보`, `근거 부족`으로 판정한다. 판정된 유형부터 순서형 ScreenSpec과 사용 계약 범위를 넓힌다.

전체 프로젝트 상태는 계속 `in-progress`다. 모바일은 사용자 결정으로 `deferred`이며, 웹의 맥락 체계화와 생성·검증 자동화가 남아 있다.
