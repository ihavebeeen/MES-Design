# 웹 UI 맥락 체계화 현황

## 결론

웹 컴포넌트와 대표 패턴은 상당 부분 모였고, 화면에서 필요한 규칙을 조회하는 기본 구조도 있다. 그러나 아직 **“컴포넌트가 존재한다”에서 “AI가 어느 화면의 어느 위치에 왜 써야 하는지 하나의 답으로 결정한다”까지 완성된 상태는 아니다.**

현재 수준을 나누면 다음과 같다.

| 영역 | 현재 판단 | 근거 |
|---|---|---|
| 자산 인벤토리 | 강함 | 컴포넌트 88개와 패턴 60개가 레지스트리에 등록됨 |
| 화면-패턴 연결 | 기본 구조 있음 | 화면 28개가 모두 `patternRefs`와 상태 규칙을 가짐 |
| 공통 맥락 규칙 | 기본 구조 있음 | 활성 규칙 34개, 공통 결정 7개, 보류 0개 |
| 컴포넌트 선택 계약 | 부분적 | 88개 중 35개만 자유문장 `rules`를 가지며 명시적 `useWhen`, `doNotUseWhen`, 상태·제약 계약이 없음 |
| 화면 내부 조합 순서 | 부분적 | 화면은 패턴의 평면 목록을 가지며 섹션 순서·슬롯·동작 대상이 구조화되지 않음 |
| 자동 생성 | 파일럿 | 결정적 생성 템플릿은 `side-slide-form-editable-list.v1` 한 종류 |
| 원본·동작 검증 연결 | 부분적 | 28개 화면 모두 상호작용 감사가 있으나, 화면 ID에 직접 연결된 시각 회귀 사례는 21개 |

따라서 다음 단계는 화면을 더 많이 추가하는 일이 아니라, 이미 모은 자산 사이의 **선택 규칙과 조합 문법을 기계가 강제할 수 있는 계약으로 바꾸는 일**이다.

## 지금 갖추어진 것

현재 생성 문법은 아래 계층을 구분한다.

```text
ScreenSpec
  = ContextDecision
  + Shell
  + SectionInstance[1..n]
  + BehaviorReference[0..n]
  + ActionSet

SectionInstance
  = SectionFrame
  + SectionPattern
  + ScreenData / Copy / FieldConfig
```

이 방향은 맞다. 중앙 팝업과 우측 슬라이드 팝업을 구분하고, 표준 섹션 프레임과 검색·테이블·폼·편집 목록 같은 내부 패턴을 분리했으며, 저장·취소·스크롤·선택 같은 동작 규칙도 별도 레지스트리에서 조회할 수 있다. 과거처럼 화면 전체를 하나의 거대한 패턴으로만 취급하는 문제는 많이 줄었다.

또한 `getImplementationContext(screenId)`는 화면이 참조한 패턴, 그 패턴이 요구하는 컴포넌트, 관련 맥락 규칙과 공통 결정을 한 번에 반환한다. 즉 AI가 근거 없이 임의 UI를 만드는 것을 막을 재료는 이미 있다.

## 아직 완벽하지 않은 이유

### 1. 컴포넌트의 “사용 맥락”이 기계 계약이 아니다

현재 컴포넌트 항목은 이름, 분류, 출처, 안정 상태, 문서 경로, 선택적 자유문장 규칙 정도를 가진다. 다음 정보는 타입과 데이터에 독립 필드로 존재하지 않는다.

- 언제 사용하고 언제 사용하지 않는가
- 허용되는 부모 셸과 섹션 패턴
- 필수 상태와 허용 variant
- 크기·내용·행동 제약
- 대체 가능한 컴포넌트와 선택 우선순위
- 접근성·키보드·포커스 계약
- 이를 입증하는 원본 화면과 대표 예시

이 때문에 AI는 `Button`, `Badge`, `Link`가 모두 존재한다는 사실은 알지만, 특정 문맥에서 무엇을 골라야 하는지 자유문장을 해석해 추론해야 한다. 과거에 링크를 배지로 만들거나 원시 `button`을 직접 쓴 문제가 다시 생길 여지가 남는다.

### 2. 화면이 패턴의 “목록”만 가지고 있다

현재 화면 레지스트리의 `patternRefs`는 어떤 패턴들이 필요한지는 알려주지만 아래를 확정하지 못한다.

- 섹션의 실제 표시 순서
- 각 패턴이 들어갈 셸의 슬롯
- 섹션 제목·필드·표 컬럼과 연결되는 컴포넌트
- 선택 행, 인라인 편집, 필터 추가가 적용되는 정확한 대상
- 본문과 내부 표 중 누가 스크롤을 소유하는가
- 화면별 action set과 취소 시 복원 범위

즉 현재 resolver가 반환하는 결과는 유용한 **규칙 묶음**이지만, 그대로 렌더링 가능한 **한 개의 조합 명세**는 아니다.

### 3. 패턴도 슬롯과 경계가 충분히 구조화되지 않았다

패턴은 필요한 컴포넌트와 자유문장 규칙을 갖지만 `slots`, `required/optional children`, `stateModel`, `behaviorTargets`, `useWhen`, `doNotUseWhen`, `evidence`, `goldenExample`이 없다. 그래서 비슷해 보이는 두 패턴을 언제 분기해야 하는지와, 패턴 내부에 무엇을 추가하면 안 되는지를 자동 검사가 완전히 판정하지 못한다.

### 4. 실제 사용 근거가 모든 자산에 연결되지는 않았다

- 패턴의 `requiredComponents`에서 직접 참조되는 컴포넌트는 88개 중 37개다.
- 화면에서 직접 참조되지 않는 패턴은 15개다.
- 화면 ID로 연결된 시각 회귀 사례가 없는 화면은 7개다.

참조되지 않았다고 곧바로 불필요한 자산은 아니다. `Tooltip`, `Toast`, `EmptyState`처럼 상황에 따라 등장하는 원자 컴포넌트도 있다. 문제는 현재 데이터만으로는 **의도적으로 독립적인 것인지, 아직 맥락 연결이 빠진 것인지**를 AI가 구분하기 어렵다는 점이다.

### 5. 생성기는 아직 범용이 아니다

현재 결정적으로 코드를 생성하는 템플릿은 우측 슬라이드 팝업의 폼 + 편집 목록 조합 한 종류다. 나머지 중앙 팝업, 조회 테이블, 전체 페이지, 마스터-상세 화면은 레지스트리 맥락을 AI에게 제공한 뒤 AI가 구현하는 방식이다. 그러므로 같은 요청을 다른 PC나 다른 AI가 받아도 구조가 완전히 같다고 보장할 수 있는 단계는 아니다.

## 권장 진행 순서

### 1단계. 핵심 웹 컴포넌트의 선택 계약 강화

화면을 더 추가하기 전에 사용 빈도가 높은 안정 컴포넌트부터 레지스트리 스키마를 확장한다.

우선 대상은 Button, Link, Badge, Input, NumberInput, SearchInput, Select, Checkbox, Radio, Filter, Table, Modal, SideSlidePanel, SectionHeader, SectionFrame, DialogFooter처럼 지금까지 오류가 반복된 자산이다.

각 항목에 다음 필드를 둔다.

```ts
type ComponentUsageContract = {
  capabilities: string[];
  variants: string[];
  requiredStates: string[];
  useWhen: string[];
  doNotUseWhen: string[];
  allowedParents: string[];
  constraints: string[];
  accessibility: string[];
  evidence: string[];
};
```

88개를 한 번에 형식적으로 채우지 않는다. 먼저 실제 화면 조합에 반복 사용되는 핵심 자산을 완료하고, 나머지는 사용 근거가 생길 때 확장한다.

### 2단계. 핵심 섹션 패턴을 구조화한다

다음 패턴부터 슬롯과 상태 모델을 명시한다.

- 표준 섹션 프레임
- 폼 그리드
- 필터·검색·테이블
- 선택 행 + 인라인 편집 테이블
- 편집 가능한 행 목록
- 검사항목 목록
- 조회 조건 영역

각 패턴은 허용 자식, 필수 슬롯, 선택 슬롯, 스크롤 소유자, 동작 대상, 허용 action set, 사용/금지 맥락, 원본 근거와 대표 화면을 가져야 한다.

### 3단계. 대표 화면을 순서가 있는 ScreenSpec으로 이관한다

처음부터 28개 전체를 바꾸기보다 서로 다른 구조를 대표하는 3개를 골든 명세로 만든다.

1. 우측 슬라이드: 폼 + 편집 목록
2. 중앙 팝업: 검색 + 선택 테이블 + 인라인 편집
3. 전체 페이지: 조회 조건 + 그룹형 테이블

각 화면은 아래처럼 섹션을 순서대로 소유한다.

```json
{
  "shell": "shell.side-slide",
  "sections": [
    {
      "id": "basic-information",
      "frame": "frame.standard-section",
      "pattern": "section.form-grid",
      "slot": "body",
      "behaviorRefs": []
    },
    {
      "id": "items",
      "frame": "frame.standard-section",
      "pattern": "section.editable-row-list",
      "slot": "body",
      "behaviorRefs": ["behavior.row-edit"]
    }
  ],
  "actionSet": "action-set.cancel-save"
}
```

### 4단계. 맥락을 안내가 아니라 검사로 바꾼다

resolver는 선택된 셸·섹션·컴포넌트마다 적용된 규칙과 제외된 후보의 이유를 `decision trace`로 출력해야 한다. 구현 감사는 다음을 실패로 처리한다.

- 허용되지 않은 부모 안의 컴포넌트
- 패턴에 없는 임의 wrapper와 장식
- 원시 HTML control 사용
- 잘못된 action set과 취소 복원 누락
- 잘못된 스크롤 소유자와 가로 overflow
- ScreenSpec의 섹션 순서·필수 슬롯 불일치

이후 대표 3개 화면을 같은 요청으로 반복 생성해 구조 해시, 동작 테스트, 시각 회귀가 안정적으로 반복되는지 확인한다.

### 5단계. 검증된 문법만 생성 템플릿으로 승격한다

대표 화면이 통과한 뒤 중앙 조회 팝업, 전체 페이지 조회 목록 등 다음 생성 템플릿을 추가한다. 템플릿 수를 먼저 늘리면 불완전한 맥락이 코드로 고착된다.

## 완료 판정 기준

웹 맥락 체계화는 다음 조건을 모두 충족할 때 해당 범위가 완료됐다고 판단한다.

- 핵심 컴포넌트가 명시적 사용·금지·상태·부모·제약 계약을 가진다.
- 표준 패턴이 슬롯, 자식, 상태, 동작 대상, 스크롤, action set, 근거 화면을 가진다.
- 대표 ScreenSpec이 섹션 순서와 슬롯까지 구조적으로 표현된다.
- AI가 선택한 자산과 제외한 후보의 이유를 decision trace로 설명한다.
- 잘못된 조합은 렌더링 전에 감사 단계에서 실패한다.
- 같은 요청을 반복했을 때 셸·섹션·action set·동작 구조가 동일하다.
- 원본이 있는 화면은 구조·렌더링·동작 검증을 각각 통과한다.

## 바로 다음 작업

다음 배치는 **“핵심 웹 컴포넌트 사용 계약 + 대표 3개 ScreenSpec”**으로 잡는 것이 가장 효율적이다. 새 화면을 더 그리는 것보다 기존 자산을 AI가 틀리게 조합할 여지를 먼저 줄여야 한다. 이 배치 결과를 보고 중앙 팝업과 전체 페이지 생성 템플릿을 확장한다.

전체 프로젝트 상태는 계속 `in-progress`다. 모바일은 사용자 결정으로 `deferred`이며, 웹의 맥락 체계화와 생성·검증 자동화가 남아 있다.
