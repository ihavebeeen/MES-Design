# 실제 MES 웹 UI 사용 맥락 인벤토리

## 무엇을 기록했나

개발 MES에서 확인한 메뉴 화면과 주요 팝업 진입 흐름을 디자인 시스템의 **관찰 근거**로 기록했다.

- 메뉴 화면: 42개
- 주요 등록·편집·조회 진입 흐름: 30개
- 한 팝업 안에서 다시 열리는 연결 결과: 3개
- 화면 구조 유형: 조회 목록, 분석 대시보드, 설비 모니터링, 추적·마스터 상세

기계가 읽는 원본은 `component-library/src/design-system/registry/web-ui-usage-inventory.json`이다.

## 이 자료의 역할

이 인벤토리는 다음 질문에 답한다.

- 어느 메뉴에서 어떤 컴포넌트 조합이 반복되는가
- 어떤 버튼이 중앙 모달 또는 우측 슬라이드 팝업을 여는가
- 팝업이 한 단계로 끝나는지, 선택 후 다음 팝업으로 연결되는지
- 같은 기능이 서로 다른 셸에서 열리거나 가로 넘침이 생기는 등 실제 구현의 불일치가 있는가

권한·API·데이터 처리 순서 같은 업무 정책은 기록하지 않는다. 디자인 시스템 선택과 UI 조합에 필요한 화면 구조만 다룬다.

## 표준과의 관계

실제 웹은 이미 구현된 사용 사례이지만 그대로 표준은 아니다. 우선순위는 다음과 같다.

1. 최신 Figma 원본에서 확인한 구조와 의도
2. 승인된 토큰·컴포넌트·패턴·맥락 규칙
3. 실제 웹에서 반복 관찰된 사용 위치
4. 단일 화면의 예외 구현

실제 웹과 Figma가 다르면 원인을 `원본 오류`, `구현 오류`, `의도적 예외`, `정규화 후보`로 판정한 뒤 표준에 반영한다. 관찰값만으로 컴포넌트 기본값이나 팝업 셸을 바꾸지 않는다.

## 현재 확인된 연결 사례

- 생산실적 등록: 중앙의 작업 선택 뒤 우측 생산실적 등록으로 연결
- 입고 등록: 중앙의 발주 선택 뒤 우측 입고 등록으로 연결
- 생산실적 안의 운전일지: 직접 메뉴 등록과 다른 셸에서 열려 최종 판정 필요

이처럼 연결 단계는 화면 한 장의 스크린샷만으로 알 수 없으므로 별도 흐름으로 관리한다.

## AI가 사용하는 방법

- `getImplementationContext(screenId)`는 등록 화면과 연결된 실제 웹 사용 근거를 함께 반환한다.
- 화면 계약 resolver도 `implementation.observedWebUsage`에 같은 근거와 권한을 포함한다.
- 로컬 MCP의 `mes_get_web_usage_context`로 메뉴명, 화면 ID, 버튼명 또는 팝업 제목을 검색할 수 있다.
- 생성 AI는 관찰 근거를 후보 탐색에 사용하되, `observed-not-canonical` 값을 표준 수치로 복사하면 안 된다.

## 아직 확인하지 않은 범위

- 행 선택 후에만 활성화되는 편집·출력·승인 팝업
- 선행 입력이 있어야 열리는 조건부 중첩 팝업
- 모든 행별 링크와 상세 팝업의 반복 유형
- 각 관찰 화면과 최신 Figma의 최종 대조

따라서 현재 상태는 `observed-in-progress`다. 42개 메뉴의 기본 구조와 30개 주요 진입점은 기록했지만, 전체 상태·권한·데이터 조건 조합을 모두 확인했다는 뜻은 아니다.
