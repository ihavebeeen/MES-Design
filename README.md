# MES UI 디자인 자동화

우리 MES의 디자인 자산과 사용 규칙을 코드로 정리하고, AI가 이 기준을 활용해 새로운 화면을 만들도록 구성한 프로젝트입니다.

Figma 화면을 단순히 코드로 옮기는 데서 시작했으며, 현재는 디자인 자산의 실제 사용 방식, 업무 맥락, 생성 전 자산 선택, 결과 검증까지 연결해 신규 UI 제작 POC를 진행하고 있습니다.

## 목표

- 기존 MES의 디자인과 화면 구성 방식을 회사 자산으로 정리합니다.
- AI가 새로운 화면을 만들 때 기존 자산과 조합을 먼저 사용하게 합니다.
- 기존 자산으로 해결하기 어려운 경우에만 새로운 디자인을 제안하게 합니다.
- 생성 결과가 기존 MES에서 벗어났는지 코드와 화면을 함께 확인합니다.
- 다른 PC와 AI 환경에서도 같은 저장소와 기준으로 작업할 수 있게 합니다.

## 디자인 자산 구조

제작한 코드는 크게 세 단계로 구분합니다.

### 1. 아톰

가장 작은 디자인 단위입니다.

- 폰트와 글자 위계
- 컬러
- 간격
- 모서리 값
- 테두리와 그림자
- 아이콘

### 2. 컴포넌트

아톰을 사용해 만든 작은 단위의 디자인 산출물입니다.

- 버튼과 링크
- 입력창, 체크박스, 라디오
- 태그와 상태 표시
- 날짜, 검색, 필터
- 테이블
- 팝업을 구성하는 공통 요소

### 3. 패턴

컴포넌트가 배치되어 화면의 한 영역이나 전체 구조를 이루는 단계입니다.

- 메인 목록
- 중앙 팝업
- 우측 슬라이드 팝업
- 기본정보, 품목정보, 검사항목, 목록 영역
- 행 선택과 편집
- 항목 추가와 삭제
- 저장과 취소

내부 코드에서는 패턴을 화면 틀, 섹션, 행동, 완성 화면으로 더 세분화합니다. 사용자는 아톰·컴포넌트·패턴의 세 단계로 이해하면 됩니다.

## 지금까지 구축한 것

### 디자인 자산 수집

Figma와 기존 MES 화면에서 반복되는 아톰, 컴포넌트, 패턴을 코드로 옮겼습니다. 각 자산의 형태, 상태, 사용 가능한 옵션을 확인할 수 있는 웹 카탈로그도 함께 구성했습니다.

### 실제 사용 방식 수집

자산이 존재한다는 사실만 기록하지 않고, 실제 MES에서 어디에 배치되고 어떤 행동과 연결되는지 수집했습니다.

예를 들어 버튼·링크·상태 태그의 역할, 중앙 팝업과 우측 슬라이드 팝업의 차이, 테이블과 반복 입력 영역의 차이, 팝업 제목과 내부 제목의 차이를 구분했습니다.

### 사용 맥락 추가

수집한 결과를 바탕으로 모든 컴포넌트와 패턴에 선택 맥락을 연결했습니다. 컴포넌트는 역할·사용 조건·비사용 조건·대안을 기본으로 가지며, 구조와 동작에 민감한 자산은 상세 계약을 추가로 가집니다. AI는 화면을 만들기 전에 다음 순서로 자산을 선택합니다.

화면마다 다른 말로 판단하지 않도록 14개의 공통 맥락 축을 정리했습니다. 업무 목적, 대상과 범위, 저장 단위, 정보 역할과 관계, 동시 참조, 업무 순서, 반복 입력, 비교, 선택 방식, 상태, 진입과 종료, 화면 환경, 근거의 확실성을 함께 봅니다.

이 맥락은 문서 설명으로만 남지 않습니다.

- 화면 요청에서 확인된 사실을 관련 맥락 축에 연결합니다.
- 화면 선택을 바꾸는 중요한 빈칸만 질문하고, 나머지는 억지로 채우지 않습니다.
- 각 요소에 기존 컴포넌트를 연결할 때 해당 종류와 관련된 맥락만 비교합니다.
- 컴포넌트의 연결 관계를 확인한 뒤 섹션 패턴과 페이지·팝업 틀을 선택합니다.
- 선택 결과에는 사용한 근거와 아직 확인되지 않은 항목을 구분해 남깁니다.
- 한 가지 이유만으로 팝업·섹션·컴포넌트를 확정하거나, 관련 없는 근거를 재사용하면 검사에서 막습니다.

1. 화면에서 확인·입력·비교·선택해야 하는 정보와 그 이유를 구분합니다.
2. 각 정보와 행동에 맞는 기존 컴포넌트를 찾고 사용 맥락과 상태를 확인합니다.
3. 선택한 컴포넌트들이 같은 대상·저장 단위·작업 순서 안에서 어떻게 연결되는지 설명합니다.
4. 그 연결을 지원하는 섹션 패턴과 페이지·팝업 틀을 선택합니다.
5. 정확한 자산이 없으면 비슷한 자산의 의미와 동작이 유지되는지 확인하고, 대체할 수 없을 때만 새로운 자산을 제안합니다.

실제 MES 웹과 기능명세서는 업무 흐름을 이해하기 위한 참고 자료로 사용합니다. 한 화면에서만 발견된 표현은 개별 사례로 유지하고, 반복 근거가 확인되면 공통 규칙으로 반영합니다.

컴포넌트와 완성 화면 사이의 반복 조합은 **섹션 패턴**으로 관리합니다. 현재 공통 섹션 패턴 18종과 등록 화면 29종의 연결을 전수 원장으로 관리하며, 한 화면에만 있는 조합은 화면 전용으로 구분합니다. Figma 노드 등록, 실제 원본 확인, 웹 참고, 코드 구현, 상세 화면 계약의 완료 상태도 서로 섞지 않고 표시합니다. `npm run check:section-compositions`는 코드나 원장이 변경된 뒤 섹션 조합 기록이 오래되었거나 선택 맥락이 빠진 경우 실패합니다.

대표 Figma 웹 화면은 별도의 **기초 레시피**로 정리했습니다. 화면별 목적과 정보 관계, 배치 성격, 밀도, 위계와 색 사용을 참고하되 그대로 복제하지 않습니다. 이 화면들은 초기 디자인이므로 버튼·입력·테이블·팝업 같은 실제 UI는 현재 승인된 컴포넌트로 구성합니다. 예를 들어 과거 표에 세로선이 없더라도 현재 Table의 세로 구분선 계약을 유지합니다. 신규 UI는 업무 목적과 컴포넌트 연결을 먼저 정한 뒤 가장 가까운 레시피의 특징만 골라 사용합니다.

### 생성 결과 검증

AI가 그럴듯하지만 MES와 다른 화면을 끝까지 제작하지 않도록 검증 단계를 연결했습니다.

- 기존 자산과 패턴을 우선 사용했는지 확인
- 메인 목록, 중앙 팝업, 우측 슬라이드 유형 확인
- 정보 위계와 섹션 순서 확인
- 임의의 설명, 장식, 버튼 추가 여부 확인
- 간격, 색상, 글꼴, 스크롤 확인
- 체크, 입력, 선택, 저장, 취소 동작 확인
- 기준 화면이 있는 경우 시각 비교

검사를 통과한 화면만 검증된 결과로 제공하며, 임시 시안의 검증과 정식 디자인 자산 승격은 별도로 관리합니다.

### 로컬 Skill과 MCP

AI가 저장소의 자산과 규칙을 읽고 같은 절차로 화면을 만들 수 있도록 전용 Skill을 구성했습니다. 로컬 MCP는 컴포넌트·패턴·화면 조회, 요청 해석, 자산 선택, 생성과 검증 기능을 AI 도구에 제공합니다.

- Skill: `.agents/skills/generate-mes-ui/SKILL.md`
- MCP 실행: `component-library`에서 `npm run mcp:start`
- MCP 점검: `component-library`에서 `npm run mcp:check`

## 화면 생성 흐름

```text
화면 요청
→ 업무 목적과 필요한 정보 확인
→ 각 정보·행동에 맞는 컴포넌트 맥락 확인
→ 컴포넌트의 연결 관계 구성
→ 연결을 지원하는 패턴과 화면 구조 선택
→ 가까운 기초 레시피의 배치·밀도·시각 분위기 조정
→ 코드 제작
→ 로컬 미리보기
→ 코드·동작·화면 검증
→ 수정 또는 저장소 반영
```

기존 화면 재현은 Figma를 기준으로 비교합니다. 신규 화면은 업무 목적과 반복 검증된 MES 패턴을 기준으로 구성합니다.

## 내 PC에서 열기

Node.js와 Git을 준비하고 저장소를 내려받습니다. `MES-Design` 폴더에서 Git Bash를 열고 실행합니다.

```bash
cd component-library
npm ci
npm run dev
```

처음 내려받았거나 설치 목록이 바뀌었을 때 `npm ci`를 실행합니다. 이후에는 `component-library` 폴더에서 `npm run dev`만 실행하면 됩니다.

브라우저에서 [localhost:3000](http://localhost:3000/)을 열면 디자인 자산, 패턴, 원본 화면과 생성 시안을 확인할 수 있습니다.

## AI에게 화면 요청하기

Codex 같은 AI 작업 도구에서 저장소를 열고 요청합니다.

> 이 저장소의 `.agents/skills/generate-mes-ui/SKILL.md`를 읽고,
> 생산 전에 자재 부족 위험을 확인하는 화면을 만들어줘.
> 메인 목록과 상세 작업용 우측 슬라이드 팝업이 필요해.
> 우리 MES 디자인 시스템으로 만들고 로컬에서 확인할 수 있게 해줘.

요청에는 다음 내용을 알려주는 것이 좋습니다.

- 누가 사용하는 화면인지
- 어떤 업무를 완료하기 위한 화면인지
- 반드시 필요한 정보와 행동
- 함께 확인하면 좋은 보조 정보
- 참고할 기존 화면이나 Figma가 있는지

화면 구성에 영향을 주는 정보가 부족하면 AI가 필요한 내용만 추가로 질문합니다.

## 생성 화면 보관

생성된 화면은 먼저 해당 PC의 임시 미리보기로 저장합니다.

Git에 남길 화면은 AI에게 **“이 시안을 저장소에 보관해줘”**라고 요청하고 변경 내용을 확인한 뒤 커밋합니다. 공통 컴포넌트나 패턴으로 사용할 자산은 별도로 승인합니다.

다른 PC에서는 저장소를 다시 내려받고 `npm ci`, `npm run dev`를 실행하면 동일한 환경에서 작업할 수 있습니다. PC 사이에서 공유할 화면과 규칙은 Git에 보관합니다.

## 검증

일반적인 변경은 AI가 변경 범위에 맞는 검사를 실행합니다.

```bash
cd component-library
npm run check:design-system
npm run verify:changed
```

공통 기반을 변경하거나 전체 배포 전에 확인할 때는 전체 검증을 실행합니다.

```bash
npm run verify:full
```

`verify:full`은 검사 목록 동기화, 디자인 시스템 검사, lint, 시각 테스트, 배포 빌드, 결과 기록을 순서대로 실행합니다. 시각 테스트용 서버는 명령이 직접 시작하고 종료하므로 테스트가 끝난 뒤 Next.js 프로세스가 남아 전체 기록을 막지 않습니다. 마지막 결과는 [전체 검증 결과](./docs/전체_검증_결과.md)에 자동으로 갱신됩니다.

화면 제작을 요청받은 AI가 구현 범위에 맞춰 명령을 실행하고 결과와 남은 항목을 보고하는 방식으로 운영합니다.

## 현재 단계

웹 디자인 시스템을 기반으로 신규 UI POC를 진행하고 있습니다.

- 기존 화면 재현과 팝업 유형 정리는 진행 중입니다.
- 생산 준비도 점검 관리와 자재 부족 위험 모니터 등 기존에 없던 화면을 제작해 선택 기준을 검증했습니다.
- 메인 목록과 팝업 구조는 초기보다 안정되었지만 상태 표현과 업무 행동 선택은 추가 조정이 필요합니다.
- 모바일은 디자인 변경 가능성을 고려해 현재 자산을 보존하고 추후 진행합니다.

### 가중치

영역별로 MES 디자인 시스템을 반영하는 강도를 조절하는 가중치를 설계하고 있습니다.

- `1`에 가까울수록 기존 MES 자산과 조합을 우선합니다.
- 값이 낮아지면 기존 자산으로 해결하기 어려운 영역에서 새로운 제안을 허용합니다.
- 모든 값에서 기존 자산을 먼저 확인한 뒤 새로운 UI의 허용 범위를 결정합니다.

현재는 Skill에 기본 방향을 반영했으며, 수치에 따라 실제 생성과 검증 범위를 조절하는 기능은 POC 결과를 보며 진행하고 있습니다.

## 다음 단계

1. 가중치 적용 방식을 신규 화면 POC로 조정합니다.
2. 반복되는 생성 오류만 공통 맥락과 검증 기준에 반영합니다.
3. 화면 요청, 자산 검색, 생성, 검증이 한 흐름으로 동작하도록 Skill을 안정화합니다.
4. POC가 끝나면 Skill, MCP, 생성기와 검증 기능을 플러그인 형태로 묶는 방안을 검토합니다.
5. 프로젝트 설정, 로컬 미리보기, 생성 요청과 검증을 간단히 실행할 수 있는 실행 도구도 검토합니다.

플러그인과 실행 도구의 목표는 특정 채팅이나 특정 PC에 의존하지 않고, 저장소를 받은 다른 환경에서도 같은 기준으로 MES UI를 제작하게 하는 것입니다.
